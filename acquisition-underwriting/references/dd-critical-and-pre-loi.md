## STAGE 2.5 item 5 (full text)

5. **Pro-forma reassessed property tax + total carrying cost ($/SF)** — compute taxes on the post-sale reassessed basis via the State Reassessment Matrix (assessment ratio × market/price basis × effective millage, net of in-place abatement/PILOT and applicable caps — IN 3% GAV, IA 90% rollback, MD 3-yr phase-in). Report total stabilized OpEx/SF and the reassessment risk tier (HIGH/MED/LOW). In acquisition-value states only (MI), state whether deal structure changes the base. Unknown reassessed tax = capped at T2. **Pre-FULL requirement (Waukee IA audit finding, resolved):** before FULL mode, a county-assessor/local-millage pull MUST be attempted (call/portal query to the county auditor or assessor) — not just disclosed as an open DD item with an [est] flag. If genuinely unattainable pre-FULL, document the specific attempt (date, office, method) alongside the [est] figure; a bare "[est] — verify pre-LOI" with no attempt logged is INCOMPLETE for FULL mode. **Millage lookup ladder (v4.6, modeled on `ora-flood-zoning-dd`'s verified-endpoint fallback pattern):** attempt sources in this order and document which tier resolved the figure — **(1) the state/county's own published static certified-rate document** (e.g. a state DOR/DLGF annual "Certified Tax Rates by District/County" PDF at a stable government URL) — fetchable and citable, PREFERRED whenever it exists; **(2)** the county auditor/assessor's parcel-specific record or phone/portal query (the existing Pre-FULL-requirement attempt above); **(3)** the interactive county/state GIS millage portal (e.g. Indiana's DLGF Gateway) — LAST resort, since these are not indexable by search and require a live interactive session; if reached only this way, log the query date and screen values used; **(4)** only if all three are genuinely unattainable pre-FULL, fall back to the State Reassessment Matrix's cited range MIDPOINT as `[EST]`, and log the attempt per the Pre-FULL requirement. **This ladder exists because tier (3) is what a bare WebSearch reliably fails to reach — tier (1) frequently succeeds where (3) doesn't, since it's a static, search-indexable government PDF rather than an interactive query tool.** **Verified reference data point:** Marion County (Pike Township, tax district 601 INDIANAPOLIS PIKE) 2026 certified gross tax rate = **2.6830%** of assessed value — source: Indiana DLGF, "2026 Certified Tax Rates by District" (in.gov/dlgf/files/2026-reports/2026_Certifed_Tax_Rates_By_District.pdf), certified 2026, retrieved 2026-07-27. Supersedes any earlier `[EST]` range-midpoint figure used for Marion County/Indianapolis screens before this date. **This ladder is a sourcing-discipline procedure, not yet a dedicated verified-endpoint skill** — a future `ora-millage-lookup`-style skill (analogous to `ora-flood-zoning-dd`'s registry of verified NFHL/zoning-GIS endpoints) is a stated candidate for systematization once a second state's static-document endpoint is confirmed; until then, run the ladder manually per state/county at this item. **Verified reference data point (DC — added v4.7, 2026-08-02; query form corrected and re-verified live 2026-08-03):** Washington DC parcel data — owner, use/class, assessment (current + proposed), 10-year tax history, and last sale — all resolve in ONE query against the DC OTR/DCGIS ArcGIS REST service `maps2.dcgis.dc.gov/dcgis/rest/services/DCGIS_DATA/Property_and_Land_WebMercator/MapServer/40/query` (layer 40 = *Owner Polygons — Common Ownership Layer*, 222 fields; `outFields=*`, `returnGeometry=false`, `f=json`). **SSL IS FIXED-WIDTH — this is the trap:** the key is 4-char square + padding + 4-char lot, e.g. `SSL='0199    0821'` with **four** spaces. A single- or double-space literal returns **HTTP 200 with zero features** — a 200 here is NOT evidence of data, and a mis-padded query reads exactly like a parcel that doesn't exist (verified null vs. inferred null). Use `SSL LIKE '0199%0821'` when the padding is uncertain. Fields that carry the underwriting inputs: `OWNERNAME` / `PREMISEADD` / `USECODE` / `CLASSTYPE` / `TAXRATE` / `LANDAREA`; `OLDTOTAL` (current assessment) and `NEWTOTAL` (proposed); `ANNUALTAX` plus `CY1–CY2TAX` and `PY1–PY10TAX` (10-year history); `SALEPRICE` / `SALEDATE` (epoch ms). **Read the taxable base, not the headline assessment:** DC phases in assessment increases, so `ANNUALTAX ÷ TAXRATE` recovers the actual taxable base and will not equal `OLDTOTAL`. Worked validation, 1518 K St NW (SSL 0199 0821, retrieved 2026-08-02, re-verified 2026-08-03): `OWNERNAME` 1518 K STREET LLC · `SALEPRICE` $5,800,000 on 2012-12-20 · `OLDTOTAL` $5,049,400 vs `NEWTOTAL` $3,488,890 · `ANNUALTAX` $48,954.02 ÷ 1.65% = **$2,966,910 taxable base**, i.e. ~41% below the current headline assessment purely on phase-in — and a sale resets that base to market, which is precisely the reassessment delta this item exists to compute. **DC Class 2 commercial rates (FY2026): $1.65/$100 ≤$5M · $1.77/$100 $5–10M · $1.89/$100 >$10M, graduated** (the subject's `TAXRATE` field returns 1.65, consistent with its sub-$5M taxable base). DC transfer + recordation combined **2.9%** commercial (effective 10/1/2023). **Tier-1-equivalent** for this ladder: a static government REST service — search-free, scriptable, no interactive portal session required. This is the **second** confirmed state/district static endpoint after the Indiana DLGF document above, so the two-endpoint systematization threshold stated immediately above is MET: an `ora-millage-lookup`-style verified-endpoint skill (analogous to `ora-flood-zoning-dd`) is now a warranted build rather than a hypothetical candidate. **BUILT 2026-08-03 — use `ora-millage-lookup`.** The skill is now the executable procedure for this item: same ladder, plus a per-jurisdiction endpoint registry (`references/endpoints.md`), the required four-part output block (rate · unit · taxable base · source+date), and the pitfalls that have actually produced wrong answers — HTTP 200 with zero features is not "no data"; parcel keys are often fixed-width composites; do not "correct" a government URL's typo; units differ by state (per-$100 vs. percent vs. mills); reconcile the rate against a real bill via `ANNUALTAX ÷ TAXRATE` every time. This item stays the doctrine anchor and the pre-FULL requirement; the skill is how you satisfy it.

## STAGE 2.5 item 6 (full text)

6. **[CONDO-CONDITIONAL] Condominium-structure sub-check** — fires only when parcels resolve to a condo plat (assessor "condo" class, unit/building numbering, named corporate/commerce center regime). Produce all three: (a) master deed/declaration & bylaws — permitted uses (often narrower than zoning), common-element control & cost allocation, reserve adequacy, use/leasing/assignment restrictions; (b) per-unit financeability — confirm units separately financeable (thinner lender appetite compresses leverage at the 65% LTV per-property refi-post-close ceiling and the disposition buyer pool); (c) association control share — ORA's post-close voting/value %, exposure to special assessments. Whole-regime acquisition = effective fee-simple control (Edge: control upside). Price the friction; never a hard kill (Ruling 5). ANY unknown caps the verdict at T2. Validation: 2196 REDACTED-119 (4-unit precast condo).

## STAGE 2.5 item 7 (full text)

7. **[SINGLE-TENANT-CONDITIONAL] Single-tenant credit + lease-structure sub-check (v4.0)** — fires whenever tenancy = single (functional single-tenant, Stage 0 Gate 1 product profile). Require, before advancing past SCREEN: (a) **tenant credit read** — cite `tenant-intelligence`; note PE-sponsor ownership or consolidation/roll-up risk where the tenant sits inside a platform assembling multiple portfolio companies under one holding structure (sponsor credit and portfolio-company credit are not the same thing — state which one the lease actually relies on); (b) **true-net verification** — confirm the lease is genuinely absolute-NNN vs. modified/NN (landlord roof/structure/capital obligations materially change NOI — do not take "NNN" at face value from an OM without the lease); (c) **single-date rollover risk** — WALT concentrated at one expiration; model the deal assuming non-renewal at that date, not just probability-weighted (per the standing renewal-economics convention); (d) **landlord-adverse clauses** — purchase option/ROFO (a landlord's nightmare — flag hard, it caps the hold), early-termination, contraction, co-tenancy, exclusive-use. ANY unknown caps the verdict at T2 (same ceiling semantics as item 6 and the rest of Stage 2.5). Never a hard kill (Ruling 5) — price the risk (credit-adjusted cap add, rollover reserve, discount for a purchase-option overhang) and report it. Validation: 2900 Northridge Dr NW (Invio Automation, single-date 2031 expiry + 2036 option; PE-sponsor-platform tenant).

## STAGE 2.6 — PRE-LOI DD RESOLUTION CHECKLIST (v3.5; fires automatically once a deal clears SCREEN at T1 PURSUE)

Reusable resolution sequence — run these four in strict order before drafting the LOI. Do not skip ahead; each step's output can invalidate the walk price computed at SCREEN. Distinct from STAGE 2.5 (DD-Critical Screen Items, which caps the SCREEN verdict itself): this is the promotion sequence from screen-time estimates to LOI-ready verified facts, and an unresolved step blocks LOI handoff to `loi-generation`. **This checklist remains strictly sequential (v3.8) — do not parallelize; see the FULL-mode execution note under MODES.**

1. **Flood determination** — resolve any Stage 0 Gate 5 / DD-Critical item 1 flood flag to a sourced NFHL/GIS determination (`ora-flood-zoning-dd`). Land credit stays $0 until this clears (Ruling 4).
2. **Zoning / permitted-use verification** — obtain the formal municipal zoning letter confirming the intended use is by-right or already-permitted (DD-Critical item 2 promoted from GIS-lookup to letter-in-hand).
3. **SF/acreage reconciliation** — reconcile broker-stated GBA/acreage against county-auditor parcel data and, where available, a survey; any material variance (>2%) flows back into the Basis floor and RCT discount calc (Stage 1) before the walk price is finalized.
4. **Rent comp pull** — refresh the rent comp grid (**COMP GRID DISCIPLINE**, `references/comp-grid-discipline.md`) against current market at LOI-drafting time, not the SCREEN-time comps; confirms the Tenancy/Yield inputs haven't drifted since screen.

Log each step's resolution (source, date, result) to the Notion Deal Sourcing Log row alongside the original screen.
