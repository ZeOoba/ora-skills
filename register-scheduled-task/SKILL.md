# Register Scheduled Task (ORA) (v2.25)

**RULE 1 — MCP ONLY.** Register and update tasks EXCLUSIVELY via the `create_scheduled_task` / `update_scheduled_task` MCP tools, in a SUPERVISED session, on the surface where the task should run. If the MCP tool is unavailable in the current session (e.g., unsupervised/scheduled context), STOP and tell Gabriel to run the registration from a supervised session — do not improvise a filesystem path.

**RULE 2 — JSON-SPLICE PROHIBITED.** Direct edits to `scheduled-tasks.json` (the v1.0 "Desktop Commander splice" procedure) are BANNED: splice-registered tasks sit in the JSON but are never picked up by the scheduler — registered-but-unscheduled. The registry file is the scheduler's private state, not an API. Proof (2026-06-09 fleet rebuild; `ora-cowork-heartbeat` dark 05-31→06-10): `references/incident-history.md` § Rule 2 proof.

**RULE 3 — PRE-FLIGHT SURFACE ASSERTION (first action of the pass, before anything else).** Before any registration, update, pause, bulk-recovery, RETIRE step, or archive move — and before reading task folders to plan one — assert the surface: search THIS session's own tool registry for `list_scheduled_tasks`.

- **Present** → this session is native on-device and can write to its local fleet. Name which fleet that is from `list_scheduled_tasks`' `path` field (PATH-DISAMBIGUATOR below) before the first write, since `create_/update_/delete_scheduled_task` all resolve session-local with no fleet parameter.
- **Absent** → this is a cloud-sandbox Cowork session (device-bridge only, no native app process). STOP per Rule 1, name the four missing tools, and route the work to a native on-device session per Rule 4. Do not improvise a filesystem path (Rule 2).
- **Absence is the surface, not a transient error.** Prove it by tool-registry search — never by calling a tool and reading the failure. A "test call" against `delete_scheduled_task` is still a delete (see the RETIRE id-collision bullet).
- **Assert BEFORE the first step of an ordered pass, never between its steps.** Archive-first-delete-second is ONE pass: a session that can do step 1 but not step 2 must do neither. Half-executing it — folder archived, registry entry still live and pointing at a moved path — is worse than not starting, and is exactly what this assertion exists to prevent.
- **State the verdict in the first turn** ("surface: native / cloud-sandbox; `list_scheduled_tasks` present / absent"). The check costs about ten seconds; discovering the gap mid-task is how both v2.10-class incidents ran.

**RULE 4 — DISPATCH-TIME SURFACE ROUTING (the brief picks the surface, not the worker).** Any brief handing a LAMS/Cowork registry WRITE — registration, update, pause, id-collision cleanup, retire — to another session MUST name the surface at dispatch time: **"a native on-device Cowork session"** (the desktop app itself, or Claude Code's "Run this task → On your computer"), never a bare "Cowork session" / "Cowork-side session" — naming only the fleet lands wherever a Cowork session happens to exist, and the cloud sandbox wins that coin flip. The dispatched brief must also (a) carry Rule 3's assertion as its own first step, and (b) state the expected before/after so the receiving session verifies rather than re-derives. **READS are exempt** — `fleet-status.py` reads BOTH registries off disk from any surface, so never dispatch a handoff merely to look something up (`fleet-advisory-remediation` step 5/6). Incident (`ora-passed-deal-tracker`, dispatched to a cloud sandbox twice, 2026-08-17 and 2026-08-22): `references/incident-history.md` § Rule 4 incident.

## Procedure (new task)

0. **Surface assertion (Rule 3)** — run it before step 1, and state the verdict. Every procedure below (new task, update, pause, retire, bounded pause) starts here.
1. **Naming:** task id = kebab-case, `ora-` prefix for firm automations. Check `list_scheduled_tasks` first — if the id exists, this is an UPDATE (`update_scheduled_task`), not a new registration. Never duplicate ids across either fleet.
2. **Surface selection:** decide which fleet the task belongs to (Cowork artifact/skill dependencies → LAMS; filesystem/git/probe work → CC) and register from THAT surface.
3. **SKILL.md content** (passed as the task prompt or stored in the fleet's SKILL.md store) must state:
   - guard conditions (e.g., "first business day only — exit silently otherwise" when cron over-fires);
   - steps with explicit data sources (Notion collection IDs, folder paths, memory names);
   - output destinations (Notion Ops Hub `32b6ecd8` block, file outputs with ISO-date prefix);
   - **email convention:** Outlook COM via `C:\Users\Owner\.claude\scheduled-tasks\_shared\send-via-outlook.ps1` — the SOLE send path (Composio retired 2026-06-11, NO fallback; Rube EOL 2026-05-15; Gmail disabled). TO `ggoldberg@oxfordra.net` ONLY — the cc to `egoldberg@oxfordra.net` is sanctioned for the ora-am-brief Daily Brief ALONE. On non-zero exit: retry once, flag loudly in the Notion completion row, do NOT halt;
   - "never fabricate" + structured QUESTIONS FOR GABRIEL escalation for data gaps;
   - pointers to sibling skills/tasks instead of duplicating their logic.
3b. **MONEY-MOVING TASKS — `offhost-backup:` frontmatter is MANDATORY, and a laptop-only registration is REFUSED (v2.19).** A task is money-moving when any step of its run can post charges or fees to a tenant/counterparty ledger, initiate a debit, credit, or transfer, or send payment instructions to a third-party system (Stripe, ACH, a lender/borrower portal, QuickBooks JE posting). Root incident (`ora-pm-monthly-billing` missed its only monthly fire inside the 2026-08-29→09-01 host outage; Automation Audit Rev 21, R21-2 / R21-4): `references/incident-history.md` § Money-moving tasks. Rule:
   - The task's SKILL.md frontmatter MUST carry an `offhost-backup:` line naming a trigger that does NOT run on this machine — repo + workflow path + cron + the date it went live (format example: `references/incident-history.md` § Money-moving tasks). **"Live" is proven, never inferred from a merge (v2.24):** a backup may be declared `live since <date>` only when ALL of — (1) the workflow file is on the repo's default branch and `active` (`gh workflow list --repo <repo> --all --json path,state`); (2) every secret the workflow reads is present BY NAME (`gh secret list --repo <repo>` — names only, never read a value; grep the workflow for `secrets.` to get the list); (3) at least one real run concluded `success` (`gh run list --repo <repo> --workflow=<file> --limit 5`) — cite that run's URL in the same line. A workflow that cannot have run yet (e.g. a monthly cron before its first 1st) proves (3) with one input-less `workflow_dispatch` run against an idempotent endpoint, or stays `pending — awaiting first run`. Merged but failing (1)–(3) is `pending`, or `dormant — <reason>` if it was previously declared live. The backup must be idempotent against the primary (a re-fire cannot double-post); if the endpoint's idempotency isn't obvious, state the mechanism in the task body. Root incident (`monthly-billing-backup.yml` declared live with no `ORA_PM_CRON_SECRET`, OI-229): `references/incident-history.md` § Money-moving tasks.
   - `offhost-backup: pending — <PR/issue>` or `offhost-backup: none — GAP …` is allowed ONLY with Gabriel's explicit in-turn acceptance quoted in the registration turn. Absent that, STOP before `create_scheduled_task` and ask ONE question. Never register a money-moving task with no `offhost-backup:` line at all — a missing line is indistinguishable from "nobody checked".
   - Re-check the line after any `update_scheduled_task` call on that task: the call drops non-owned frontmatter keys (memory: `reference_update_scheduled_task_drops_frontmatter_keys`). Restore it by file edit, never by another update call.
   - Declarations are read from each task's frontmatter, never restated here (a dated copy in this file already went stale once). `automation-health-monitor` v1.10 Step 1.75 re-verifies (1)–(3) for the ora-pm backups every weekday. Neither money-moving task's gap may be cleared by narrowing this definition.
3c. **CLAIM-BEARING TASKS — unattended runs MUST claim under the `sched-` namespace (2026-09-07 ruling, OI-116).** A task's SKILL.md instructions claim a slug via `hooks/lib/claim_work.py claim` whenever a run can perform structural writes to a shared claim-relevant path (`hooks/**`, `open-items-tracker.md`, `oxford-command-center` data files, a `~/.claude` repo-maintenance sweep, an `ora-skills` commit — slug table in the reference). Before this skill registers or updates such a task, its instructions must claim under **`sched-<slug>`**, not the bare slug — e.g. `sched-ora-skills-housekeeping`. `sched-` gets a 30-minute TTL (never widened) and a refusal message that states force-takeover is ROUTINE, which is what an unattended, unmessageable, self-renewing holder needs. **Hyphen, not colon** — the slug is the claim filename and `:` is illegal on Windows; `_safe_filename()` would silently mangle `sched:foo`. Apply at registration for every new claim-bearing task, and retrofit into any existing task's instructions the next time this skill touches its SKILL.md. Why mandatory (`memory/tech.md` §3e): `references/incident-history.md` § Claim-bearing tasks.
4. **Register:** call `create_scheduled_task` with cron (ET, 5-field) and the prompt. Cron notes: quarterly-on-first-business-day → `30 6 1-3 1,4,7,10 *` + in-skill business-day guard; avoid `*/n` day-of-month patterns (drift); avoid the 05:00–09:30 pileup window and same-minute collisions with existing tasks.
4b. **MODEL TAG — required at registration, dated, for every in-scope task (2026-07-24).** End the `description` with `[MODEL: <id-or-UNVERIFIABLE> | set|checked YYYY-MM-DD]`. **The date half is mandatory** — a bare `[MODEL: <id>]` is not a valid tag (freshness can't be aged against the model-release lineup anchor), and it lands the task in the stale bucket on the very next guard run. Which tasks are in scope, which verb to use, and which are exempt (CC/MCP one-time; anything disabled) is defined ONCE in `memory/reference_scheduled_task_model_standard.md` § "Tag scope & required fields" — read it, do not restate it here. Tag at registration, never retroactively (every retroactive sweep so far was cleaning up tasks that shipped untagged from this step).
4c. **Post-registration fire-time sanity check.** Registering after a cadence's slot has already passed for the current cycle still returns a syntactically valid `nextRunAt` — just one a full cycle later than "today," and nothing upstream catches that. Before calling step 5 complete, compare the returned `nextRunAt` against the stated cadence's expected interval (daily → ~1 day, weekly → ~7 days, monthly → ~30 days): if it is more than ~1.5× that interval away from the registration timestamp, flag it in the same turn — state plainly that the task registered after this cycle's slot and won't fire until the following one, and ask Gabriel whether that's fine or whether the first run should also go out as a one-time task to close the gap. A syntactically valid `nextRunAt` is not proof the timing is what anyone intended. Root incident (`ora-psa-drift-watch`, 2026-08-12): `references/incident-history.md` § Fire-time sanity check.
4d. **Progress markers for multi-step one-time tasks (OI-202).** A model-driven one-time task that stalls mid-run is indistinguishable from a healthy "still running" task to `lastRunAt` — the scheduler stamps that the instant it fires, not when/if it finishes. If the one-time task you are registering has **3 or more sequential steps with side effects** (not a single-shot action), its SKILL.md instructions must call the marker script after each step:
    `C:/Users/Owner/AppData/Local/Programs/Python/Python313/python.exe C:\Users\Owner\.claude\maintenance\task-progress-marker.py write --fleet <cc|lams> --task-id <this-task-id> --step N --of TOTAL --note "<short state, e.g. current item>"`
    **`--fleet` is REQUIRED** (v2.23). The 2026-09-11 resume's own marker call omitted it and failed with `the following arguments are required: --fleet`. Use the full interpreter path, because bare `python` is not on PATH in scheduled sessions.
    Opt-in and additive — a task with no marker calls is invisible to the check, never a false alarm. `ORA Fleet Pause-Resume Guard` (native, every 6h, off-fleet) reads every marker via `task-progress-marker.py find_stalled()` and alarms on a stale incomplete step (grace 20min); it never auto-resumes or restarts anything. Extend that guard — do not build a second monitor. Root incident: `references/incident-history.md` § Progress markers.
5. **Verify (mandatory — no "done" without evidence):** call `list_scheduled_tasks` and paste the returned entry (id, cron, enabled, next-fire), including the step 4c sanity check's verdict. A registry-file grep is NOT verification (Rule 2 lesson: file presence ≠ scheduled).

## Update / pause / retire — three DIFFERENT operations, do not conflate them

- **UPDATE:** `update_scheduled_task` (cron and/or prompt). Re-verify via `list_scheduled_tasks`.
- **PAUSE (temporary, reversible — the task and its content stay intact):** set `enabled: false` via `update_scheduled_task` on CC/MCP, or the Cowork UI's own enable/disable toggle on LAMS. This is the ONLY correct action when someone says "disable," "pause," "turn off," or "stop this from running for now." **NEVER use the Cowork Scheduled-sidebar's delete/trash icon for a pause** — that control performs RETIRE's destructive step regardless of intent, and there is no undo. If you are not certain the sidebar has a distinct disable-only control separate from delete, ask before touching it, or do the pause from Claude Code via `update_scheduled_task` instead. Incident precedent: `references/incident-history.md` § PAUSE — sidebar-delete incident. **RE-ENABLE carries a model-tag precondition (2026-07-24):** a paused task is exempt from the `[MODEL:]` tag while paused. The moment you flip `enabled: true`, it is back in scope — re-tag it with a CURRENT date in the same pass, before or with the enable call, never "later."
- **RETIRE (permanent — only when the task is genuinely done):** disable first via `update_scheduled_task`; move the SKILL.md directory to `_archive_YYYY-MM-DD_retired\` in its store; note in Ops Hub. Never delete history silently. Update the fleet disposition ledger (`00_Governance/outputs/`). Add the task id to the consolidated "do NOT re-register" list in `session-context.md` — a retirement recorded only in the task's own frontmatter is not enough (incident: `references/incident-history.md` § RETIRE — do-NOT-re-register list incident).
- **RETIRE — ARCHIVE FIRST, DELETE SECOND (hard ordering):** the Cowork Scheduled-sidebar delete is FOLDER-DESTRUCTIVE — it hard-deletes the task's SKILL.md folder along with the registry entry, bypassing the Windows Recycle Bin (OneDrive online recycle bin ~93d is the only recovery). Therefore: (1) MOVE the task folder to the dated `_archive_*` folder, (2) VERIFY the move landed, (3) only THEN delete the registry entry in the UI. Log planned removals to `memory/event_log.md` with the literal token `RATIFIED` + the task id — `registry-membership-probe.py` auto-ratifies such drops (≤14d window) instead of raising a false [ACTION]. Incidents behind this ordering: `references/incident-history.md` § RETIRE — archive-first-delete-second incidents.
- **RETIRE — a RATIFIED-but-UNEXECUTED retirement must be filed in the retire-pending register, in the SAME pass that ratifies it.** A decided-but-unexecuted retirement leaves a registration alive with `enabled:false` — which is a pause that any fleet-wide resume silently undoes, and the ratification→execution gap is often days (a surface handoff, per Rule 4). Add the entry to `C:\Users\Owner\.claude\maintenance\_state\retire-pending.json` (`{"fleet": "cc"|"lams", "id": "<task-id>", "ratified": "YYYY-MM-DD", "reason": "...", "executeFrom": "native on-device Cowork session"|"Claude Code"}`), and remove it in the pass that actually executes the retirement. `ORA Fleet Pause-Resume Guard` (native, off-fleet, every 6h) ALARMS if a listed id is found `enabled: true` on its named fleet. This register is a plain state file consulted by a guard, NOT a registry: writing to it is not a Rule 2 violation and does not retire anything by itself. Full rationale: `references/incident-history.md` § Retire-pending register.
- **RETIRE — re-home solely-run producer scripts BEFORE deleting the registry entry:** before retiring any task, grep `maintenance/*.py`, `hooks/*.py`, and every other live task's SKILL.md for scripts this task is the SOLE invoker of. If any are found, re-home them into a surviving task's steps (or explicitly retire the script too, with the same archive-first ordering) BEFORE completing this retirement — never after. A task's own SKILL.md naming what it "replaces" or "folds in" is not proof nothing downstream was missed. Root incident: `references/incident-history.md` § RETIRE — orphaned producer-script incident.
- **RETIRE — id-collision fleet-resolution: never verify by deleting a live task (2026-08-17).** `delete_scheduled_task` carries no fleet parameter — on a same-id collision it resolves to whichever fleet is LOCAL to the calling session (`memory/reference_delete_scheduled_task_resolves_colliding_id_to_local_fleet.md`). The only safe ways to confirm which fleet a session's calls will hit are (a) `list_scheduled_tasks`' own `path` field (PATH-DISAMBIGUATOR above), or (b) the client identity the host surface itself reports (e.g., Desktop Commander's `currentClient`). **Never** probe resolution with an actual delete, and never target `ora-cowork-heartbeat` or any other dead-man/heartbeat-chain id as a test subject under any circumstance — a "test delete" against a live task is still a delete, and deleting the wrong copy of an id-collision pair is exactly the hazard archive-first-delete-second exists to prevent. Root incident: `references/incident-history.md` § Id-collision fleet-resolution.

## Editing a task's SKILL.md CONTENT — a commit is not a live change

UPDATE above covers the registry (cron, enabled, prompt). This section covers changing the **instructions a task runs by**. Every ORA scheduled task's SKILL.md exists in two places — the fleet store the scheduler reads at fire time (`~\.claude\scheduled-tasks\<id>\SKILL.md` for CC/MCP; `OneDrive…\Documents\Claude\Scheduled\<id>\` for LAMS), and the git-tracked copy under `~/.claude`. The registry stores only a `filePath`, so **committing an edit changes nothing about what runs** — the same trap as "a merged PR is not a live deploy" in `CLAUDE.md`'s Release rule. Never report a content fix as done on the strength of a commit.

Procedure, in this order:

1. **Edit in a worktree, never the shared checkout.** `~/.claude` routinely carries 100+ dirty files from concurrent sessions. Gate with `preflight-shared-checkout.py` before committing, passing the sha you actually built on — a stale `--since` returns `HEAD_MOVED`, which reads identically to real contention; check `dirty_overlap_foreign` and `competing_claims` in its `RESULT_JSON` before believing a contention verdict.
2. **Make the edit with the Edit/Write tool, not a Bash heredoc/sed/script.** Provenance is recorded only by the Edit/Write hook, so a Bash-written file reads to the gate as unowned and returns `CONTESTED` against your own work. Re-applying the identical edit through Edit is the fix; `--force` never is.
3. **Fix every site of the rule you are changing.** A skip rule, routing constant or threshold is typically stated in both a standing-prohibition section and the step that evaluates it; changing one leaves the spec self-contradictory. Grep the file for the constant before editing, and quote every site back when reporting.
4. **Back up the live file, then propagate.** Copy the live SKILL.md to `SKILL.md.bak-YYYY-MM-DD-<reason>` beside it (`.bak` is gitignored under `scheduled-tasks/`) — Hard Invariant 6, never overwrite a config without reading it first. Then copy the committed version over the live path.
5. **Check line endings BEFORE the copy.** These files are CRLF; copying an LF-normalised worktree file over a CRLF live file rewrites every line and destroys the ability to diff the real change. Compare `grep -c $'\r'` and line counts on both, and confirm `diff --strip-trailing-cr` shows only the lines you meant to touch.
6. **Hash-verify.** `sha256sum` the live file and the committed file and show they match. A copy that silently failed looks exactly like a copy that worked.
7. **Test the changed rule against real data before declaring done.** If the edit changed a matching rule, run it over the actual population it will face plus adversarial cases — for a name-based skip rule, every real counterparty name in that pipeline (must NOT match) and every sentinel variant (must match). Doctrine asserted is not doctrine verified.

**Do not silently widen a matching rule to make it simpler.** A skip/exclusion pattern must stay anchored and narrow enough that it cannot swallow real counterparty work: a false negative on a genuine tenant, deal or payment is far worse than the false positive the rule exists to stop. Record that reasoning inline next to the rule. The test-artifact convention is the `ZZ` sentinel — `^ZZ[\s._-]*TEST`, case-insensitive, leading whitespace stripped, anchored prefix only (never a bare `TEST`, which matches real tenants like "TESTA Construction"). Use that same sentinel for any new name-based test exclusion.

**The same live-vs-source split exists for SKILLS, and is not this skill's to fix.** `~/.claude/skills/synced/<uuid>/<skill>/SKILL.md` is what Claude loads; `C:\Users\Owner\ora-skills\<skill>\SKILL.md` is the source of record. They drift. Before quoting a skill's own doctrine at someone, check which copy you read. Measured drift (2026-09-19): `references/incident-history.md` § Skills live-vs-source drift.

## Bounded pause — the resume is part of the pause, not a follow-up

- **Rule:** a pause with a stated or implied end ("until Friday," "for two weeks," "while I'm out") is NOT complete until its resume task is registered — or confirmed already registered — in the SAME supervised session, on the SAME surface, in the SAME pass. Bulk is the aggravating factor, not the trigger: one task paused "until Friday" fails identically. A genuinely open-ended pause has no resume to register — say that explicitly rather than skipping the step silently.
- **"Pause all routines" is FLEET-AMBIGUOUS — resolve it before acting.** The instruction names no fleet, so enumerate BOTH registries, state which are in scope, and register one resume per fleet in scope. A resume task cannot reach the other fleet's registry (`update_scheduled_task` resolves session-local — see PATH-DISAMBIGUATOR). Reporting "N tasks paused" after touching one fleet reads as complete and is the exact shape of the root incident below.
- **A resume must EXCLUDE every retire-pending id.** Read `maintenance/_state/retire-pending.json` before building any bulk resume's id list, and carve those ids out explicitly — they are `enabled:false` because they are on their way OUT, not because they are paused; re-enabling one reverses a ratified retirement and, on a same-id cross-fleet pair, resurrects the duplicate. Say in the same turn which ids you carved out and why. (The guard alarms on this within 6h, but an alarm is the backstop, not the control.)
- **Never blanket-pause the detectors.** `ora-cowork-heartbeat` (dead-man chain → Notion `35c6ecd8…` → GitHub watchdog) and `automation-health-monitor` are what would otherwise surface a failed resume — and BOTH live on LAMS, so a LAMS-wide pause silences the detector for its own failure. Either carve them out of the pause, or state plainly in the same turn that the dead-man chain and health monitor are down for the window and will not report the gap.
- **RESUME-TIME COLLISION CHECK — pick the resume time off the fleet's own cron table, not off the clock (NEW v2.15, 2026-08-24).** A resume time is not a scheduling detail; it decides which of the paused tasks get their last slot back and which lose it permanently. Before committing a `fireAt`, list every paused task whose cadence slot falls in the **last 2 hours before** the proposed resume, and for each one make an explicit call:
  - **Make-up-able** — most sweeps, monitors and nudges re-scan current state on their next fire, so a skipped slot costs latency, not content. Note it and move on.
  - **Period-bounded — the output is GONE if the slot is missed**, because the deliverable only ever covers the period it fired in: week-closeouts, month-end ledgers, inbox windows, daily briefs, EOD ledgers. For these, move the resume **earlier than the slot**, not later. Minutes are enough; the cost of resuming 45 minutes early is nil, and the cost of resuming 30 minutes late is one permanently missing deliverable.
  State the check and its outcome in the same turn as the pause, even when nothing collides — "no period-bounded slot falls in the 2h before the proposed resume" is a real assertion and takes one line.
  **Root incident (2026-08-17 → 2026-08-21 pause — resume set 30 minutes AFTER `ora-friday-closeout`'s slot; week-of-08-17 closeout never produced, undetected for three days):** `references/incident-history.md` § Resume-time collision incident.
- **Verify before reporting done:** `list_scheduled_tasks` shows the resume task for EACH paused fleet — id, `fireAt` (a one-time resume carries `fireAt`, not `cronExpression`/`nextRunAt`), and an id list matching exactly what was paused — pasted in the SAME response that reports the pause complete. If the current surface cannot reach the MCP tools for either half, STOP per Rule 1 and name which half is missing; never report "N tasks paused" without either a registered resume or an explicit flag that none exists.
- **⛔ AN UNATTENDED RESUME WILL NOT COMPLETE ON ITS OWN (NEW v2.23, 2026-09-12, root cause of OI-273).** The Claude Desktop scheduled-task runner does **not** auto-approve `mcp__scheduled-tasks__update_scheduled_task` in an unattended run.
  - **What happens:** it logs `Not auto-approving "mcp__scheduled-tasks__update_scheduled_task" ... no suggestions on request` and blocks on a permission prompt with no "always allow" option, ignoring the `settings.json` allow rule; Bash in the same run IS auto-approved. **Permission mode does NOT help** — the 09-11 run ran `bypassPermissions` and still blocked on every call; nothing in our configuration can pre-approve it. 09-11 record: `references/incident-history.md` § Unattended resume.

  So **the only working path is an ATTENDED resume**, and it must be arranged at pause time and stated in the same turn:
  - Tell Gabriel the resume fires at `fireAt` and will stop for approval. Someone must open that run in the Desktop app and approve each `update_scheduled_task` call.
  - Keep the resume batched: all ids issued in as few turns as possible, so approvals are quick.
  - Alternatively, skip the scheduled resume and have Gabriel ask a live session to "unpause all routines" at the chosen time.
  - A fleet-wide pause can therefore never resume while Gabriel is away, so plan pause length accordingly.

  **Detection backstop (slow, not a timely alarm):** `pause-resume-guard.py` `find_incomplete_resumes()` (OI-273) alarms when a fired resume's listed ids are still disabled 30 min to 72h after firing — it reads live `enabled`, not run status or markers. The guard runs on a fixed 6h cycle and its slots can be skipped silently, so **expect detection hours late. After any resume, verify with `list_scheduled_tasks` rather than waiting for this alarm.** Detail: `references/incident-history.md` § Unattended resume.
- **RECORD THE PAUSE WINDOW — same pass, right after the resume is verified (v2.22).** Run `python ~/.claude/maintenance/_shared/pause_windows.py capture` and paste its `held` counts for EACH paused fleet in the same response; they should equal the paused-id counts. This writes `maintenance/_state/fleet-pause-windows.json`, the durable record the health checks subtract from gaps (`fleet_pause.py` only knows a pause *while it is live*). `capture` records **observed registry state, not parsed text** — a task is *held* only if it is actually **disabled** AND an enabled, not-yet-fired resume naming **≥3 currently-disabled tasks** names it; for a 1–2 task pause, hand-record with `pause_windows.py record --note "<evidence>"`. A hold longer than 21 days is voided. **If the capture does not list your window, the resume SKILL.md is malformed — fix that, don't hand-record around it.** The native guard re-runs `capture` every 6h as the backstop. Held semantics in full, root incident, and what this replaces: `references/incident-history.md` § Pause window record.
- **A resume does NOT re-stamp `[MODEL:]` dates.** Re-enabling returns a task to tag scope, which makes it DUE for a currency check — it is not itself an observation, and bumping `checked`/`set` dates fabricates a verification (`memory/feedback_verified_null_vs_inferred_null.md`). This QUALIFIES the PAUSE bullet's "re-tag in the same pass": that binds a hand re-enable where the model IS observed, not an automated bulk resume.
- **ONE-TIME EFFICACY-CHECK CHECK — enumerate overlapping one-time tasks before committing the pause (v2.17).** A bounded pause also poisons any one-time (`fireAt`) task whose MEASUREMENT WINDOW overlaps the pause, even though that task is never itself paused — an efficacy/retime check that counts "days delivered" from the send log cannot distinguish a disabled task from a genuine miss. Before committing any bounded pause: list every one-time task on the affected fleet(s) whose `fireAt` falls between the pause start and the earliest plausible resume, and for each one that reads status/delivery history over a window the pause will fall inside, make an explicit call:
  - **Defer** — push its `fireAt` to after the resume, so it measures a live fleet. Preferred when the check has no independent value tied to its original date.
  - **Knowingly void** — if the date is fixed for a reason that outlives the pause (e.g. a hard reporting deadline), leave `fireAt` as-is but record in the SAME pass, in `event_log.md` or the pause's own resume-ledger entry, that its window will include a pause and its verdict must be read against `enabled` history, not the send log alone.
  A pause is not complete with only its own resume registered — an overlapping one-time check left neither deferred nor flagged is a live footgun for the next efficacy ruling. ## Concurrent-writer check (before any registration/recovery/bulk-retire session)

Registering, retiring, or bulk-recovering tasks touches shared state exactly like the `ora-skills` git repo and `event_log.md` — the same claim-first-write-second discipline applies.

**PRIMARY CHECK (2026-07-12) — `session_info list_sessions`:** before the first write of any registration/retime/retire pass, call `list_sessions` and scan for another session that is `running` or recently active with an overlapping title (task ids, "scheduler," "LAMS," or the same skill name) — that IS a live sibling, not a maybe. `registry-membership.log` does NOT catch this class of collision — it only logs task adds/drops, not cron edits or same-value re-pins. If a live sibling is found: stop, compare notes in-conversation if possible, and agree who applies the write before either session calls `update_scheduled_task` or `create_scheduled_task` again.

**SECONDARY SIGNAL — `registry-membership.log`:** still worth checking for id-level adds/drops, but treat a clean log as inconclusive, not as proof no one else is active — it has a blind spot for cron-only edits.

Two incident precedents motivate the checks above (duplicate-id registration, and a same-day event_log.md write collision from an idempotent concurrent edit) — full narrative: `references/incident-history.md` § Concurrent-writer incidents.

If you discover mid-task that another session is concurrently active, stop, compare notes, and agree who owns which fleet before either of you registers or deletes anything further.
