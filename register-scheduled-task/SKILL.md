# Register Scheduled Task (ORA) — v2.13

**RULE 1 — MCP ONLY.** Register and update tasks EXCLUSIVELY via the `create_scheduled_task` / `update_scheduled_task` MCP tools, in a SUPERVISED session, on the surface where the task should run. If the MCP tool is unavailable in the current session (e.g., unsupervised/scheduled context), STOP and tell Gabriel to run the registration from a supervised session — do not improvise a filesystem path.

**RULE 2 — JSON-SPLICE PROHIBITED.** Direct edits to `scheduled-tasks.json` (the v1.0 "Desktop Commander splice" procedure) are BANNED. Proof: the 2026-06-09 fleet rebuild left splice-registered tasks present in the JSON but never picked up by the scheduler — registered-but-unscheduled. `ora-cowork-heartbeat` went dark 2026-05-31→06-10 in exactly this failure mode. The registry file is the scheduler's private state, not an API.

## Dual-fleet registry model (both live; neither is "the" store)

| Fleet | Registry | SKILL.md store | Register from |
|---|---|---|---|
| CC/MCP | `claude-code-sessions` registry | `~/.claude/scheduled-tasks/{task-id}/` | Claude Code (supervised) |
| LAMS/Cowork | `local-agent-mode-sessions` registry | `OneDrive — Oxford Capital Partners\Documents\Claude\Scheduled\{task-id}\` | Cowork (supervised) |

- Cowork-created tasks land in the LAMS registry BY DESIGN — do not migrate them to the CC store; monitors are store-agnostic.
- **Surface note — cloud-sandbox Cowork sessions never carry these MCP tools (2026-08-17):** `create_scheduled_task`/`update_scheduled_task`/`delete_scheduled_task`/`list_scheduled_tasks` exist only in a session running natively on-device (Claude Code, or Cowork launched via "Run this task → On your computer") — a cloud-sandbox Cowork session (device-bridge only, no native app process) never carries them, regardless of how a task brief names them. Absence of the tool is the surface, not a transient error: per Rule 1, STOP rather than improvise, and route LAMS registry writes (registrations, id-collision cleanups, retires) to a native on-device session from the start instead of discovering the gap mid-task. Incident: 2026-08-17, an `ora-passed-deal-tracker` id-collision deregistration dispatched to a cloud session that had neither tool.
- Both fleets fire only while the Desktop app is open. Dead-man chain: ora-cowork-heartbeat → Notion page `35c6ecd8…` → GitHub watchdog.
- **Path note:** sole physical store is `C:\Users\Owner\AppData\Roaming\Claude\...` — the MSIX LocalCache path holds no Claude data on this machine. Probe (`Test-Path`) before sourcing either path; if both exist AND diverge, stop and escalate. Never write to either directly (Rule 2). Verify the LAMS OneDrive path with a directory check before trusting either the '(1)' or no-suffix form. Full verification history: `references/incident-history.md` § Path note.
- **CROSS-FLEET SHARED-FILE RISK:** a CC/MCP task's SKILL.md is often a thin redirect stub pointing at the SAME OneDrive path a same-id LAMS task uses for its own full spec — deleting or overwriting one can silently destroy the other. Before deleting (not disabling) any task folder, check whether a same-id task exists on the other fleet and whether its spec might share that path. Full mechanism + incident: `references/incident-history.md` § Cross-fleet shared-file risk.
- **PATH-DISAMBIGUATOR:** when a same-id task may exist on both fleets, the `path` field from `list_scheduled_tasks` is the SOLE reliable disambiguator (CC/MCP → `~\.claude\scheduled-tasks\{id}\`; LAMS/Cowork → `...\Documents\Claude\Scheduled\{id}\`). Act only on the entry whose `path` matches your target fleet. **A SKILL.md folder found OUTSIDE both store roots is an orphaned/misfiled copy, NOT evidence of a live registration** — the only proof is the task appearing in `list_scheduled_tasks`. If a task brief, memory note, or runbook cites a store path that is neither root, treat it as stale and verify against `list_scheduled_tasks` + the two roots before acting. Full incident precedent: `references/incident-history.md` § Path disambiguator.

## Procedure (new task)

1. **Naming:** task id = kebab-case, `ora-` prefix for firm automations. Check `list_scheduled_tasks` first — if the id exists, this is an UPDATE (`update_scheduled_task`), not a new registration. Never duplicate ids across either fleet.
2. **Surface selection:** decide which fleet the task belongs to (Cowork artifact/skill dependencies → LAMS; filesystem/git/probe work → CC) and register from THAT surface.
3. **SKILL.md content** (passed as the task prompt or stored in the fleet's SKILL.md store) must state:
   - guard conditions (e.g., "first business day only — exit silently otherwise" when cron over-fires);
   - steps with explicit data sources (Notion collection IDs, folder paths, memory names);
   - output destinations (Notion Ops Hub `32b6ecd8` block, file outputs with ISO-date prefix);
   - **email convention:** Outlook COM via `C:\Users\Owner\.claude\scheduled-tasks\_shared\send-via-outlook.ps1` — the SOLE send path (Composio retired 2026-06-11, NO fallback; Rube EOL 2026-05-15; Gmail disabled). TO `ggoldberg@oxfordra.net` ONLY — the cc to `egoldberg@oxfordra.net` is sanctioned for the ora-am-brief Daily Brief ALONE. On non-zero exit: retry once, flag loudly in the Notion completion row, do NOT halt;
   - "never fabricate" + structured QUESTIONS FOR GABRIEL escalation for data gaps;
   - pointers to sibling skills/tasks instead of duplicating their logic.
4. **Register:** call `create_scheduled_task` with cron (ET, 5-field) and the prompt. Cron notes: quarterly-on-first-business-day → `30 6 1-3 1,4,7,10 *` + in-skill business-day guard; avoid `*/n` day-of-month patterns (drift); avoid the 05:00–09:30 pileup window and same-minute collisions with existing tasks.
4b. **MODEL TAG — required at registration, dated, for every in-scope task (2026-07-24).** End the `description` with `[MODEL: <id-or-UNVERIFIABLE> | set|checked YYYY-MM-DD]`. **The date half is mandatory** — a bare `[MODEL: <id>]` is not a valid tag (freshness can't be aged against the model-release lineup anchor), and it lands the task in the stale bucket on the very next guard run rather than passing clean. Which tasks are in scope, which verb to use, and which are exempt (CC/MCP one-time; anything disabled) is defined ONCE in `memory/reference_scheduled_task_model_standard.md` § "Tag scope & required fields" — read it, do not restate it here. Tag at registration, never retroactively: every retroactive sweep so far (07-13, 07-15, 07-22, 07-24) was cleaning up tasks that shipped untagged from this step.
4c. **Post-registration fire-time sanity check (2026-08-15).** Registering after a cadence's slot has already passed for the current cycle still returns a syntactically valid `nextRunAt` — just one a full cycle later than "today," and nothing upstream catches that: the cron is well-formed, and step 5's "state the next 2 fire dates" only asks you to report them, not judge them. Root incident: `ora-psa-drift-watch`, registered 2026-08-12 (a Wednesday, after a 42+-minute permission-request delay pushed registration past its own 1:30 PM Wednesday slot) — it silently sat until the following Wednesday with nothing flagging the wait; the cron-collision fix that eventually touched it was found by separate investigation, not by this check. Before calling step 5 complete, compare the returned `nextRunAt` against the stated cadence's expected interval (daily → ~1 day, weekly → ~7 days, monthly → ~30 days): if it's more than ~1.5× that interval away from the registration timestamp, flag it in the same turn — state plainly that the task registered after this cycle's slot and won't fire until the following one, and ask Gabriel whether that's fine or whether the first run should also go out as a one-time task to close the gap. A syntactically valid `nextRunAt` is not proof the timing is what anyone intended.
4d. **Progress markers for multi-step one-time tasks (OI-202, 2026-08-21).** A model-driven one-time task (natural-language steps run by an agent session, not a deterministic script) that stalls mid-run is indistinguishable from a healthy "still running" task to `lastRunAt` — the scheduler stamps that the instant it fires, not when/if it finishes. Root incident: `ora-routine-pause-resume-08-21` fired, stamped `lastRunAt`, then silently stopped after re-enabling 2 of 35 tasks — no error, no summary email, nothing caught it until a manual `list_scheduled_tasks` diff. If the one-time task you are registering has **3 or more sequential steps with side effects** (not a single-shot action), its SKILL.md instructions must call the marker script after each step:
    `python C:\Users\Owner\.claude\maintenance\task-progress-marker.py write --task-id <this-task-id> --step N --of TOTAL --note "<short state, e.g. current item>"`
    This is opt-in and additive — a task with no marker calls is simply invisible to the check below (not flagged as stalled), so omitting it is a silent no-op, never a false alarm. `ORA Fleet Pause-Resume Guard` (native, every 6h, off-fleet — survives a full pause by construction) reads every marker via `task-progress-marker.py find_stalled()` and alarms on any one-time task whose marker shows an incomplete step that hasn't updated within its grace window (default 20min); it does NOT auto-resume or auto-restart anything. Do not build a second monitor for this — extend the existing guard script, matching the "pointers to sibling skills instead of duplicating logic" rule above.
5. **Verify (mandatory — no "done" without evidence):** call `list_scheduled_tasks` and paste the returned entry (id, cron, enabled, next-fire), including the step 4c sanity check's verdict. A registry-file grep is NOT verification (Rule 2 lesson: file presence ≠ scheduled).

## Update / pause / retire — three DIFFERENT operations, do not conflate them

- **UPDATE:** `update_scheduled_task` (cron and/or prompt). Re-verify via `list_scheduled_tasks`.
- **PAUSE (temporary, reversible — the task and its content stay intact):** set `enabled: false` via `update_scheduled_task` on CC/MCP, or the Cowork UI's own enable/disable toggle on LAMS. This is the ONLY correct action when someone says "disable," "pause," "turn off," or "stop this from running for now." **NEVER use the Cowork Scheduled-sidebar's delete/trash icon for a pause** — that control performs RETIRE's destructive step (see below) regardless of intent, and there is no undo. If you are not certain the sidebar has a distinct disable-only control separate from delete, ask before touching it, or do the pause from Claude Code via `update_scheduled_task` instead. Incident precedent: `references/incident-history.md` § PAUSE — sidebar-delete incident. **RE-ENABLE carries a model-tag precondition (2026-07-24):** a paused task is exempt from the `[MODEL:]` tag while paused (nothing is firing, so there is nothing to observe or set). The moment you flip `enabled: true`, it is back in scope — re-tag it with a CURRENT date in the same pass, before or with the enable call, never "later." An enable that leaves a stale or absent tag behind is exactly how a task re-enters the fleet invisible to the currency check.
- **RETIRE (permanent — only when the task is genuinely done):** disable first via `update_scheduled_task`; move the SKILL.md directory to `_archive_YYYY-MM-DD_retired\` in its store; note in Ops Hub. Never delete history silently. Update the fleet disposition ledger (`00_Governance/outputs/`). Add the task id to the consolidated "do NOT re-register" list in `session-context.md` — a retirement recorded only in the task's own frontmatter is not enough (incident: `references/incident-history.md` § RETIRE — do-NOT-re-register list incident).
- **RETIRE — ARCHIVE FIRST, DELETE SECOND (hard ordering):** the Cowork Scheduled-sidebar delete is FOLDER-DESTRUCTIVE — it hard-deletes the task's SKILL.md folder along with the registry entry, bypassing the Windows Recycle Bin (OneDrive online recycle bin ~93d is the only recovery). Therefore: (1) MOVE the task folder to the dated `_archive_*` folder, (2) VERIFY the move landed, (3) only THEN delete the registry entry in the UI. Log planned removals to `memory/event_log.md` with the literal token `RATIFIED` + the task id — `registry-membership-probe.py` auto-ratifies such drops (≤14d window) instead of raising a false [ACTION]. Incidents behind this ordering: `references/incident-history.md` § RETIRE — archive-first-delete-second incidents.
- **RETIRE — re-home solely-run producer scripts BEFORE deleting the registry entry:** before retiring any task, grep `maintenance/*.py`, `hooks/*.py`, and every other live task's SKILL.md for scripts this task is the SOLE invoker of. If any are found, re-home them into a surviving task's steps (or explicitly retire the script too, with the same archive-first ordering) BEFORE completing this retirement — never after. A task's own SKILL.md naming what it "replaces" or "folds in" is not proof nothing downstream was missed. Root incident: `references/incident-history.md` § RETIRE — orphaned producer-script incident.
- **RETIRE — id-collision fleet-resolution: never verify by deleting a live task (2026-08-17).** `delete_scheduled_task` carries no fleet parameter — on a same-id collision it resolves to whichever fleet is LOCAL to the calling session (`memory/reference_delete_scheduled_task_resolves_colliding_id_to_local_fleet.md`). The only safe ways to confirm which fleet a session's calls will hit are (a) `list_scheduled_tasks`' own `path` field (see PATH-DISAMBIGUATOR above), or (b) the client identity the host surface itself reports (e.g., Desktop Commander's `currentClient`). **Never** probe resolution with an actual delete, and never target `ora-cowork-heartbeat` or any other dead-man/heartbeat-chain id as a test subject under any circumstance — a "test delete" against a live task is still a delete, and deleting the wrong copy of a genuine id-collision pair is exactly the hazard the archive-first-delete-second ordering above exists to prevent. Root incident: a session correctly declined to test fleet-resolution against `ora-cowork-heartbeat` before retiring the `ora-passed-deal-tracker` LAMS duplicate, for lack of a documented safe method — this bullet is that method.

## Bounded pause — the resume is part of the pause, not a follow-up

- **Rule:** a pause with a stated or implied end ("until Friday," "for two weeks," "while I'm out") is NOT complete until its resume task is registered — or confirmed already registered — in the SAME supervised session, on the SAME surface, in the SAME pass. Bulk is the aggravating factor, not the trigger: one task paused "until Friday" fails identically. A genuinely open-ended pause has no resume to register — say that explicitly rather than skipping the step silently.
- **"Pause all routines" is FLEET-AMBIGUOUS — resolve it before acting.** The instruction names no fleet, so enumerate BOTH registries, state which are in scope, and register one resume per fleet in scope. A resume task cannot reach the other fleet's registry (`update_scheduled_task` resolves session-local — see PATH-DISAMBIGUATOR). Reporting "N tasks paused" after touching one fleet reads as complete and is the exact shape of the root incident below.
- **Never blanket-pause the detectors.** `ora-cowork-heartbeat` (dead-man chain → Notion `35c6ecd8…` → GitHub watchdog) and `automation-health-monitor` are what would otherwise surface a failed resume — and BOTH live on LAMS, so a LAMS-wide pause silences the detector for its own failure. Either carve them out of the pause, or state plainly in the same turn that the dead-man chain and health monitor are down for the window and will not report the gap.
- **Verify before reporting done:** `list_scheduled_tasks` shows the resume task for EACH paused fleet — id, `fireAt` (a one-time resume carries `fireAt`, not `cronExpression`/`nextRunAt`), and an id list matching exactly what was paused — pasted in the SAME response that reports the pause complete. If the current surface cannot reach the MCP tools for either half, STOP per Rule 1 and name which half is missing; never report "N tasks paused" without either a registered resume or an explicit flag that none exists.
- **A resume does NOT re-stamp `[MODEL:]` dates.** Re-enabling returns a task to tag scope, which makes it DUE for a currency check — it is not itself an observation. A resume task must not bump `checked`/`set` dates on the tasks it flips; that fabricates a verification (`memory/feedback_verified_null_vs_inferred_null.md`). This QUALIFIES the PAUSE bullet's "re-tag in the same pass" above: that binds a hand re-enable where the model IS observed, not an automated bulk resume.
- Root incident (2026-08-17) + the verified fleet asymmetry it left behind: `references/incident-history.md` § Bounded pause.

## Concurrent-writer check (before any registration/recovery/bulk-retire session)

Registering, retiring, or bulk-recovering tasks touches shared state exactly like the `ora-skills` git repo and `event_log.md` — the same claim-first-write-second discipline applies.

**PRIMARY CHECK (2026-07-12) — `session_info list_sessions`:** before the first write of any registration/retime/retire pass, call `list_sessions` and scan for another session that is `running` or recently active with an overlapping title (task ids, "scheduler," "LAMS," or the same skill name) — that IS a live sibling, not a maybe. `registry-membership.log` does NOT catch this class of collision — it only logs task adds/drops, not cron edits or same-value re-pins, so a same-value collision (two sessions independently arriving at the identical correct cron) leaves no trace there at all. If a live sibling is found: stop, compare notes in-conversation if possible, and agree who applies the write before either session calls `update_scheduled_task` or `create_scheduled_task` again.

**SECONDARY SIGNAL — `registry-membership.log`:** still worth checking for id-level adds/drops (catches the 2026-07-08 duplicate-registration class below), but treat a clean log as inconclusive, not as proof no one else is active — it has a blind spot for cron-only edits.

Two incident precedents motivate the checks above (duplicate-id registration, and a same-day event_log.md write collision from an idempotent concurrent edit) — full narrative: `references/incident-history.md` § Concurrent-writer incidents.

If you discover mid-task that another session is concurrently active, stop, compare notes, and agree who owns which fleet before either of you registers or deletes anything further.

## QC gate before declaring done

`list_scheduled_tasks` shows the entry · id unique across BOTH fleets · cron fires as intended (state the next 2 fire dates ET) · **step 4c's fire-time sanity check run, and any >1.5×-interval gap flagged to Gabriel same-turn** · routing = ggoldberg-only (or sanctioned Daily-Brief exception) · send path = COM script only · no JSON edits anywhere · **`[MODEL:]` tag present WITH a date on the returned `description`, or the task is provably exempt per the scope table (step 4b)** · **for any bounded pause: a resume task verified present for EVERY paused fleet, or its absence flagged same-turn** · **for any one-time task with 3+ sequential side-effect steps: progress-marker calls present in the instructions (step 4d)** · automation-health-monitor coverage flagged for its next list revision.
