# Register Scheduled Task (ORA) — v2.8

**RULE 1 — MCP ONLY.** Register and update tasks EXCLUSIVELY via the `create_scheduled_task` / `update_scheduled_task` MCP tools, in a SUPERVISED session, on the surface where the task should run. If the MCP tool is unavailable in the current session (e.g., unsupervised/scheduled context), STOP and tell Gabriel to run the registration from a supervised session — do not improvise a filesystem path.

**RULE 2 — JSON-SPLICE PROHIBITED.** Direct edits to `scheduled-tasks.json` (the v1.0 "Desktop Commander splice" procedure) are BANNED. Proof: the 2026-06-09 fleet rebuild left splice-registered tasks present in the JSON but never picked up by the scheduler — registered-but-unscheduled. `ora-cowork-heartbeat` went dark 2026-05-31→06-10 in exactly this failure mode. The registry file is the scheduler's private state, not an API.

## Dual-fleet registry model (both live; neither is "the" store)

| Fleet | Registry | SKILL.md store | Register from |
|---|---|---|---|
| CC/MCP | `claude-code-sessions` registry | `~/.claude/scheduled-tasks/{task-id}/` | Claude Code (supervised) |
| LAMS/Cowork | `local-agent-mode-sessions` registry | `OneDrive — Oxford Capital Partners\Documents\Claude\Scheduled\{task-id}\` | Cowork (supervised) |

- Cowork-created tasks land in the LAMS registry BY DESIGN — do not migrate them to the CC store; monitors are store-agnostic.
- Both fleets fire only while the Desktop app is open. Dead-man chain: ora-cowork-heartbeat → Notion page `35c6ecd8…` → GitHub watchdog.
- **Path note (corrected 2026-07-16 — supersedes the v2.0 same-file-via-virtualization framing):** the MSIX store `C:\Users\Owner\AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\...` holds NO Claude data on this machine — verified 2026-07-16: no `Claude` folder under `LocalCache\Roaming` at all, recursive LocalCache search zero hits. The post-2026-07-05-migration install does not write through MSIX virtualization; the SOLE physical store is `C:\Users\Owner\AppData\Roaming\Claude\...`. Probe (`Test-Path`) before sourcing either path; if both ever exist AND diverge (e.g. a future reinstall reintroduces MSIX virtualization), stop and escalate rather than pick a side. Never write to either directly (Rule 2). Prior correction retained, 2026-07-08: the LAMS SKILL.md store path above previously read a "(1)"-suffixed OneDrive folder that does not have a `Documents\Claude\Scheduled` directory at all (a second/legacy synced OneDrive account on this machine) — always verify with a directory check before trusting either "(1)" or no-suffix if a future re-sync reintroduces the ambiguity.
- **CROSS-FLEET SHARED-FILE RISK (2026-07-08):** a CC/MCP task's `~/.claude/scheduled-tasks/{id}/SKILL.md` is very often just a thin redirect stub whose actual content lives at the SAME OneDrive path a LAMS task of the same id would use for its own full spec. If a task with a given id ever exists on BOTH fleets (which Rule "never duplicate ids across either fleet" should prevent, but a same-id collision has now happened during a recovery), deleting or overwriting that file on ONE fleet's surface can silently destroy the OTHER fleet's task content too — even though only one registry entry was touched. Before deleting (not just disabling) any task folder, check whether a same-id task exists on the other fleet and whether its spec might share that path.
- **PATH-DISAMBIGUATOR — which copy am I about to touch? (2026-07-12):** When a same-id task may exist on both fleets, the `path` field returned by `list_scheduled_tasks` is the SOLE reliable disambiguator between the two copies: CC/MCP copy → `path` under `~\.claude\scheduled-tasks\{id}\`; LAMS/Cowork copy → `path` under `...\Documents\Claude\Scheduled\{id}\`. Pause/retire ONLY the entry whose `path` matches the fleet you intend to act on; never act on an entry whose `path` sits under the OTHER fleet's root. **A SKILL.md folder found on disk OUTSIDE both store roots (e.g. `Claude_Workspace\00_Governance\Scheduled\{id}\`) is an orphaned/misfiled copy, NOT evidence of a live registration** — the only proof of a live registration is the task appearing in `list_scheduled_tasks` on that fleet. If a task brief, memory note, or runbook cites a store path that is neither root, treat it as stale and verify against `list_scheduled_tasks` + the two roots above before acting — do not scope a retirement around an unverified path. (2026-07-12 incident: a "retire the redundant LAMS `ora-pm-ledger`" task was scoped around a `00_Governance\Scheduled\ora-pm-ledger\` folder; the live LAMS registry had no such task and that on-disk folder was an orphan in the wrong convention — net: nothing to retire, and a runbook built on the wrong path would have hard-aborted at best.)

## Procedure (new task)

1. **Naming:** task id = kebab-case, `ora-` prefix for firm automations. Check `list_scheduled_tasks` first — if the id exists, this is an UPDATE (`update_scheduled_task`), not a new registration. Never duplicate ids across either fleet.
2. **Surface selection:** decide which fleet the task belongs to (Cowork artifact/skill dependencies → LAMS; filesystem/git/probe work → CC) and register from THAT surface.
3. **SKILL.md content** (passed as the task prompt or stored in the fleet's SKILL.md store) must state:
   - guard conditions (e.g., "first business day only — exit silently otherwise" when cron over-fires);
   - steps with explicit data sources (Notion collection IDs, folder paths, memory names);
   - output destinations (Notion Ops Hub `32b6ecd8` block, file outputs with ISO-date prefix);
   - **email convention:** Outlook COM via `C:\Users\Owner\.claude\scheduled-tasks\_shared\send-via-outlook.ps1` — the SOLE send path (Composio retired 2026-06-11, NO fallback; Rube EOL 2026-05-15; Gmail disabled). TO `ggoldberg@oxfordra.net` ONLY — the cc to `egoldberg@oxfordra.net` is sanctioned for the ora-am-brief Daily Brief ALONE. On non-zero exit: retry once, flag loudly in the Notion completion row, do NOT halt;
   - "never fabricate" + structured QUESTIONS FOR GABRIEL escalation for data gaps;
   - pointers to sibling skills/tasks instead of duplicating their logic.
4. **Register:** call `create_scheduled_task` with cron (ET, 5-field) and the prompt. Cron notes: quarterly-on-first-business-day → `30 6 1-3 1,4,7,10 *` + in-skill business-day guard; avoid `*/n` day-of-month patterns (drift); avoid the 05:00–09:30 pileup window and same-minute collisions with existing tasks.
4b. **MODEL TAG — required at registration, dated, for every in-scope task (2026-07-24).** End the `description` with `[MODEL: <id-or-UNVERIFIABLE> | set|checked YYYY-MM-DD]`. **The date half is mandatory** — a bare `[MODEL: <id>]` is not a valid tag (freshness can't be aged against the model-release lineup anchor), and it lands the task in the stale bucket on the very next guard run rather than passing clean. Which tasks are in scope, which verb to use, and which are exempt (CC/MCP one-time; anything disabled) is defined ONCE in `memory/reference_scheduled_task_model_standard.md` § "Tag scope & required fields" — read it, do not restate it here. Tag at registration, never retroactively: every retroactive sweep so far (07-13, 07-15, 07-22, 07-24) was cleaning up tasks that shipped untagged from this step.
5. **Verify (mandatory — no "done" without evidence):** call `list_scheduled_tasks` and paste the returned entry (id, cron, enabled, next-fire). A registry-file grep is NOT verification (Rule 2 lesson: file presence ≠ scheduled).

## Update / pause / retire — three DIFFERENT operations, do not conflate them

- **UPDATE:** `update_scheduled_task` (cron and/or prompt). Re-verify via `list_scheduled_tasks`.
- **PAUSE (temporary, reversible — the task and its content stay intact):** set `enabled: false` via `update_scheduled_task` on CC/MCP, or the Cowork UI's own enable/disable toggle on LAMS. This is the ONLY correct action when someone says "disable," "pause," "turn off," or "stop this from running for now." **NEVER use the Cowork Scheduled-sidebar's delete/trash icon for a pause** — that control performs RETIRE's destructive step (see below) regardless of intent, and there is no undo. If you are not certain the sidebar has a distinct disable-only control separate from delete, ask before touching it, or do the pause from Claude Code via `update_scheduled_task` instead (2026-07-08 incident: a "disable these" instruction was carried out via sidebar delete, destroying shared spec files and breaking tasks on the OTHER fleet too — see cross-fleet shared-file risk above). **RE-ENABLE carries a model-tag precondition (2026-07-24):** a paused task is exempt from the `[MODEL:]` tag while paused (nothing is firing, so there is nothing to observe or set). The moment you flip `enabled: true`, it is back in scope — re-tag it with a CURRENT date in the same pass, before or with the enable call, never "later." An enable that leaves a stale or absent tag behind is exactly how a task re-enters the fleet invisible to the currency check.
- **RETIRE (permanent — only when the task is genuinely done):** disable first via `update_scheduled_task`; move the SKILL.md directory to `_archive_YYYY-MM-DD_retired\` in its store; note in Ops Hub. Never delete history silently. Update the fleet disposition ledger (`00_Governance/outputs/`). Add the task id to the consolidated "do NOT re-register" list in `session-context.md` (2026-07-08: several previously-retired tasks were resurrected during a recovery because the retirement was only recorded in that task's own SKILL.md frontmatter, not in one checkable place — a scattered record does not stop a future rebuild from re-creating it).
- **RETIRE — ARCHIVE FIRST, DELETE SECOND (hard ordering):** the Cowork Scheduled-sidebar delete is FOLDER-DESTRUCTIVE — it hard-deletes the task's SKILL.md folder along with the registry entry, bypassing the Windows Recycle Bin (OneDrive online recycle bin ~93d is the only recovery; 2026-06-11 incident: `scheduled-task-integrity-guard` kept-by-design backups lost this way; 2026-07-08 incident: recurred, four unrelated CC/MCP tasks broken as collateral damage via the cross-fleet shared-file risk above). Therefore: (1) MOVE the task folder to the dated `_archive_*` folder, (2) VERIFY the move landed, (3) only THEN delete the registry entry in the UI. Log planned removals to `memory/event_log.md` with the literal token `RATIFIED` + the task id — `registry-membership-probe.py` auto-ratifies such drops (≤14d window) instead of raising a false [ACTION].
- **RETIRE — re-home solely-run producer scripts BEFORE deleting the registry entry (added 2026-07-16, setup-review finding C5):** before retiring any task, grep `maintenance/*.py`, `hooks/*.py`, and every other live task's SKILL.md for scripts this task is the SOLE invoker of. If any are found, re-home them into a surviving task's steps (or explicitly retire the script too, with the same archive-first ordering) BEFORE completing this retirement — never after. Root incident: retiring `ora-setup-audit` (2026-06-16) silently orphaned two downstream scripts it alone ran (`registry-membership-probe.py`, `emit-fleet-heartbeat.py`) — the external cross-fleet dead-man froze for a week (2026-07-09→07-16) with its own GitHub alarm sitting unread, before the 2026-07-16 setup review found the gap and fixed it by adding the two scripts as a new step inside `ora-task-integrity-guard`. A task's own SKILL.md naming what it "replaces" or "folds in" is not proof nothing downstream was missed — this is the same producer-orphaning class the do-NOT-re-register list above prevents for the task itself, one level down, for what the task silently ran on the side.

## Concurrent-writer check (before any registration/recovery/bulk-retire session)

Registering, retiring, or bulk-recovering tasks touches shared state exactly like the `ora-skills` git repo and `event_log.md` — the same claim-first-write-second discipline applies.

**PRIMARY CHECK (2026-07-12) — `session_info list_sessions`:** before the first write of any registration/retime/retire pass, call `list_sessions` and scan for another session that is `running` or recently active with an overlapping title (task ids, "scheduler," "LAMS," or the same skill name) — that IS a live sibling, not a maybe. `registry-membership.log` does NOT catch this class of collision — it only logs task adds/drops, not cron edits or same-value re-pins, so a same-value collision (two sessions independently arriving at the identical correct cron) leaves no trace there at all. If a live sibling is found: stop, compare notes in-conversation if possible, and agree who applies the write before either session calls `update_scheduled_task` or `create_scheduled_task` again.

**SECONDARY SIGNAL — `registry-membership.log`:** still worth checking for id-level adds/drops (catches the 2026-07-08 duplicate-registration class below), but treat a clean log as inconclusive, not as proof no one else is active — it has a blind spot for cron-only edits.

**2026-07-08 incident:** two sessions (one on CC/MCP, one on Cowork/LAMS) independently recovered the same failed fleet at the same time without knowing about each other, registering duplicate task ids minutes apart across both fleets. Caught only by re-reading the live registry JSON directly rather than trusting an earlier `list_scheduled_tasks` response.

**2026-07-12 incident (lower severity, motivated the primary-check promotion above):** two Cowork sessions ran the identical LAMS retime handoff concurrently. Both converged on the same correct cron values for the same 3 existing task ids (idempotent, no duplicate ids created), but their simultaneous `append-event-log.py` writes collided on the `event_log.md` file handle (WinError 5 on Windows), and neither session had checked for a live sibling before starting — `registry-membership.log` had nothing to show since no ids were added or dropped. The append script's spool-and-auto-drain design absorbed the collision with zero data loss, but the check that should have prevented the redundant work entirely didn't exist yet. A `list_sessions` call at the start of either session would have shown the other as `running` with a matching title.

If you discover mid-task that another session is concurrently active, stop, compare notes, and agree who owns which fleet before either of you registers or deletes anything further.

## QC gate before declaring done

`list_scheduled_tasks` shows the entry · id unique across BOTH fleets · cron fires as intended (state the next 2 fire dates ET) · routing = ggoldberg-only (or sanctioned Daily-Brief exception) · send path = COM script only · no JSON edits anywhere · **`[MODEL:]` tag present WITH a date on the returned `description`, or the task is provably exempt per the scope table (step 4b)** · automation-health-monitor coverage flagged for its next list revision.
