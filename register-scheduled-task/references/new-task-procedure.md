## Step 3 — SKILL.md content

3. **SKILL.md content** (passed as the task prompt or stored in the fleet's SKILL.md store) must state:
   - guard conditions (e.g., "first business day only — exit silently otherwise" when cron over-fires);
   - steps with explicit data sources (Notion collection IDs, folder paths, memory names);
   - output destinations (Notion Ops Hub `32b6ecd8` block, file outputs with ISO-date prefix);
   - **email convention:** Outlook COM via `C:\Users\Owner\.claude\scheduled-tasks\_shared\send-via-outlook.ps1` — the SOLE send path (Composio retired 2026-06-11, NO fallback; Rube EOL 2026-05-15; Gmail disabled). TO `ggoldberg@oxfordra.net` ONLY — the cc to `egoldberg@oxfordra.net` is sanctioned for the ora-am-brief Daily Brief ALONE. On non-zero exit: retry once, flag loudly in the Notion completion row, do NOT halt;
   - "never fabricate" + structured QUESTIONS FOR GABRIEL escalation for data gaps;
   - pointers to sibling skills/tasks instead of duplicating their logic;
   - **run date computed once (v2.27):** `date '+%A %Y-%m-%d'` at run start, that exact value reused in every title, subject and body (a brief once mixed Tuesday/Wednesday). Its date part fills every date slot and the weekday appears only where one is named, so existing `{DATE}`/`YYYY-MM-DD` subjects, output-contract patterns and Sent-Items probe stems stay byte-compatible (v2.29);
   - **Notion create-pages without a page ID** (e.g. a grace-period/quota notice): look for the page before any retry; treat a match as this run's only if created at/after the create call — never blind-retry a create (produced a duplicate page). Look by `notion-fetch` of the known parent (every Ops Hub page) for an exact-title child first, then by title search: search lags, so a search miss alone is not proof of failure. A retry-once is only for other failures: after a grace-period/quota notice with no match, do not retry — the create is UNVERIFIED and takes the task's publication-failure/fallback path (v2.29). Quota errors: `notion-quota-fallback` skill;
   - **event-log entries** only via `python ~/.claude/maintenance/append-event-log.py`, header `## YYYY-MM-DD — <title>`. Exit 1 = malformed header rejected: match the newest existing heading, don't retry blindly.

## Step 3b — Money-moving tasks

3b. **MONEY-MOVING TASKS — `offhost-backup:` frontmatter is MANDATORY, and a laptop-only registration is REFUSED (v2.19, 2026-09-03).** A task is money-moving when any step of its run can post charges or fees to a tenant/counterparty ledger, initiate a debit, credit, or transfer, or send payment instructions to a third-party system (Stripe, ACH, a lender/borrower portal, QuickBooks JE posting). Root incident: `references/incident-history.md` § Money-moving host outage. Rule:
   - The task's SKILL.md frontmatter MUST carry an `offhost-backup:` line naming a trigger that does NOT run on this machine — repo + workflow path + cron + the date it went live, e.g. `offhost-backup: ZeOoba/ora-pm .github/workflows/monthly-billing-backup.yml (cron 40 17 1 * * UTC, live since YYYY-MM-DD)`. **"Live" is proven, never inferred from a merge (v2.24):** a backup may be declared `live since <date>` only when ALL of — (1) the workflow file is on the repo's default branch and `active` (`gh workflow list --repo <repo> --all --json path,state`); (2) every secret the workflow reads is present BY NAME (`gh secret list --repo <repo>` — names only, never read a value; grep the workflow for `secrets.` to get the list); (3) at least one real run concluded `success` (`gh run list --repo <repo> --workflow=<file> --limit 5`) — cite that run's URL in the same line. A workflow that cannot have run yet (e.g. a monthly cron before its first 1st) proves (3) with one input-less `workflow_dispatch` run against an idempotent endpoint, or stays `pending — awaiting first run`. Merged but failing (1)–(3) is `pending`, or `dormant — <reason>` if it was previously declared live. Root incident: `monthly-billing-backup.yml` merged 2026-09-03 and was declared `live` the same day, but `ORA_PM_CRON_SECRET` was never created — zero runs, would have failed 2026-10-01 (OI-229). The backup must be idempotent against the primary (a re-fire cannot double-post); if the endpoint's idempotency isn't obvious, state the mechanism in the task body.
   - `offhost-backup: pending — <PR/issue>` or `offhost-backup: none — GAP …` is allowed ONLY with Gabriel's explicit in-turn acceptance quoted in the registration turn. Absent that, STOP before `create_scheduled_task` and ask ONE question. Never register a money-moving task with no `offhost-backup:` line at all — a missing line is indistinguishable from "nobody checked".
   - Re-check the line after any `update_scheduled_task` call on that task: the call drops non-owned frontmatter keys (memory: `reference_update_scheduled_task_drops_frontmatter_keys`). Restore it by file edit, never by another update call.
   - Declarations are read from each task's frontmatter, never restated here (a dated copy in this file already went stale once). `automation-health-monitor` v1.10 Step 1.75 re-verifies (1)–(3) for the ora-pm backups every weekday and flags any `live` line that no longer holds. Neither money-moving task's gap may be cleared by narrowing this definition.

## Step 3c — Claim-bearing tasks

3c. **CLAIM-BEARING TASKS — unattended runs MUST claim under the `sched-` namespace (2026-09-07 ruling, OI-116).** A task's SKILL.md instructions claim a slug via `hooks/lib/claim_work.py claim` whenever a run can perform structural writes to a shared claim-relevant path — `hooks/**` (`hooks-override-auth`), `open-items-tracker.md` (`open-items-tracker`), `oxford-command-center` `data/overlay.json`/`data/snapshots/portfolio.json` (`oxford-command-center-data`), a `~/.claude` repo-maintenance sweep (`repo-housekeeping`), or an `ora-skills` commit (`ora-skills-housekeeping`). Before this skill registers or updates such a task, its instructions must claim under **`sched-<slug>`**, not the bare slug — e.g. `sched-ora-skills-housekeeping`, not `ora-skills-housekeeping`. Why this is mandatory, not a style choice: an ordinary claim gets a 120-minute TTL and a "message the holder" refusal, both useless against an unattended holder that cannot be messaged and that self-renews on every edit (OI-116) — `sched-` gets a 30-minute TTL (`min(caller_ttl, 30)`, never widened) so a dead run's claim ages out fast, and the refusal message states outright that force-takeover is ROUTINE for it. **Hyphen, not colon** — the slug is the claim filename and `:` is illegal on Windows; `claim_work.py`'s own `_safe_filename()` would silently mangle `sched:foo` into a different slug than intended. This is the carrier that makes the ruling in `memory/tech.md` §3e effective — the namespace existing in `claim_work.py` alone does nothing for a task whose own instructions never invoke it that way, and no scheduled task claims a `sched-` slug today. Apply this at registration time for every new claim-bearing task, and retrofit it into any existing task's instructions the next time this skill touches that task's SKILL.md.

## Step 4b — Model tag

4b. **MODEL TAG — required at registration, dated, for every in-scope task (2026-07-24).** End the `description` with `[MODEL: <id-or-UNVERIFIABLE> | set|checked YYYY-MM-DD]`. **The date half is mandatory** — a bare `[MODEL: <id>]` is not a valid tag (freshness can't be aged against the model-release lineup anchor), and it lands the task in the stale bucket on the very next guard run rather than passing clean. Which tasks are in scope, which verb to use, and which are exempt (CC/MCP one-time; anything disabled) is defined ONCE in `memory/reference_scheduled_task_model_standard.md` § "Tag scope & required fields" — read it, do not restate it here. Tag at registration, never retroactively: every retroactive sweep so far (07-13, 07-15, 07-22, 07-24) was cleaning up tasks that shipped untagged from this step.

## Step 4c — Fire-time sanity check

4c. **Post-registration fire-time sanity check (2026-08-15).** Registering after a cadence's slot has already passed for the current cycle still returns a syntactically valid `nextRunAt` — just one a full cycle later than "today," and nothing upstream catches that: the cron is well-formed, and step 5's "state the next 2 fire dates" only asks you to report them, not judge them. Root incident: `references/incident-history.md` § Fire-time gap. Before calling step 5 complete, compare the returned `nextRunAt` against the stated cadence's expected interval (daily → ~1 day, weekly → ~7 days, monthly → ~30 days): if it's more than ~1.5× that interval away from the registration timestamp, flag it in the same turn — state plainly that the task registered after this cycle's slot and won't fire until the following one, and ask Gabriel whether that's fine or whether the first run should also go out as a one-time task to close the gap. A syntactically valid `nextRunAt` is not proof the timing is what anyone intended.

## Step 4d — Progress markers for multi-step one-time tasks

4d. **Progress markers for multi-step one-time tasks (OI-202, 2026-08-21).** A model-driven one-time task (natural-language steps run by an agent session, not a deterministic script) that stalls mid-run is indistinguishable from a healthy "still running" task to `lastRunAt` — the scheduler stamps that the instant it fires, not when/if it finishes. Root incident: `ora-routine-pause-resume-08-21` fired, stamped `lastRunAt`, then silently stopped after re-enabling 2 of 35 tasks — no error, no summary email, nothing caught it until a manual `list_scheduled_tasks` diff. If the one-time task you are registering has **3 or more sequential steps with side effects** (not a single-shot action), its SKILL.md instructions must call the marker script after each step:
    `C:/Users/Owner/AppData/Local/Programs/Python/Python313/python.exe C:\Users\Owner\.claude\maintenance\task-progress-marker.py write --fleet <cc|lams> --task-id <this-task-id> --step N --of TOTAL --note "<short state, e.g. current item>"`
    **`--fleet` is REQUIRED** (v2.23). The 2026-09-11 resume's own marker call omitted it and failed with `the following arguments are required: --fleet`. Use the full interpreter path, because bare `python` is not on PATH in scheduled sessions.
    This is opt-in and additive — a task with no marker calls is simply invisible to the check below (not flagged as stalled), so omitting it is a silent no-op, never a false alarm. `ORA Fleet Pause-Resume Guard` (native, every 6h, off-fleet — survives a full pause by construction) reads every marker via `task-progress-marker.py find_stalled()` and alarms on any one-time task whose marker shows an incomplete step that hasn't updated within its grace window (default 20min); it does NOT auto-resume or auto-restart anything. Do not build a second monitor for this — extend the existing guard script, matching the "pointers to sibling skills instead of duplicating logic" rule above.
