# Bounded pause — full rules

Moved verbatim from `SKILL.md` (v2.30 core/reference split, no rule changed). `SKILL.md` names every obligation in a one-line stub; this file holds the full wording. Read the relevant section BEFORE acting.

## Rules

- **A resume must EXCLUDE every retire-pending id.** Read `maintenance/_state/retire-pending.json` before building any bulk resume's id list, and carve those ids out explicitly — they are `enabled:false` because they are on their way OUT, not because they are paused. A resume that re-enables one silently reverses a ratified retirement, and on a same-id cross-fleet pair it also resurrects the duplicate the retirement existed to remove. Say in the same turn which ids you carved out and why. (The guard alarms on this within 6h, but an alarm is the backstop, not the control.)
- **Never blanket-pause the detectors.** `ora-cowork-heartbeat` (dead-man chain → Notion `35c6ecd8…` → GitHub watchdog) and `automation-health-monitor` are what would otherwise surface a failed resume — and BOTH live on LAMS, so a LAMS-wide pause silences the detector for its own failure. Either carve them out of the pause, or state plainly in the same turn that the dead-man chain and health monitor are down for the window and will not report the gap.
- **RESUME-TIME COLLISION CHECK — pick the resume time off the fleet's own cron table, not off the clock (NEW v2.15, 2026-08-24).** A resume time is not a scheduling detail; it decides which of the paused tasks get their last slot back and which lose it permanently. Before committing a `fireAt`, list every paused task whose cadence slot falls in the **last 2 hours before** the proposed resume, and for each one make an explicit call:
  - **Make-up-able** — most sweeps, monitors and nudges re-scan current state on their next fire, so a skipped slot costs latency, not content. Note it and move on.
  - **Period-bounded — the output is GONE if the slot is missed**, because the deliverable only ever covers the period it fired in: week-closeouts, month-end ledgers, inbox windows, daily briefs, EOD ledgers. For these, move the resume **earlier than the slot**, not later. Minutes are enough; the cost of resuming 45 minutes early is nil, and the cost of resuming 30 minutes late is one permanently missing deliverable.
  State the check and its outcome in the same turn as the pause, even when nothing collides — "no period-bounded slot falls in the 2h before the proposed resume" is a real assertion and takes one line.
  Root incident (a round-number resume landed 30 min after `ora-friday-closeout`'s slot; that week's closeout was lost for good): `references/incident-history.md` § Resume-time collision.
- **⛔ AN UNATTENDED RESUME WILL NOT COMPLETE ON ITS OWN (NEW v2.23, 2026-09-12, root cause of OI-273).** The Claude Desktop scheduled-task runner does **not** auto-approve `mcp__scheduled-tasks__update_scheduled_task` in an unattended run.
  - It logs `Not auto-approving "mcp__scheduled-tasks__update_scheduled_task"` and blocks on a prompt with no "always allow" option. Neither the `settings.json` allow rule nor `bypassPermissions` pre-approves it. Bash in the same run IS auto-approved. A partially-approved resume still reports `succeeded` in `list_task_runs`. Evidence (09-11 case, main.log, session record): `references/incident-history.md` § Unattended resume.

  So **the only working path is an ATTENDED resume**, and it must be arranged at pause time and stated in the same turn:
  - Tell Gabriel the resume fires at `fireAt` and will stop for approval. Someone must open that run in the Desktop app and approve each `update_scheduled_task` call.
  - Keep the resume batched: all ids issued in as few turns as possible, so approvals are quick.
  - Alternatively, skip the scheduled resume and have Gabriel ask a live session to "unpause all routines" at the chosen time.
  - A fleet-wide pause can therefore never resume while Gabriel is away, so plan pause length accordingly.

  **Detection backstop (slow, not a timely alarm):** `pause-resume-guard.py` `find_incomplete_resumes()` (OI-273) alarms when a fired resume's listed ids are still disabled 30 min to 72h after firing. It reads live `enabled`, not run status or markers, so a `succeeded` partial resume can no longer pass silently forever. The guard runs on a fixed 6h cycle, though, and its slots can be skipped silently (on 09-11 no run fell in 20:01–20:45Z and the 20:20 ET slot never launched). **Expect detection hours late. After any resume, verify with `list_scheduled_tasks` rather than waiting for this alarm.**
- **RECORD THE PAUSE WINDOW — same pass, right after the resume is verified (NEW v2.22, 2026-09-12).** Run `python ~/.claude/maintenance/_shared/pause_windows.py capture` and paste its `held` counts for EACH paused fleet in the same response. They should equal the paused-id counts. This writes `maintenance/_state/fleet-pause-windows.json`, the durable record that `health-guard-beacon.py`, `fleet-status.py`'s missed-cycle check and `ora-health-guard` C.0b subtract from gaps. `fleet_pause.py` only knows about a pause *while it is live*, so without this record every check that looks back across the pause alarms on it. `capture` records **observed registry state, not parsed text**. A recurring task is *held* at a capture only if it is actually **disabled** AND an enabled, not-yet-fired resume task names its id, where that resume names **≥3 currently-disabled tasks**. For a 1–2 task pause, hand-record it with `pause_windows.py record --note "<evidence>"`. A hold longer than 21 days is voided, not excused. Carve-outs (left enabled) and efficacy checks (which disable nothing) can therefore never be counted, whatever their wording. A task re-enabled early, or one that ran between captures, closes its own interval. Right after pausing, `capture` should list your paused ids under `held`; if it doesn't, the resume isn't registered or doesn't name them. Intervals begin at the FIRST capture that sees the task held, so capturing at pause time is what makes the window start on time. **If the capture does not list your window, the resume SKILL.md is malformed — fix that, don't hand-record around it.** The native `pause-resume-guard.py` also re-runs `capture` every 6h as the backstop, so a forgotten step costs at most one guard cycle, never the record itself. It replaces the hand-written `*_FleetPause_RestoreLedger*.json`. Root incident: `references/incident-history.md` § Pause-window record.
- **A resume does NOT re-stamp `[MODEL:]` dates.** Re-enabling returns a task to tag scope, which makes it DUE for a currency check — it is not itself an observation. A resume task must not bump `checked`/`set` dates on the tasks it flips; that fabricates a verification (`memory/feedback_verified_null_vs_inferred_null.md`). This QUALIFIES the PAUSE bullet's "re-tag in the same pass" above: that binds a hand re-enable where the model IS observed, not an automated bulk resume.
- **ONE-TIME EFFICACY-CHECK CHECK — enumerate overlapping one-time tasks before committing the pause (NEW v2.17, 2026-08-24).** A bounded pause doesn't only cost the paused tasks their own slots — it also poisons any one-time (`fireAt`) task whose MEASUREMENT WINDOW overlaps the pause, even though that one-time task is itself never paused. An efficacy/retime check that counts "days delivered" from the send log cannot distinguish a disabled task from a genuine miss (`memory/reference_bounded_pause_voided_overlapping_efficacy_checks_2026-08-21.md`). Before committing any bounded pause: list every one-time task on the affected fleet(s) whose `fireAt` falls between the pause start and the earliest plausible resume, and for each one that reads status/delivery history over a window the pause will fall inside, make an explicit call:
  - **Defer** — push its `fireAt` to after the resume, so it measures a live fleet. Preferred when the check has no independent value tied to its original date.
  - **Knowingly void** — if the date is fixed for a reason that outlives the pause (e.g. a hard reporting deadline), leave `fireAt` as-is but record in the SAME pass, in `event_log.md` or the pause's own resume-ledger entry, that its window will include a pause and its verdict must be read against `enabled` history, not the send log alone.
  A pause is not complete with only its own resume registered — an overlapping one-time check left neither deferred nor flagged is a live footgun for the next efficacy ruling. Root incident: `references/incident-history.md` § Voided efficacy checks.
