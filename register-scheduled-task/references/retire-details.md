# RETIRE — detailed rules

Moved verbatim from `SKILL.md` (v2.30 core/reference split, no rule changed). `SKILL.md` names every obligation in a one-line stub; this file holds the full wording. Read the relevant section BEFORE acting.

## Rules

- **RETIRE — a RATIFIED-but-UNEXECUTED retirement must be filed in the retire-pending register, in the SAME pass that ratifies it.** A retirement that is decided but not yet executed leaves a registration alive with `enabled:false` — and `enabled:false` is not a retirement, it is a pause that any fleet-wide resume silently undoes. The gap between ratification and execution is often days (a surface handoff, per Rule 4), so the interval must be guarded, not merely documented. Add the entry to `C:\Users\Owner\.claude\maintenance\_state\retire-pending.json` (`{"fleet": "cc"|"lams", "id": "<task-id>", "ratified": "YYYY-MM-DD", "reason": "...", "executeFrom": "native on-device Cowork session"|"Claude Code"}`), and remove it in the pass that actually executes the retirement. `ORA Fleet Pause-Resume Guard` (native, off-fleet, every 6h) reads that file and ALARMS if a listed id is found `enabled: true` on its named fleet — which is precisely what a blanket resume would do. This register is a plain state file consulted by a guard, NOT a registry: writing to it is not a Rule 2 violation and does not retire anything by itself.
- **RETIRE — re-home solely-run producer scripts BEFORE deleting the registry entry:** before retiring any task, grep `maintenance/*.py`, `hooks/*.py`, and every other live task's SKILL.md for scripts this task is the SOLE invoker of. If any are found, re-home them into a surviving task's steps (or explicitly retire the script too, with the same archive-first ordering) BEFORE completing this retirement — never after. A task's own SKILL.md naming what it "replaces" or "folds in" is not proof nothing downstream was missed. Root incident: `references/incident-history.md` § RETIRE — orphaned producer-script incident.
- **RETIRE — id-collision fleet-resolution: never verify by deleting a live task (2026-08-17).** `delete_scheduled_task` carries no fleet parameter — on a same-id collision it resolves to whichever fleet is LOCAL to the calling session (`memory/reference_delete_scheduled_task_resolves_colliding_id_to_local_fleet.md`). The only safe ways to confirm which fleet a session's calls will hit are (a) `list_scheduled_tasks`' own `path` field (see PATH-DISAMBIGUATOR above), or (b) the client identity the host surface itself reports (e.g., Desktop Commander's `currentClient`). **Never** probe resolution with an actual delete, and never target `ora-cowork-heartbeat` or any other dead-man/heartbeat-chain id as a test subject under any circumstance — a "test delete" against a live task is still a delete, and deleting the wrong copy of a genuine id-collision pair is exactly the hazard the archive-first-delete-second ordering above exists to prevent. Root incident: a session correctly declined to test fleet-resolution against `ora-cowork-heartbeat` before retiring the `ora-passed-deal-tracker` LAMS duplicate, for lack of a documented safe method — this bullet is that method.
