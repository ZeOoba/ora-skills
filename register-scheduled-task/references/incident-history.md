## Cross-fleet shared-file risk (2026-07-08)

A CC/MCP task's `~/.claude/scheduled-tasks/{id}/SKILL.md` is very often just a thin redirect stub whose actual content lives at the SAME OneDrive path a LAMS task of the same id would use for its own full spec. If a task with a given id ever exists on BOTH fleets (which "never duplicate ids across either fleet" should prevent, but a same-id collision has now happened during a recovery), deleting or overwriting that file on ONE fleet's surface can silently destroy the OTHER fleet's task content too — even though only one registry entry was touched.

## Path disambiguator (2026-07-12 incident)

A "retire the redundant LAMS `ora-pm-ledger`" task was scoped around a `00_Governance\Scheduled\ora-pm-ledger\` folder; the live LAMS registry had no such task and that on-disk folder was an orphan in the wrong convention — net: nothing to retire, and a runbook built on the wrong path would have hard-aborted at best.

## PAUSE — sidebar-delete incident (2026-07-08)

A "disable these" instruction was carried out via the Cowork Scheduled-sidebar's delete/trash icon, destroying shared spec files and breaking tasks on the OTHER fleet too (see Cross-fleet shared-file risk above).

## RETIRE — do-NOT-re-register list incident (2026-07-08)

Several previously-retired tasks were resurrected during a fleet-recovery incident because their retirement was recorded only in the task's own SKILL.md frontmatter, not in one checkable place — a scattered record does not stop a future rebuild from re-creating it. This is why RETIRE requires adding the task id to `session-context.md`'s consolidated do-NOT-re-register list.

## Concurrent-writer incidents

**2026-07-08:** two sessions (one on CC/MCP, one on Cowork/LAMS) independently recovered the same failed fleet at the same time without knowing about each other, registering duplicate task ids minutes apart across both fleets. Caught only by re-reading the live registry JSON directly rather than trusting an earlier `list_scheduled_tasks` response.

**2026-07-12 (lower severity, motivated the primary-check promotion in SKILL.md):** two Cowork sessions ran the identical LAMS retime handoff concurrently. Both converged on the same correct cron values for the same 3 existing task ids (idempotent, no duplicate ids created), but their simultaneous `append-event-log.py` writes collided on the `event_log.md` file handle (WinError 5 on Windows), and neither session had checked for a live sibling before starting — `registry-membership.log` had nothing to show since no ids were added or dropped. The append script's spool-and-auto-drain design absorbed the collision with zero data loss, but the check that should have prevented the redundant work entirely didn't exist yet. A `list_sessions` call at the start of either session would have shown the other as `running` with a matching title.

## Bounded pause — LAMS fleet paused with no resume (2026-08-17)

Gabriel asked to pause all routines until Friday 2026-08-21 5:00 PM ET. The CC/MCP half was executed correctly: 35 recurring tasks disabled, and a one-time resume `ora-routine-pause-resume-08-21` registered to fire 2026-08-21 17:00 ET, naming all 35 ids explicitly and passing ONLY `enabled: true` on each `update_scheduled_task` call so hand-edits made during the window survive.

The LAMS/Cowork half did not get that far. The pause landed, but the matching `ora-lams-routine-pause-resume-08-21` was dispatched to a cloud-sandbox Cowork session, which carries none of the registry MCP tools (see SKILL.md § Dual-fleet registry model, surface note). That session correctly halted at Rule 1 rather than improvising — but the halt happened AFTER the pause had already committed, so the fleet was left disabled with no scheduled restore.

Verified against both registries the same day (read-only): CC/MCP 35 of 40 tasks disabled with the resume pending; LAMS 27 of 28 disabled with no resume of any kind — the sole enabled entry being `ora-counsel-review-standard-positions-2027`, a one-time task firing in August 2027. So the CC fleet restores itself on Friday and the LAMS fleet does not restore at all.

Three properties of the failure, each of which the v2.12 rule addresses separately:

1. **Split-by-surface is fine; split-by-turn is not.** A dual-fleet pause naturally divides by surface, since neither fleet's MCP tools reach the other registry. What failed is that one fleet's pause COMMITTED while its own resume registration was still pending on another surface. Pause and resume are one operation per fleet, not two deliverables that can land in different turns.
2. **"Pause all routines" is fleet-ambiguous.** The instruction named no fleet. Reporting "N tasks paused" after touching one registry reads as complete to everyone downstream.
3. **The pause swallowed its own detectors.** `ora-cowork-heartbeat` (dead-man chain → Notion `35c6ecd8…` → GitHub watchdog) and `automation-health-monitor` both live on LAMS and were both disabled by the sweep. The two mechanisms that would otherwise have surfaced a 4-day silent gap were themselves inside it. The only thing that flags the asymmetry is a reminder line in the CC resume task's step-6 summary email — which does not send until 2026-08-21 17:00 ET, i.e. at the end of the window rather than the start.

Separately, the CC resume task's step 5 instructs that re-enabling must NOT bump any `[MODEL:]` freshness date, because re-enabling is not an observation (`memory/feedback_verified_null_vs_inferred_null.md`). That is correct, and it contradicts a literal reading of the v2.8 PAUSE bullet's "re-tag it with a CURRENT date in the same pass." v2.12 reconciles them: the v2.8 rule binds a hand re-enable where the model is actually observed; an automated bulk resume leaves the dates alone and simply returns the task to scope for its next normal currency check.

## Rule 2 proof — JSON splice (2026-06-09)

**RULE 2 — JSON-SPLICE PROHIBITED.** Direct edits to `scheduled-tasks.json` (the v1.0 "Desktop Commander splice" procedure) are BANNED. Proof: the 2026-06-09 fleet rebuild left splice-registered tasks present in the JSON but never picked up by the scheduler — registered-but-unscheduled. `ora-cowork-heartbeat` went dark 2026-05-31→06-10 in exactly this failure mode. The registry file is the scheduler's private state, not an API.

## Rule 3 — verdict in the first turn

- **State the verdict in the first turn** ("surface: native / cloud-sandbox; `list_scheduled_tasks` present / absent"). The check costs about ten seconds; the alternative is discovering the gap mid-task, which is how both v2.10-class incidents ran.

## Rule 4 incident — ora-passed-deal-tracker (2026-08-17, 2026-08-22)

**RULE 4 — DISPATCH-TIME SURFACE ROUTING (the brief picks the surface, not the worker).** Any brief handing a LAMS/Cowork registry WRITE — registration, update, pause, id-collision cleanup, retire — to another session MUST name the surface at dispatch time: **"a native on-device Cowork session"** (the desktop app itself, or Claude Code's "Run this task → On your computer"), never a bare "Cowork session" / "Cowork-side session". Naming only the fleet routes by fleet and lands wherever a Cowork session happens to exist — a coin flip the cloud sandbox wins. The dispatched brief must also (a) carry Rule 3's assertion as its own first step, and (b) state the expected before/after so the receiving session verifies rather than re-derives. **READS are exempt** — `fleet-status.py` reads BOTH registries off disk from any surface, so never dispatch a handoff merely to look something up (`fleet-advisory-remediation` step 5/6). Incident: the `ora-passed-deal-tracker` LAMS deregistration was dispatched to a cloud sandbox TWICE — 2026-08-17 (which created the v2.10 surface note) and again 2026-08-22, same id, same class. The note existed the second time; nothing in the dispatch step pointed at it. This rule is that pointer.

## Surface note — cloud-sandbox sessions (2026-08-17)

- **Surface note — cloud-sandbox Cowork sessions never carry these MCP tools (2026-08-17):** `create_scheduled_task`/`update_scheduled_task`/`delete_scheduled_task`/`list_scheduled_tasks` exist only in a session running natively on-device (Claude Code, or Cowork launched via "Run this task → On your computer") — a cloud-sandbox Cowork session (device-bridge only, no native app process) never carries them, regardless of how a task brief names them. Absence of the tool is the surface, not a transient error: per Rule 1, STOP rather than improvise, and route LAMS registry writes (registrations, id-collision cleanups, retires) to a native on-device session from the start instead of discovering the gap mid-task. Incident: 2026-08-17, an `ora-passed-deal-tracker` id-collision deregistration dispatched to a cloud session that had neither tool. **This note is the WHAT; Rule 3 (assert the surface first) and Rule 4 (name the surface at dispatch time) are the WHEN — a note nothing routes to is what let the same id recur on 2026-08-22.**

## Dual-fleet bullets (verbatim)

- **CROSS-FLEET SHARED-FILE RISK:** a CC/MCP task's SKILL.md is often a thin redirect stub pointing at the SAME OneDrive path a same-id LAMS task uses for its own full spec — deleting or overwriting one can silently destroy the other. Before deleting (not disabling) any task folder, check whether a same-id task exists on the other fleet and whether its spec might share that path. Full mechanism + incident: `references/incident-history.md` § Cross-fleet shared-file risk.
- **PATH-DISAMBIGUATOR:** when a same-id task may exist on both fleets, the `path` field from `list_scheduled_tasks` is the SOLE reliable disambiguator (CC/MCP → `~\.claude\scheduled-tasks\{id}\`; LAMS/Cowork → `...\Documents\Claude\Scheduled\{id}\`). Act only on the entry whose `path` matches your target fleet. **A SKILL.md folder found OUTSIDE both store roots is an orphaned/misfiled copy, NOT evidence of a live registration** — the only proof is the task appearing in `list_scheduled_tasks`. If a task brief, memory note, or runbook cites a store path that is neither root, treat it as stale and verify against `list_scheduled_tasks` + the two roots before acting. Full incident precedent: `references/incident-history.md` § Path disambiguator.

## Money-moving tasks — offhost-backup (2026-09-03, OI-229)

3b. **MONEY-MOVING TASKS — `offhost-backup:` frontmatter is MANDATORY, and a laptop-only registration is REFUSED (v2.19, 2026-09-03).** A task is money-moving when any step of its run can post charges or fees to a tenant/counterparty ledger, initiate a debit, credit, or transfer, or send payment instructions to a third-party system (Stripe, ACH, a lender/borrower portal, QuickBooks JE posting). Root incident: `ora-pm-monthly-billing` (cron `10 11 1 * *`) missed its ONLY monthly fire inside the 2026-08-29→09-01 host outage — every trigger it had lived on the laptop whose downtime WAS the outage, and `fleet-status.py` read it as "0 overdue" for 25h (Automation Audit Rev 21, R21-2 / R21-4). Rule:
   - The task's SKILL.md frontmatter MUST carry an `offhost-backup:` line naming a trigger that does NOT run on this machine — repo + workflow path + cron + the date it went live, e.g. `offhost-backup: ZeOoba/ora-pm .github/workflows/monthly-billing-backup.yml (cron 40 17 1 * * UTC, live since YYYY-MM-DD)`. **"Live" is proven, never inferred from a merge (v2.24):** a backup may be declared `live since <date>` only when ALL of — (1) the workflow file is on the repo's default branch and `active` (`gh workflow list --repo <repo> --all --json path,state`); (2) every secret the workflow reads is present BY NAME (`gh secret list --repo <repo>` — names only, never read a value; grep the workflow for `secrets.` to get the list); (3) at least one real run concluded `success` (`gh run list --repo <repo> --workflow=<file> --limit 5`) — cite that run's URL in the same line. A workflow that cannot have run yet (e.g. a monthly cron before its first 1st) proves (3) with one input-less `workflow_dispatch` run against an idempotent endpoint, or stays `pending — awaiting first run`. Merged but failing (1)–(3) is `pending`, or `dormant — <reason>` if it was previously declared live. Root incident: `monthly-billing-backup.yml` merged 2026-09-03 and was declared `live` the same day, but `ORA_PM_CRON_SECRET` was never created — zero runs, would have failed 2026-10-01 (OI-229). The backup must be idempotent against the primary (a re-fire cannot double-post); if the endpoint's idempotency isn't obvious, state the mechanism in the task body.
   - Declarations are read from each task's frontmatter, never restated here (a dated copy in this file already went stale once). `automation-health-monitor` v1.10 Step 1.75 re-verifies (1)–(3) for the ora-pm backups every weekday and flags any `live` line that no longer holds. Neither money-moving task's gap may be cleared by narrowing this definition.

## Claim-bearing tasks — sched- namespace (2026-09-07, OI-116)

3c. **CLAIM-BEARING TASKS — unattended runs MUST claim under the `sched-` namespace (2026-09-07 ruling, OI-116).** A task's SKILL.md instructions claim a slug via `hooks/lib/claim_work.py claim` whenever a run can perform structural writes to a shared claim-relevant path — `hooks/**` (`hooks-override-auth`), `open-items-tracker.md` (`open-items-tracker`), `oxford-command-center` `data/overlay.json`/`data/snapshots/portfolio.json` (`oxford-command-center-data`), a `~/.claude` repo-maintenance sweep (`repo-housekeeping`), or an `ora-skills` commit (`ora-skills-housekeeping`). Before this skill registers or updates such a task, its instructions must claim under **`sched-<slug>`**, not the bare slug — e.g. `sched-ora-skills-housekeeping`, not `ora-skills-housekeeping`. Why this is mandatory, not a style choice: an ordinary claim gets a 120-minute TTL and a "message the holder" refusal, both useless against an unattended holder that cannot be messaged and that self-renews on every edit (OI-116) — `sched-` gets a 30-minute TTL (`min(caller_ttl, 30)`, never widened) so a dead run's claim ages out fast, and the refusal message states outright that force-takeover is ROUTINE for it. **Hyphen, not colon** — the slug is the claim filename and `:` is illegal on Windows; `claim_work.py`'s own `_safe_filename()` would silently mangle `sched:foo` into a different slug than intended. This is the carrier that makes the ruling in `memory/tech.md` §3e effective — the namespace existing in `claim_work.py` alone does nothing for a task whose own instructions never invoke it that way, and no scheduled task claims a `sched-` slug today. Apply this at registration time for every new claim-bearing task, and retrofit it into any existing task's instructions the next time this skill touches that task's SKILL.md.

## Model tag (2026-07-24)

4b. **MODEL TAG — required at registration, dated, for every in-scope task (2026-07-24).** End the `description` with `[MODEL: <id-or-UNVERIFIABLE> | set|checked YYYY-MM-DD]`. **The date half is mandatory** — a bare `[MODEL: <id>]` is not a valid tag (freshness can't be aged against the model-release lineup anchor), and it lands the task in the stale bucket on the very next guard run rather than passing clean. Which tasks are in scope, which verb to use, and which are exempt (CC/MCP one-time; anything disabled) is defined ONCE in `memory/reference_scheduled_task_model_standard.md` § "Tag scope & required fields" — read it, do not restate it here. Tag at registration, never retroactively: every retroactive sweep so far (07-13, 07-15, 07-22, 07-24) was cleaning up tasks that shipped untagged from this step.

## Fire-time sanity check (2026-08-15)

4c. **Post-registration fire-time sanity check (2026-08-15).** Registering after a cadence's slot has already passed for the current cycle still returns a syntactically valid `nextRunAt` — just one a full cycle later than "today," and nothing upstream catches that: the cron is well-formed, and step 5's "state the next 2 fire dates" only asks you to report them, not judge them. Root incident: `ora-psa-drift-watch`, registered 2026-08-12 (a Wednesday, after a 42+-minute permission-request delay pushed registration past its own 1:30 PM Wednesday slot) — it silently sat until the following Wednesday with nothing flagging the wait; the cron-collision fix that eventually touched it was found by separate investigation, not by this check. Before calling step 5 complete, compare the returned `nextRunAt` against the stated cadence's expected interval (daily → ~1 day, weekly → ~7 days, monthly → ~30 days): if it's more than ~1.5× that interval away from the registration timestamp, flag it in the same turn — state plainly that the task registered after this cycle's slot and won't fire until the following one, and ask Gabriel whether that's fine or whether the first run should also go out as a one-time task to close the gap. A syntactically valid `nextRunAt` is not proof the timing is what anyone intended.

## Progress markers (OI-202, 2026-08-21)

4d. **Progress markers for multi-step one-time tasks (OI-202, 2026-08-21).** A model-driven one-time task (natural-language steps run by an agent session, not a deterministic script) that stalls mid-run is indistinguishable from a healthy "still running" task to `lastRunAt` — the scheduler stamps that the instant it fires, not when/if it finishes. Root incident: `ora-routine-pause-resume-08-21` fired, stamped `lastRunAt`, then silently stopped after re-enabling 2 of 35 tasks — no error, no summary email, nothing caught it until a manual `list_scheduled_tasks` diff. If the one-time task you are registering has **3 or more sequential steps with side effects** (not a single-shot action), its SKILL.md instructions must call the marker script after each step:
    This is opt-in and additive — a task with no marker calls is simply invisible to the check below (not flagged as stalled), so omitting it is a silent no-op, never a false alarm. `ORA Fleet Pause-Resume Guard` (native, every 6h, off-fleet — survives a full pause by construction) reads every marker via `task-progress-marker.py find_stalled()` and alarms on any one-time task whose marker shows an incomplete step that hasn't updated within its grace window (default 20min); it does NOT auto-resume or auto-restart anything. Do not build a second monitor for this — extend the existing guard script, matching the "pointers to sibling skills instead of duplicating logic" rule above.

## PAUSE — re-enable re-tag precondition (2026-07-24)

- **PAUSE (temporary, reversible — the task and its content stay intact):** set `enabled: false` via `update_scheduled_task` on CC/MCP, or the Cowork UI's own enable/disable toggle on LAMS. This is the ONLY correct action when someone says "disable," "pause," "turn off," or "stop this from running for now." **NEVER use the Cowork Scheduled-sidebar's delete/trash icon for a pause** — that control performs RETIRE's destructive step (see below) regardless of intent, and there is no undo. If you are not certain the sidebar has a distinct disable-only control separate from delete, ask before touching it, or do the pause from Claude Code via `update_scheduled_task` instead. Incident precedent: `references/incident-history.md` § PAUSE — sidebar-delete incident. **RE-ENABLE carries a model-tag precondition (2026-07-24):** a paused task is exempt from the `[MODEL:]` tag while paused (nothing is firing, so there is nothing to observe or set). The moment you flip `enabled: true`, it is back in scope — re-tag it with a CURRENT date in the same pass, before or with the enable call, never "later." An enable that leaves a stale or absent tag behind is exactly how a task re-enters the fleet invisible to the currency check.

## Retire-pending register (2026-08-22)

- **RETIRE — a RATIFIED-but-UNEXECUTED retirement must be filed in the retire-pending register, in the SAME pass that ratifies it.** A retirement that is decided but not yet executed leaves a registration alive with `enabled:false` — and `enabled:false` is not a retirement, it is a pause that any fleet-wide resume silently undoes. The gap between ratification and execution is often days (a surface handoff, per Rule 4), so the interval must be guarded, not merely documented. Add the entry to `C:\Users\Owner\.claude\maintenance\_state\retire-pending.json` (`{"fleet": "cc"|"lams", "id": "<task-id>", "ratified": "YYYY-MM-DD", "reason": "...", "executeFrom": "native on-device Cowork session"|"Claude Code"}`), and remove it in the pass that actually executes the retirement. `ORA Fleet Pause-Resume Guard` (native, off-fleet, every 6h) reads that file and ALARMS if a listed id is found `enabled: true` on its named fleet — which is precisely what a blanket resume would do. This register is a plain state file consulted by a guard, NOT a registry: writing to it is not a Rule 2 violation and does not retire anything by itself.

## Id-collision fleet-resolution (2026-08-17)

- **RETIRE — id-collision fleet-resolution: never verify by deleting a live task (2026-08-17).** `delete_scheduled_task` carries no fleet parameter — on a same-id collision it resolves to whichever fleet is LOCAL to the calling session (`memory/reference_delete_scheduled_task_resolves_colliding_id_to_local_fleet.md`). The only safe ways to confirm which fleet a session's calls will hit are (a) `list_scheduled_tasks`' own `path` field (see PATH-DISAMBIGUATOR above), or (b) the client identity the host surface itself reports (e.g., Desktop Commander's `currentClient`). **Never** probe resolution with an actual delete, and never target `ora-cowork-heartbeat` or any other dead-man/heartbeat-chain id as a test subject under any circumstance — a "test delete" against a live task is still a delete, and deleting the wrong copy of a genuine id-collision pair is exactly the hazard the archive-first-delete-second ordering above exists to prevent. Root incident: a session correctly declined to test fleet-resolution against `ora-cowork-heartbeat` before retiring the `ora-passed-deal-tracker` LAMS duplicate, for lack of a documented safe method — this bullet is that method.

## Editing a task's SKILL.md content (v2.25)

UPDATE above covers the registry (cron, enabled, prompt). This section covers the other half: changing the **instructions a task runs by**. Every ORA scheduled task's SKILL.md exists in two places — the fleet store the scheduler actually reads at fire time (`~\.claude\scheduled-tasks\<id>\SKILL.md` for CC/MCP; `OneDrive…\Documents\Claude\Scheduled\<id>\` for LAMS), and the git-tracked copy under `~/.claude`. The registry stores only a `filePath`, so **committing an edit changes nothing about what runs** — the same trap as "a merged PR is not a live deploy" in `CLAUDE.md`'s Release rule. Never report a content fix as done on the strength of a commit.
1. **Edit in a worktree, never the shared checkout.** `~/.claude` routinely carries 100+ dirty files from concurrent sessions; editing there co-mingles hunks. Gate with `preflight-shared-checkout.py` before committing, passing the sha you actually built on — a stale `--since` returns `HEAD_MOVED`, which reads identically to real contention (`memory/feedback_preflight_stale_since_false_contention.md`). Check `dirty_overlap_foreign` and `competing_claims` in its `RESULT_JSON` before believing a contention verdict.
2. **Make the edit with the Edit/Write tool, not a Bash heredoc/sed/script.** Provenance is recorded only by the Edit/Write hook, so a Bash-written file reads to the gate as having no owner and returns `CONTESTED` against your own work (`memory/feedback_preflight_provenance_needs_edit_tool.md`). Re-applying the identical edit through Edit is the fix; `--force` never is.
3. **Fix every site of the rule you are changing.** A skip rule, routing constant or threshold is typically stated in both a standing-prohibition section and the step that evaluates it. Changing one leaves the spec self-contradictory and an agent free to follow either. Grep the file for the constant before editing, and quote every site back when reporting.
5. **Check line endings BEFORE the copy.** These files are CRLF. Copying an LF-normalised worktree file over a CRLF live file rewrites all 27-odd lines and destroys any ability to diff the real change. Compare `grep -c $'\r'` and line counts on both, and confirm `diff --strip-trailing-cr` shows only the lines you meant to touch.
7. **Test the changed rule against real data before declaring done.** If the edit changed a matching rule, run it over the actual population it will face plus adversarial cases — for a name-based skip rule, every real counterparty name in that pipeline (must NOT match) and every sentinel variant (must match). Doctrine asserted is not doctrine verified; this is the Done-bar's evidence-before-claim applied to prose specs.
**Do not silently widen a matching rule to make it simpler.** A skip/exclusion pattern must stay anchored and narrow enough that it cannot swallow real counterparty work: a false negative on a genuine tenant, deal or payment is far worse than the false positive the rule exists to stop. Record that reasoning inline next to the rule, so a later "tidy-up" does not undo it. The test-artifact convention is the `ZZ` sentinel — `^ZZ[\s._-]*TEST`, case-insensitive, leading whitespace stripped, anchored prefix only (never a bare `TEST`, which matches real tenants like "TESTA Construction"). Use that same sentinel for any new name-based test exclusion rather than inventing a per-task variant.

## Bounded pause bullets (verbatim)

- **Rule:** a pause with a stated or implied end ("until Friday," "for two weeks," "while I'm out") is NOT complete until its resume task is registered — or confirmed already registered — in the SAME supervised session, on the SAME surface, in the SAME pass. Bulk is the aggravating factor, not the trigger: one task paused "until Friday" fails identically. A genuinely open-ended pause has no resume to register — say that explicitly rather than skipping the step silently.
- **A resume must EXCLUDE every retire-pending id.** Read `maintenance/_state/retire-pending.json` before building any bulk resume's id list, and carve those ids out explicitly — they are `enabled:false` because they are on their way OUT, not because they are paused. A resume that re-enables one silently reverses a ratified retirement, and on a same-id cross-fleet pair it also resurrects the duplicate the retirement existed to remove. Say in the same turn which ids you carved out and why. (The guard alarms on this within 6h, but an alarm is the backstop, not the control.)
- **A resume does NOT re-stamp `[MODEL:]` dates.** Re-enabling returns a task to tag scope, which makes it DUE for a currency check — it is not itself an observation. A resume task must not bump `checked`/`set` dates on the tasks it flips; that fabricates a verification (`memory/feedback_verified_null_vs_inferred_null.md`). ## Pause window record (v2.22, 2026-09-12)

- **RECORD THE PAUSE WINDOW — same pass, right after the resume is verified (NEW v2.22, 2026-09-12).** Run `python ~/.claude/maintenance/_shared/pause_windows.py capture` and paste its `held` counts for EACH paused fleet in the same response. This writes `maintenance/_state/fleet-pause-windows.json`, the durable record that `health-guard-beacon.py`, `fleet-status.py`'s missed-cycle check and `ora-health-guard` C.0b subtract from gaps. `fleet_pause.py` only knows about a pause *while it is live*, so without this record every check that looks back across the pause alarms on it. `capture` records **observed registry state, not parsed text**. A recurring task is *held* at a capture only if it is actually **disabled** AND an enabled, not-yet-fired resume task names its id, where that resume names **≥3 currently-disabled tasks**. For a 1–2 task pause, hand-record it with `pause_windows.py record --note "<evidence>"`. A hold longer than 21 days is voided, not excused. Carve-outs (left enabled) and efficacy checks (which disable nothing) can therefore never be counted, whatever their wording. A task re-enabled early, or one that ran between captures, closes its own interval. Right after pausing, `capture` should list your paused ids under `held`; if it doesn't, the resume isn't registered or doesn't name them. Intervals begin at the FIRST capture that sees the task held, so capturing at pause time is what makes the window start on time. **If the capture does not list your window, the resume SKILL.md is malformed — fix that, don't hand-record around it.** The native `pause-resume-guard.py` also re-runs `capture` every 6h as the backstop, so a forgotten step costs at most one guard cycle, never the record itself.
