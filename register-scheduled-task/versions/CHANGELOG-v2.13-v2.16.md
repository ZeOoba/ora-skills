# register-scheduled-task — Changelog (v2.13–v2.16)

Archived from `SKILL.md` 2026-08-28 (workflow-optimization follow-up to ORA Automation Audit Revision 19 — repo-only, excluded from packaging per `tools/package_skills.py`'s top-level `versions/` exclusion). Current version's changelog entry lives in `SKILL.md` itself; only superseded entries move here going forward. Continues `CHANGELOG-v2.9-v2.12.md`.

- **v2.16 (2026-08-24):** Description trimmed 1015 → ~950 chars against the 1024-char platform limit. v2.15's RESUME-TIME COLLISION CHECK clause pushed the description to 1070, over the cap — the pre-commit frontmatter gate blocked the commit, and an emergency trim brought it to 1015, leaving **nine characters** of headroom. That is not a working margin: the next clause anyone adds silently overflows, and an over-length description is rejected at import with no error text anywhere. Trimmed by compressing already-redundant qualifiers ("PAUSE-vs-RETIRE distinction" → "PAUSE-vs-RETIRE", "cross-fleet shared-file blast radius" → "cross-fleet blast radius", "an id-collision safety rule" → "an id-collision rule", "a one-time-task progress-marker convention" → "a progress-marker convention", and dropping the parenthetical gloss on the pre-flight surface assertion). **No trigger vocabulary removed and no rule text changed** — every clause still names its rule; the body is where each is defined. Run `python tools/description_budget.py register-scheduled-task` before the next description edit.
- **v2.15 (2026-08-24, Gabriel-directed — "fix all workflow optimizations" from that morning's Automation Health report):** Added the **RESUME-TIME COLLISION CHECK** to the bounded-pause section, and a matching QC-gate item. v2.12 got the resume's *existence* right and said nothing about its *time*; the time turns out to decide which paused tasks get their last slot back and which lose it permanently. Root incident, found three days late by `automation-health-monitor`: the 2026-08-17 pause's resume was set to Friday 17:00 ET — a round number picked off the clock — and `ora-friday-closeout` fires Fridays at 16:30, so the resume landed 30 minutes after the one slot it needed to precede. The week-of-08-17 closeout ledger and week-ahead synthesis were never produced and cannot be reconstructed. What makes this worth a rule rather than a note: the failure is **invisible by construction**. The health monitor correctly suppresses the lateness finding (PAUSED-SLOT, its new Step 0.5d), so no ⚠️ is raised and the missing OUTPUT is the only trace — which is exactly why the check has to sit here, upstream, at the moment the `fireAt` is chosen. The rule is cheap: enumerate paused tasks with a slot in the 2h before the proposed resume, classify each make-up-able vs period-bounded, and move the resume EARLIER than any period-bounded slot. Stating the outcome is mandatory even when nothing collides, so "I checked" is distinguishable from "I didn't think about it."
- **v2.14 (2026-08-22):** Added RULE 3 (pre-flight surface assertion) and RULE 4 (dispatch-time surface routing), plus the retire-pending register (RETIRE section + a matching bounded-pause carve-out bullet, guarded by `pause-resume-guard.py`). Root incident: the `ora-passed-deal-tracker` LAMS deregistration was dispatched to a cloud-sandbox Cowork session for the SECOND time (2026-08-17, then 2026-08-22 — same id, same class). v2.10 had already documented the surface gap correctly; nothing at dispatch time read it, and the receiving session could only discover the gap after it had begun. Rule 3 moves the discovery to the first ten seconds of the pass and forbids splitting an ordered pass across it; Rule 4 moves the decision one step earlier still, to whoever writes the brief — "a native on-device Cowork session," never a bare "Cowork session." Also closes the adjacent hazard the second incident exposed: the LAMS copy sits `enabled:false` only because of the stalled 2026-08-21 bulk resume, so every future fleet-wide resume re-arms it until the registration is actually dropped — retire-pending.json plus the guard's new check makes that interval observable instead of silent. Doc change here; the guard-script check and its tests are in `~/.claude/maintenance/`.
- **v2.13 (2026-08-21):** Added step 4d — multi-step one-time tasks (3+ sequential side-effect steps) must call `task-progress-marker.py write` after each step, so a mid-run stall is distinguishable from "still running" instead of only visible via a manual `list_scheduled_tasks` diff. Opt-in and additive (a task with no marker calls is invisible to the check, never a false alarm). `ORA Fleet Pause-Resume Guard` (native, off-fleet, every 6h) now also reads markers via `task-progress-marker.py find_stalled()` and alarms on a stale/incomplete one. Root incident: `ora-routine-pause-resume-08-21` stalled after 2 of 35 steps with no error and no summary email; filed as `open-items-tracker.md#OI-202`. Same pass, also fixed two live bugs in the guard script found while wiring this in: it read a live registry task's id via a `taskId` field (the actual field is `id`) and parsed `fireAt` as an ISO string (it's epoch-ms) — both silently swallowed by a bare `except`, so the guard's resume-overdue detection could never match anything since it was built earlier the same day. Doc + guard-script change; no change to registration/pause/retire procedure itself.
