# Register Scheduled Task (ORA) (v2.29)

**RULE 1 — MCP ONLY.** Register and update tasks EXCLUSIVELY via the `create_scheduled_task` / `update_scheduled_task` MCP tools, in a SUPERVISED session, on the surface where the task should run. If the MCP tool is unavailable in the current session (e.g., unsupervised/scheduled context), STOP and tell Gabriel to run the registration from a supervised session — do not improvise a filesystem path.

**RULE 2 — JSON-SPLICE PROHIBITED.** Direct edits to `scheduled-tasks.json` (the v1.0 "Desktop Commander splice" procedure) are BANNED. Proof: the 2026-06-09 fleet rebuild left splice-registered tasks present in the JSON but never picked up by the scheduler — registered-but-unscheduled. `ora-cowork-heartbeat` went dark 2026-05-31→06-10 in exactly this failure mode. The registry file is the scheduler's private state, not an API.

**RULE 3 — PRE-FLIGHT SURFACE ASSERTION (first action of the pass, before anything else).** Before any registration, update, pause, bulk-recovery, RETIRE step, or archive move — and before reading task folders to plan one — assert the surface: search THIS session's own tool registry for `list_scheduled_tasks`.

- **Present** → this session is native on-device and can write to its local fleet. Name which fleet that is from `list_scheduled_tasks`' `path` field (PATH-DISAMBIGUATOR below) before the first write, since `create_/update_/delete_scheduled_task` all resolve session-local with no fleet parameter.
- **Absent** → this is a cloud-sandbox Cowork session (device-bridge only, no native app process). STOP per Rule 1, name the four missing tools, and route the work to a native on-device session per Rule 4. Do not improvise a filesystem path (Rule 2).
- **Absence is the surface, not a transient error.** Prove it by tool-registry search — never by calling a tool and reading the failure. A "test call" against `delete_scheduled_task` is still a delete (see the RETIRE id-collision bullet).
- **Assert BEFORE the first step of an ordered pass, never between its steps.** Archive-first-delete-second is ONE pass: a session that can do step 1 but not step 2 must do neither. Half-executing it — folder archived, registry entry still live and pointing at a moved path — is worse than not starting, and is exactly what this assertion exists to prevent.
- **State the verdict in the first turn** ("surface: native / cloud-sandbox; `list_scheduled_tasks` present / absent"). The check costs about ten seconds; the alternative is discovering the gap mid-task, which is how both v2.10-class incidents ran.

**RULE 4 — DISPATCH-TIME SURFACE ROUTING (the brief picks the surface, not the worker).** Any brief handing a LAMS/Cowork registry WRITE — registration, update, pause, id-collision cleanup, retire — to another session MUST name the surface at dispatch time: **"a native on-device Cowork session"** (the desktop app itself, or Claude Code's "Run this task → On your computer"), never a bare "Cowork session" / "Cowork-side session". Naming only the fleet routes by fleet and lands wherever a Cowork session happens to exist — a coin flip the cloud sandbox wins. The dispatched brief must also (a) carry Rule 3's assertion as its own first step, and (b) state the expected before/after so the receiving session verifies rather than re-derives. **READS are exempt** — `fleet-status.py` reads BOTH registries off disk from any surface, so never dispatch a handoff merely to look something up (`fleet-advisory-remediation` step 5/6). Incident: the `ora-passed-deal-tracker` LAMS deregistration was dispatched to a cloud sandbox TWICE — 2026-08-17 (which created the v2.10 surface note) and again 2026-08-22, same id, same class. The note existed the second time; nothing in the dispatch step pointed at it. This rule is that pointer.

## Dual-fleet registry model (both live; neither is "the" store)

| Fleet | Registry | SKILL.md store | Register from |
|---|---|---|---|
| CC/MCP | `claude-code-sessions` registry | `~/.claude/scheduled-tasks/{task-id}/` | Claude Code (supervised) |
| LAMS/Cowork | `local-agent-mode-sessions` registry | `OneDrive — Oxford Capital Partners\Documents\Claude\Scheduled\{task-id}\` | Cowork (supervised) |

- Cowork-created tasks land in the LAMS registry BY DESIGN — do not migrate them to the CC store; monitors are store-agnostic.
- **Surface note — cloud-sandbox Cowork sessions never carry these MCP tools (2026-08-17):** `create_scheduled_task`/`update_scheduled_task`/`delete_scheduled_task`/`list_scheduled_tasks` exist only in a session running natively on-device (Claude Code, or Cowork launched via "Run this task → On your computer") — a cloud-sandbox Cowork session (device-bridge only, no native app process) never carries them, regardless of how a task brief names them. Absence of the tool is the surface, not a transient error: per Rule 1, STOP rather than improvise, and route LAMS registry writes (registrations, id-collision cleanups, retires) to a native on-device session from the start instead of discovering the gap mid-task. Incident: 2026-08-17, an `ora-passed-deal-tracker` id-collision deregistration dispatched to a cloud session that had neither tool. **This note is the WHAT; Rule 3 (assert the surface first) and Rule 4 (name the surface at dispatch time) are the WHEN — a note nothing routes to is what let the same id recur on 2026-08-22.**
- Both fleets fire only while the Desktop app is open. Dead-man chain: ora-cowork-heartbeat → Notion page `35c6ecd8…` → GitHub watchdog.
- **Path note:** sole physical store is `C:\Users\Owner\AppData\Roaming\Claude\...` — the MSIX LocalCache path holds no Claude data on this machine. Probe (`Test-Path`) before sourcing either path; if both exist AND diverge, stop and escalate. Never write to either directly (Rule 2). Verify the LAMS OneDrive path with a directory check before trusting either the '(1)' or no-suffix form. Full verification history: `references/incident-history.md` § Path note.
- **CROSS-FLEET SHARED-FILE RISK:** a CC/MCP task's SKILL.md is often a thin redirect stub pointing at the SAME OneDrive path a same-id LAMS task uses for its own full spec — deleting or overwriting one can silently destroy the other. Before deleting (not disabling) any task folder, check whether a same-id task exists on the other fleet and whether its spec might share that path. Full mechanism + incident: `references/incident-history.md` § Cross-fleet shared-file risk.
- **PATH-DISAMBIGUATOR:** when a same-id task may exist on both fleets, the `path` field from `list_scheduled_tasks` is the SOLE reliable disambiguator (CC/MCP → `~\.claude\scheduled-tasks\{id}\`; LAMS/Cowork → `...\Documents\Claude\Scheduled\{id}\`). Act only on the entry whose `path` matches your target fleet. **A SKILL.md folder found OUTSIDE both store roots is an orphaned/misfiled copy, NOT evidence of a live registration** — the only proof is the task appearing in `list_scheduled_tasks`. If a task brief, memory note, or runbook cites a store path that is neither root, treat it as stale and verify against `list_scheduled_tasks` + the two roots before acting. Full incident precedent: `references/incident-history.md` § Path disambiguator.

## Procedure (new task)

0. **Surface assertion (Rule 3)** — run it before step 1, and state the verdict. Every procedure below (new task, update, pause, retire, bounded pause) starts here.
1. **Naming:** task id = kebab-case, `ora-` prefix for firm automations. Check `list_scheduled_tasks` first — if the id exists, this is an UPDATE (`update_scheduled_task`), not a new registration. Never duplicate ids across either fleet.
2. **Surface selection:** decide which fleet the task belongs to (Cowork artifact/skill dependencies → LAMS; filesystem/git/probe work → CC) and register from THAT surface.
3. **SKILL.md content** (passed as the task prompt or stored in the fleet's SKILL.md store) must state:
   - guard conditions (e.g., "first business day only — exit silently otherwise" when cron over-fires);
   - steps with explicit data sources (Notion collection IDs, folder paths, memory names);
   - output destinations (Notion Ops Hub `32b6ecd8` block, file outputs with ISO-date prefix);
   - **email convention:** Outlook COM via `C:\Users\Owner\.claude\scheduled-tasks\_shared\send-via-outlook.ps1` — the SOLE send path (Composio retired 2026-06-11, NO fallback; Rube EOL 2026-05-15; Gmail disabled). TO `ggoldberg@oxfordra.net` ONLY — the cc to `egoldberg@oxfordra.net` is sanctioned for the ora-am-brief Daily Brief ALONE. On non-zero exit: retry once, flag loudly in the Notion completion row, do NOT halt;
   - "never fabricate" + structured QUESTIONS FOR GABRIEL escalation for data gaps;
   - pointers to sibling skills/tasks instead of duplicating their logic;
   - **run date computed once (v2.27):** `date '+%A %Y-%m-%d'` at run start, that exact value reused in every title, subject and body (a brief once mixed Tuesday/Wednesday). Its date part fills every date slot and the weekday appears only where one is named, so existing `{DATE}`/`YYYY-MM-DD` subjects, output-contract patterns and Sent-Items probe stems stay byte-compatible (v2.29);
   - **Notion create-pages without a page ID** (e.g. a grace-period/quota notice): look for the page before any retry; treat a match as this run's only if created at/after the create call — never blind-retry a create (produced a duplicate page). Look by `notion-fetch` of the known parent (every Ops Hub page) for an exact-title child first, then by title search: search lags, so a search miss alone is not proof of failure. After a grace-period/quota notice specifically, do not retry at all; report the create as UNVERIFIED (v2.29). Quota errors: `notion-quota-fallback` skill;
   - **event-log entries** only via `python ~/.claude/maintenance/append-event-log.py`, header `## YYYY-MM-DD — <title>`. Exit 1 = malformed header rejected: match the newest existing heading, don't retry blindly.
3b. **MONEY-MOVING TASKS — `offhost-backup:` frontmatter is MANDATORY, and a laptop-only registration is REFUSED (v2.19, 2026-09-03).** A task is money-moving when any step of its run can post charges or fees to a tenant/counterparty ledger, initiate a debit, credit, or transfer, or send payment instructions to a third-party system (Stripe, ACH, a lender/borrower portal, QuickBooks JE posting). Root incident: `references/incident-history.md` § Money-moving host outage. Rule:
   - The task's SKILL.md frontmatter MUST carry an `offhost-backup:` line naming a trigger that does NOT run on this machine — repo + workflow path + cron + the date it went live, e.g. `offhost-backup: ZeOoba/ora-pm .github/workflows/monthly-billing-backup.yml (cron 40 17 1 * * UTC, live since YYYY-MM-DD)`. **"Live" is proven, never inferred from a merge (v2.24):** a backup may be declared `live since <date>` only when ALL of — (1) the workflow file is on the repo's default branch and `active` (`gh workflow list --repo <repo> --all --json path,state`); (2) every secret the workflow reads is present BY NAME (`gh secret list --repo <repo>` — names only, never read a value; grep the workflow for `secrets.` to get the list); (3) at least one real run concluded `success` (`gh run list --repo <repo> --workflow=<file> --limit 5`) — cite that run's URL in the same line. A workflow that cannot have run yet (e.g. a monthly cron before its first 1st) proves (3) with one input-less `workflow_dispatch` run against an idempotent endpoint, or stays `pending — awaiting first run`. Merged but failing (1)–(3) is `pending`, or `dormant — <reason>` if it was previously declared live. Root incident: `monthly-billing-backup.yml` merged 2026-09-03 and was declared `live` the same day, but `ORA_PM_CRON_SECRET` was never created — zero runs, would have failed 2026-10-01 (OI-229). The backup must be idempotent against the primary (a re-fire cannot double-post); if the endpoint's idempotency isn't obvious, state the mechanism in the task body.
   - `offhost-backup: pending — <PR/issue>` or `offhost-backup: none — GAP …` is allowed ONLY with Gabriel's explicit in-turn acceptance quoted in the registration turn. Absent that, STOP before `create_scheduled_task` and ask ONE question. Never register a money-moving task with no `offhost-backup:` line at all — a missing line is indistinguishable from "nobody checked".
   - Re-check the line after any `update_scheduled_task` call on that task: the call drops non-owned frontmatter keys (memory: `reference_update_scheduled_task_drops_frontmatter_keys`). Restore it by file edit, never by another update call.
   - Declarations are read from each task's frontmatter, never restated here (a dated copy in this file already went stale once). `automation-health-monitor` v1.10 Step 1.75 re-verifies (1)–(3) for the ora-pm backups every weekday and flags any `live` line that no longer holds. Neither money-moving task's gap may be cleared by narrowing this definition.
3c. **CLAIM-BEARING TASKS — unattended runs MUST claim under the `sched-` namespace (2026-09-07 ruling, OI-116).** A task's SKILL.md instructions claim a slug via `hooks/lib/claim_work.py claim` whenever a run can perform structural writes to a shared claim-relevant path — `hooks/**` (`hooks-override-auth`), `open-items-tracker.md` (`open-items-tracker`), `oxford-command-center` `data/overlay.json`/`data/snapshots/portfolio.json` (`oxford-command-center-data`), a `~/.claude` repo-maintenance sweep (`repo-housekeeping`), or an `ora-skills` commit (`ora-skills-housekeeping`). Before this skill registers or updates such a task, its instructions must claim under **`sched-<slug>`**, not the bare slug — e.g. `sched-ora-skills-housekeeping`, not `ora-skills-housekeeping`. Why this is mandatory, not a style choice: an ordinary claim gets a 120-minute TTL and a "message the holder" refusal, both useless against an unattended holder that cannot be messaged and that self-renews on every edit (OI-116) — `sched-` gets a 30-minute TTL (`min(caller_ttl, 30)`, never widened) so a dead run's claim ages out fast, and the refusal message states outright that force-takeover is ROUTINE for it. **Hyphen, not colon** — the slug is the claim filename and `:` is illegal on Windows; `claim_work.py`'s own `_safe_filename()` would silently mangle `sched:foo` into a different slug than intended. This is the carrier that makes the ruling in `memory/tech.md` §3e effective — the namespace existing in `claim_work.py` alone does nothing for a task whose own instructions never invoke it that way, and no scheduled task claims a `sched-` slug today. Apply this at registration time for every new claim-bearing task, and retrofit it into any existing task's instructions the next time this skill touches that task's SKILL.md.
4. **Register:** call `create_scheduled_task` with cron (ET, 5-field) and the prompt. Cron notes: quarterly-on-first-business-day → `30 6 1-3 1,4,7,10 *` + in-skill business-day guard; avoid `*/n` day-of-month patterns (drift); avoid the 05:00–09:30 pileup window and same-minute collisions with existing tasks.
4b. **MODEL TAG — required at registration, dated, for every in-scope task (2026-07-24).** End the `description` with `[MODEL: <id-or-UNVERIFIABLE> | set|checked YYYY-MM-DD]`. **The date half is mandatory** — a bare `[MODEL: <id>]` is not a valid tag (freshness can't be aged against the model-release lineup anchor), and it lands the task in the stale bucket on the very next guard run rather than passing clean. Which tasks are in scope, which verb to use, and which are exempt (CC/MCP one-time; anything disabled) is defined ONCE in `memory/reference_scheduled_task_model_standard.md` § "Tag scope & required fields" — read it, do not restate it here. Tag at registration, never retroactively: every retroactive sweep so far (07-13, 07-15, 07-22, 07-24) was cleaning up tasks that shipped untagged from this step.
4c. **Post-registration fire-time sanity check (2026-08-15).** Registering after a cadence's slot has already passed for the current cycle still returns a syntactically valid `nextRunAt` — just one a full cycle later than "today," and nothing upstream catches that: the cron is well-formed, and step 5's "state the next 2 fire dates" only asks you to report them, not judge them. Root incident: `references/incident-history.md` § Fire-time gap. Before calling step 5 complete, compare the returned `nextRunAt` against the stated cadence's expected interval (daily → ~1 day, weekly → ~7 days, monthly → ~30 days): if it's more than ~1.5× that interval away from the registration timestamp, flag it in the same turn — state plainly that the task registered after this cycle's slot and won't fire until the following one, and ask Gabriel whether that's fine or whether the first run should also go out as a one-time task to close the gap. A syntactically valid `nextRunAt` is not proof the timing is what anyone intended.
4d. **Progress markers for multi-step one-time tasks (OI-202, 2026-08-21).** A model-driven one-time task (natural-language steps run by an agent session, not a deterministic script) that stalls mid-run is indistinguishable from a healthy "still running" task to `lastRunAt` — the scheduler stamps that the instant it fires, not when/if it finishes. Root incident: `ora-routine-pause-resume-08-21` fired, stamped `lastRunAt`, then silently stopped after re-enabling 2 of 35 tasks — no error, no summary email, nothing caught it until a manual `list_scheduled_tasks` diff. If the one-time task you are registering has **3 or more sequential steps with side effects** (not a single-shot action), its SKILL.md instructions must call the marker script after each step:
    `C:/Users/Owner/AppData/Local/Programs/Python/Python313/python.exe C:\Users\Owner\.claude\maintenance\task-progress-marker.py write --fleet <cc|lams> --task-id <this-task-id> --step N --of TOTAL --note "<short state, e.g. current item>"`
    **`--fleet` is REQUIRED** (v2.23). The 2026-09-11 resume's own marker call omitted it and failed with `the following arguments are required: --fleet`. Use the full interpreter path, because bare `python` is not on PATH in scheduled sessions.
    This is opt-in and additive — a task with no marker calls is simply invisible to the check below (not flagged as stalled), so omitting it is a silent no-op, never a false alarm. `ORA Fleet Pause-Resume Guard` (native, every 6h, off-fleet — survives a full pause by construction) reads every marker via `task-progress-marker.py find_stalled()` and alarms on any one-time task whose marker shows an incomplete step that hasn't updated within its grace window (default 20min); it does NOT auto-resume or auto-restart anything. Do not build a second monitor for this — extend the existing guard script, matching the "pointers to sibling skills instead of duplicating logic" rule above.
5. **Verify (mandatory — no "done" without evidence):** call `list_scheduled_tasks` and paste the returned entry (id, cron, enabled, next-fire), including the step 4c sanity check's verdict. A registry-file grep is NOT verification (Rule 2 lesson: file presence ≠ scheduled).

## Update / pause / retire — three DIFFERENT operations, do not conflate them

- **UPDATE:** `update_scheduled_task` (cron and/or prompt). Re-verify via `list_scheduled_tasks`. **A `cronExpression` change RE-ENABLES a disabled task** — during a pause, pass `enabled:false` in the SAME call, then confirm the enabled count matches a pre-change snapshot (hit twice: 09-17, 09-22).
- **PAUSE (temporary, reversible — the task and its content stay intact):** set `enabled: false` via `update_scheduled_task` on CC/MCP, or the Cowork UI's own enable/disable toggle on LAMS. This is the ONLY correct action when someone says "disable," "pause," "turn off," or "stop this from running for now." **NEVER use the Cowork Scheduled-sidebar's delete/trash icon for a pause** — that control performs RETIRE's destructive step (see below) regardless of intent, and there is no undo. If you are not certain the sidebar has a distinct disable-only control separate from delete, ask before touching it, or do the pause from Claude Code via `update_scheduled_task` instead. Incident precedent: `references/incident-history.md` § PAUSE — sidebar-delete incident. **RE-ENABLE carries a model-tag precondition (2026-07-24):** a paused task is exempt from the `[MODEL:]` tag while paused (nothing is firing, so there is nothing to observe or set). The moment you flip `enabled: true`, it is back in scope — re-tag it with a CURRENT date in the same pass, before or with the enable call, never "later." An enable that leaves a stale or absent tag behind is exactly how a task re-enters the fleet invisible to the currency check.
- **RETIRE (permanent — only when the task is genuinely done):** disable first via `update_scheduled_task`; move the SKILL.md directory to `_archive_YYYY-MM-DD_retired\` in its store; note in Ops Hub. Never delete history silently. Update the fleet disposition ledger (`00_Governance/outputs/`). Add the task id to the consolidated "do NOT re-register" list in `session-context.md` — a retirement recorded only in the task's own frontmatter is not enough (incident: `references/incident-history.md` § RETIRE — do-NOT-re-register list incident).
- **RETIRE — ARCHIVE FIRST, DELETE SECOND (hard ordering):** the Cowork Scheduled-sidebar delete is FOLDER-DESTRUCTIVE — it hard-deletes the task's SKILL.md folder along with the registry entry, bypassing the Windows Recycle Bin (OneDrive online recycle bin ~93d is the only recovery). Therefore: (1) MOVE the task folder to the dated `_archive_*` folder, (2) VERIFY the move landed, (3) only THEN delete the registry entry in the UI. Log planned removals to `memory/event_log.md` with the literal token `RATIFIED` + the task id — `registry-membership-probe.py` auto-ratifies such drops (≤14d window) instead of raising a false [ACTION]. Incidents behind this ordering: `references/incident-history.md` § RETIRE — archive-first-delete-second incidents.
- **RETIRE — a RATIFIED-but-UNEXECUTED retirement must be filed in the retire-pending register, in the SAME pass that ratifies it.** A retirement that is decided but not yet executed leaves a registration alive with `enabled:false` — and `enabled:false` is not a retirement, it is a pause that any fleet-wide resume silently undoes. The gap between ratification and execution is often days (a surface handoff, per Rule 4), so the interval must be guarded, not merely documented. Add the entry to `C:\Users\Owner\.claude\maintenance\_state\retire-pending.json` (`{"fleet": "cc"|"lams", "id": "<task-id>", "ratified": "YYYY-MM-DD", "reason": "...", "executeFrom": "native on-device Cowork session"|"Claude Code"}`), and remove it in the pass that actually executes the retirement. `ORA Fleet Pause-Resume Guard` (native, off-fleet, every 6h) reads that file and ALARMS if a listed id is found `enabled: true` on its named fleet — which is precisely what a blanket resume would do. This register is a plain state file consulted by a guard, NOT a registry: writing to it is not a Rule 2 violation and does not retire anything by itself.
- **RETIRE — re-home solely-run producer scripts BEFORE deleting the registry entry:** before retiring any task, grep `maintenance/*.py`, `hooks/*.py`, and every other live task's SKILL.md for scripts this task is the SOLE invoker of. If any are found, re-home them into a surviving task's steps (or explicitly retire the script too, with the same archive-first ordering) BEFORE completing this retirement — never after. A task's own SKILL.md naming what it "replaces" or "folds in" is not proof nothing downstream was missed. Root incident: `references/incident-history.md` § RETIRE — orphaned producer-script incident.
- **RETIRE — id-collision fleet-resolution: never verify by deleting a live task (2026-08-17).** `delete_scheduled_task` carries no fleet parameter — on a same-id collision it resolves to whichever fleet is LOCAL to the calling session (`memory/reference_delete_scheduled_task_resolves_colliding_id_to_local_fleet.md`). The only safe ways to confirm which fleet a session's calls will hit are (a) `list_scheduled_tasks`' own `path` field (see PATH-DISAMBIGUATOR above), or (b) the client identity the host surface itself reports (e.g., Desktop Commander's `currentClient`). **Never** probe resolution with an actual delete, and never target `ora-cowork-heartbeat` or any other dead-man/heartbeat-chain id as a test subject under any circumstance — a "test delete" against a live task is still a delete, and deleting the wrong copy of a genuine id-collision pair is exactly the hazard the archive-first-delete-second ordering above exists to prevent. Root incident: a session correctly declined to test fleet-resolution against `ora-cowork-heartbeat` before retiring the `ora-passed-deal-tracker` LAMS duplicate, for lack of a documented safe method — this bullet is that method.

## Editing a task's SKILL.md CONTENT — a commit is not a live change

UPDATE above covers the registry (cron, enabled, prompt). This section covers the other half: changing the **instructions a task runs by**. Every ORA scheduled task's SKILL.md exists in two places — the fleet store the scheduler actually reads at fire time (`~\.claude\scheduled-tasks\<id>\SKILL.md` for CC/MCP; `OneDrive…\Documents\Claude\Scheduled\<id>\` for LAMS), and the git-tracked copy under `~/.claude`. The registry stores only a `filePath`, so **committing an edit changes nothing about what runs** — the same trap as "a merged PR is not a live deploy" in `CLAUDE.md`'s Release rule. Never report a content fix as done on the strength of a commit.

Procedure, in this order:

1. **Edit in a worktree, never the shared checkout.** `~/.claude` routinely carries 100+ dirty files from concurrent sessions; editing there co-mingles hunks. Gate with `preflight-shared-checkout.py` before committing, passing the sha you actually built on — a stale `--since` returns `HEAD_MOVED`, which reads identically to real contention (`memory/feedback_preflight_stale_since_false_contention.md`). Check `dirty_overlap_foreign` and `competing_claims` in its `RESULT_JSON` before believing a contention verdict.
2. **Make the edit with the Edit/Write tool, not a Bash heredoc/sed/script.** Provenance is recorded only by the Edit/Write hook, so a Bash-written file reads to the gate as having no owner and returns `CONTESTED` against your own work (`memory/feedback_preflight_provenance_needs_edit_tool.md`). Re-applying the identical edit through Edit is the fix; `--force` never is.
3. **Fix every site of the rule you are changing.** A skip rule, routing constant or threshold is typically stated in both a standing-prohibition section and the step that evaluates it. Changing one leaves the spec self-contradictory and an agent free to follow either. Grep the file for the constant before editing, and quote every site back when reporting.
4. **Back up the live file, then propagate.** Copy the live SKILL.md to `SKILL.md.bak-YYYY-MM-DD-<reason>` beside it (`.bak` is gitignored under `scheduled-tasks/`) — Hard Invariant 6, never overwrite a config without reading it first. Then copy the committed version over the live path.
5. **Check line endings BEFORE the copy.** Live files are a CRLF/LF mix (measured 2026-09-22: 16 LF, 6 CRLF of 22), and `core.autocrlf=true` checks the worktree out as CRLF regardless. Write each file in the LIVE file's own style; a style flip rewrites every line and destroys any ability to diff the real change. Confirm `diff --strip-trailing-cr` shows only the lines you meant to touch. `~/.claude/maintenance/propagate-task-spec.py` does steps 4–6 (dry run by default, refuses a mixed-EOL file or an unplanned diff).
6. **Hash-verify.** For CC files, `git hash-object --path <repo path> <live file>` must equal the committed blob — a raw `sha256sum` against `git show` output reports false drift, because git stores LF. For LAMS (not in git), raw sha256 of live vs the edited copy. A copy that silently failed looks exactly like a copy that worked.
7. **Test the changed rule against real data before declaring done.** If the edit changed a matching rule, run it over the actual population it will face plus adversarial cases — for a name-based skip rule, every real counterparty name in that pipeline (must NOT match) and every sentinel variant (must match). Doctrine asserted is not doctrine verified; this is the Done-bar's evidence-before-claim applied to prose specs.

**Do not silently widen a matching rule to make it simpler.** A skip/exclusion pattern must stay anchored and narrow enough that it cannot swallow real counterparty work: a false negative on a genuine tenant, deal or payment is far worse than the false positive the rule exists to stop. Record that reasoning inline next to the rule, so a later "tidy-up" does not undo it. The test-artifact convention is the `ZZ` sentinel — `^ZZ[\s._-]*TEST`, case-insensitive, leading whitespace stripped, anchored prefix only (never a bare `TEST`, which matches real tenants like "TESTA Construction"). Use that same sentinel for any new name-based test exclusion rather than inventing a per-task variant.

**The same live-vs-source split exists for SKILLS, and is not this skill's to fix.** `~/.claude/skills/synced/<uuid>/<skill>/SKILL.md` is what Claude loads; `C:\Users\Owner\ora-skills\<skill>\SKILL.md` is the source of record. They drift (measured 2026-09-19: this skill was v2.21/120 lines live against v2.24/141 lines in source). Before quoting a skill's own doctrine at someone, check which copy you read.

## Bounded pause — the resume is part of the pause, not a follow-up

- **Rule:** a pause with a stated or implied end ("until Friday," "for two weeks," "while I'm out") is NOT complete until its resume task is registered — or confirmed already registered — in the SAME supervised session, on the SAME surface, in the SAME pass. Bulk is the aggravating factor, not the trigger: one task paused "until Friday" fails identically. A genuinely open-ended pause has no resume to register — say that explicitly rather than skipping the step silently.
- **"Pause all routines" is FLEET-AMBIGUOUS — resolve it before acting.** The instruction names no fleet, so enumerate BOTH registries, state which are in scope, and register one resume per fleet in scope. A resume task cannot reach the other fleet's registry (`update_scheduled_task` resolves session-local — see PATH-DISAMBIGUATOR). Reporting "N tasks paused" after touching one fleet reads as complete and is the exact shape of the root incident below.
- **A resume must EXCLUDE every retire-pending id.** Read `maintenance/_state/retire-pending.json` before building any bulk resume's id list, and carve those ids out explicitly — they are `enabled:false` because they are on their way OUT, not because they are paused. A resume that re-enables one silently reverses a ratified retirement, and on a same-id cross-fleet pair it also resurrects the duplicate the retirement existed to remove. Say in the same turn which ids you carved out and why. (The guard alarms on this within 6h, but an alarm is the backstop, not the control.)
- **Never blanket-pause the detectors.** `ora-cowork-heartbeat` (dead-man chain → Notion `35c6ecd8…` → GitHub watchdog) and `automation-health-monitor` are what would otherwise surface a failed resume — and BOTH live on LAMS, so a LAMS-wide pause silences the detector for its own failure. Either carve them out of the pause, or state plainly in the same turn that the dead-man chain and health monitor are down for the window and will not report the gap.
- **RESUME-TIME COLLISION CHECK — pick the resume time off the fleet's own cron table, not off the clock (NEW v2.15, 2026-08-24).** A resume time is not a scheduling detail; it decides which of the paused tasks get their last slot back and which lose it permanently. Before committing a `fireAt`, list every paused task whose cadence slot falls in the **last 2 hours before** the proposed resume, and for each one make an explicit call:
  - **Make-up-able** — most sweeps, monitors and nudges re-scan current state on their next fire, so a skipped slot costs latency, not content. Note it and move on.
  - **Period-bounded — the output is GONE if the slot is missed**, because the deliverable only ever covers the period it fired in: week-closeouts, month-end ledgers, inbox windows, daily briefs, EOD ledgers. For these, move the resume **earlier than the slot**, not later. Minutes are enough; the cost of resuming 45 minutes early is nil, and the cost of resuming 30 minutes late is one permanently missing deliverable.
  State the check and its outcome in the same turn as the pause, even when nothing collides — "no period-bounded slot falls in the 2h before the proposed resume" is a real assertion and takes one line.
  Root incident (a round-number resume landed 30 min after `ora-friday-closeout`'s slot; that week's closeout was lost for good): `references/incident-history.md` § Resume-time collision.
- **Verify before reporting done:** `list_scheduled_tasks` shows the resume task for EACH paused fleet — id, `fireAt` (a one-time resume carries `fireAt`, not `cronExpression`/`nextRunAt`), and an id list matching exactly what was paused — pasted in the SAME response that reports the pause complete. If the current surface cannot reach the MCP tools for either half, STOP per Rule 1 and name which half is missing; never report "N tasks paused" without either a registered resume or an explicit flag that none exists.
- **⛔ AN UNATTENDED RESUME WILL NOT COMPLETE ON ITS OWN (NEW v2.23, 2026-09-12, root cause of OI-273).** The Claude Desktop scheduled-task runner does **not** auto-approve `mcp__scheduled-tasks__update_scheduled_task` in an unattended run.
  - It logs `Not auto-approving "mcp__scheduled-tasks__update_scheduled_task"` and blocks on a prompt with no "always allow" option. Neither the `settings.json` allow rule nor `bypassPermissions` pre-approves it. Bash in the same run IS auto-approved. A partially-approved resume still reports `succeeded` in `list_task_runs`. Evidence (09-11 case, main.log, session record): `references/incident-history.md` § Unattended resume.

  So **the only working path is an ATTENDED resume**, and it must be arranged at pause time and stated in the same turn:
  - Tell Gabriel the resume fires at `fireAt` and will stop for approval. Someone must open that run in the Desktop app and approve each `update_scheduled_task` call.
  - Keep the resume batched: all ids issued in as few turns as possible, so approvals are quick.
  - Alternatively, skip the scheduled resume and have Gabriel ask a live session to "unpause all routines" at the chosen time.
  - A fleet-wide pause can therefore never resume while Gabriel is away, so plan pause length accordingly.

  **Detection backstop (slow, not a timely alarm):** `pause-resume-guard.py` `find_incomplete_resumes()` (OI-273) alarms when a fired resume's listed ids are still disabled 30 min to 72h after firing. It reads live `enabled`, not run status or markers, so a `succeeded` partial resume can no longer pass silently forever. The guard runs on a fixed 6h cycle, though, and its slots can be skipped silently (on 09-11 no run fell in 20:01–20:45Z and the 20:20 ET slot never launched). **Expect detection hours late. After any resume, verify with `list_scheduled_tasks` rather than waiting for this alarm.**
- **RECORD THE PAUSE WINDOW — same pass, right after the resume is verified (NEW v2.22, 2026-09-12).** Run `python ~/.claude/maintenance/_shared/pause_windows.py capture` and paste its `held` counts for EACH paused fleet in the same response. They should equal the paused-id counts. This writes `maintenance/_state/fleet-pause-windows.json`, the durable record that `health-guard-beacon.py`, `fleet-status.py`'s missed-cycle check and `ora-health-guard` C.0b subtract from gaps. `fleet_pause.py` only knows about a pause *while it is live*, so without this record every check that looks back across the pause alarms on it. `capture` records **observed registry state, not parsed text**. A recurring task is *held* at a capture only if it is actually **disabled** AND an enabled, not-yet-fired resume task names its id, where that resume names **≥3 currently-disabled tasks**. For a 1–2 task pause, hand-record it with `pause_windows.py record --note "<evidence>"`. A hold longer than 21 days is voided, not excused. Carve-outs (left enabled) and efficacy checks (which disable nothing) can therefore never be counted, whatever their wording. A task re-enabled early, or one that ran between captures, closes its own interval. Right after pausing, `capture` should list your paused ids under `held`; if it doesn't, the resume isn't registered or doesn't name them. Intervals begin at the FIRST capture that sees the task held, so capturing at pause time is what makes the window start on time. **If the capture does not list your window, the resume SKILL.md is malformed — fix that, don't hand-record around it.** The native `pause-resume-guard.py` also re-runs `capture` every 6h as the backstop, so a forgotten step costs at most one guard cycle, never the record itself. It replaces the hand-written `*_FleetPause_RestoreLedger*.json`. Root incident: `references/incident-history.md` § Pause-window record.
- **A resume does NOT re-stamp `[MODEL:]` dates.** Re-enabling returns a task to tag scope, which makes it DUE for a currency check — it is not itself an observation. A resume task must not bump `checked`/`set` dates on the tasks it flips; that fabricates a verification (`memory/feedback_verified_null_vs_inferred_null.md`). This QUALIFIES the PAUSE bullet's "re-tag in the same pass" above: that binds a hand re-enable where the model IS observed, not an automated bulk resume.
- **ONE-TIME EFFICACY-CHECK CHECK — enumerate overlapping one-time tasks before committing the pause (NEW v2.17, 2026-08-24).** A bounded pause doesn't only cost the paused tasks their own slots — it also poisons any one-time (`fireAt`) task whose MEASUREMENT WINDOW overlaps the pause, even though that one-time task is itself never paused. An efficacy/retime check that counts "days delivered" from the send log cannot distinguish a disabled task from a genuine miss (`memory/reference_bounded_pause_voided_overlapping_efficacy_checks_2026-08-21.md`). Before committing any bounded pause: list every one-time task on the affected fleet(s) whose `fireAt` falls between the pause start and the earliest plausible resume, and for each one that reads status/delivery history over a window the pause will fall inside, make an explicit call:
  - **Defer** — push its `fireAt` to after the resume, so it measures a live fleet. Preferred when the check has no independent value tied to its original date.
  - **Knowingly void** — if the date is fixed for a reason that outlives the pause (e.g. a hard reporting deadline), leave `fireAt` as-is but record in the SAME pass, in `event_log.md` or the pause's own resume-ledger entry, that its window will include a pause and its verdict must be read against `enabled` history, not the send log alone.
  A pause is not complete with only its own resume registered — an overlapping one-time check left neither deferred nor flagged is a live footgun for the next efficacy ruling. Root incident: `references/incident-history.md` § Voided efficacy checks.
- Root incident (2026-08-17) + the verified fleet asymmetry it left behind: `references/incident-history.md` § Bounded pause.

## Concurrent-writer check (before any registration/recovery/bulk-retire session)

Registering, retiring, or bulk-recovering tasks touches shared state exactly like the `ora-skills` git repo and `event_log.md` — the same claim-first-write-second discipline applies.

**PRIMARY CHECK (2026-07-12) — `session_info list_sessions`:** before the first write of any registration/retime/retire pass, call `list_sessions` and scan for another session that is `running` or recently active with an overlapping title (task ids, "scheduler," "LAMS," or the same skill name) — that IS a live sibling, not a maybe. `registry-membership.log` does NOT catch this class of collision — it only logs task adds/drops, not cron edits or same-value re-pins, so a same-value collision (two sessions independently arriving at the identical correct cron) leaves no trace there at all. If a live sibling is found: stop, compare notes in-conversation if possible, and agree who applies the write before either session calls `update_scheduled_task` or `create_scheduled_task` again.

**SECONDARY SIGNAL — `registry-membership.log`:** still worth checking for id-level adds/drops (catches the 2026-07-08 duplicate-registration class below), but treat a clean log as inconclusive, not as proof no one else is active — it has a blind spot for cron-only edits.

Two incident precedents motivate the checks above (duplicate-id registration, and a same-day event_log.md write collision from an idempotent concurrent edit) — full narrative: `references/incident-history.md` § Concurrent-writer incidents.

If you discover mid-task that another session is concurrently active, stop, compare notes, and agree who owns which fleet before either of you registers or deletes anything further.
