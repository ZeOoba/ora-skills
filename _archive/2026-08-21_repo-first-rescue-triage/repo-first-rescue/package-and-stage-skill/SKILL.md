# package-and-stage-skill

Companion to `ora-skill-store-drift-check`. Turns a "repo newer → re-upload to Cowork/claude.ai needed" finding (or any repo skill edit that must reach the platform) into one staged, one-click installer.

**Source of truth = the git repo** `C:\Users\Owner\ora-skills\<skill>\SKILL.md`. The AppData runtime cache is a read-only mirror that rebuilds from the platform after import — never write it directly (2026-06-11 Roaming-alias clobber incident).

**Registration is human-gated.** This skill packages and stages; it does NOT install. A session cannot write the skill registry — Gabriel clicks **Save skill** (or Settings → Capabilities) on the staged `.skill`.

**A publish/unpublished claim in a Rev-log or advisory must be freshly sourced, never carried forward (added 2026-08-15).** Motivated by a Rev 5 log that recorded capex-budgeting as Gabriel-confirmed unpublished as of 2026-08-09, while the Code catalog separately carried a 2026-08-12 update — nothing had re-checked live state between the two records, so a Rev 10 pass had no way to tell which was current without a manual walk. Before ANY session writes a sentence asserting a skill IS or IS NOT currently published/enabled, run `python tools\skill_drift_report.py --publish-status <skill ...>` and cite its verdict + `checked_at` timestamp inline. Do not cite a prior Rev-log's claim, memory, or the frontmatter version token alone as evidence of current publish state — only a fresh run of this flag (or, from a Cowork session, a live `ListSkills` account call) counts as verification. This is a doc-only convention, not a code gate: nothing blocks an un-cited claim from being written, so the discipline is on whoever authors the log entry.

## Input

- **Entry point A (package + stage, default):** one or more skill names. Default: the skill(s) the latest drift-check comment flagged **repo-newer**, or the skill(s) returned by `python tools/pending_reimport.py candidates` — the UNION of the post-commit PENDING-REIMPORT ledger (written by `tools/hooks/post-commit` on every commit that changes a skill's packaged content or the shared `target-markets.json`) and a fresh full repo-vs-cache SHA256 sweep across every packageable skill. **Do not call `pending_reimport.py list` alone as the candidate source** — the ledger only records skills touched by a commit *after* the hook existed (added 2026-07-16); drift that predates the hook, or a hook run that failed/was bypassed, never reaches it, and a session that trusts `list` as exhaustive silently skips those skills' STEP 1b precheck entirely (root-caused 2026-07-16: acquisition-underwriting v4.1 and this skill's own v1.5 both predated the hook and were invisible to `list`). `candidates` is read-only and never mutates the ledger; a skill it surfaces that only came from the sweep (no ledger line) is exactly the retroactive-blindness case this exists to close. Run `python tools/pending_reimport.py backfill` to persist sweep-only findings into the ledger itself when a durable record is wanted, not just a one-off union.

  **Surface boundary — a Cowork-bash `candidates` run can't see the runtime cache (found 2026-08-03).** `CACHE_ROOT` is a native-Windows AppData path with no mount inside Cowork's `mcp__workspace__bash` sandbox. When `pending_reimport.py candidates`/`sweep_drift` runs from there, `skill_drifted()` cannot tell "the cache directory doesn't exist" apart from "the sandbox can't see it" and short-circuits to "not drifted" either way — so a Cowork-bash run reports **zero cache-side drift regardless of ground truth**. (This is separate from, and not fixed by, the same-day `_win_long()` fix that stopped a POSIX-context path crash in this same tool — that fix makes the repo-vs-repo/shared-dep checks run cleanly from Cowork bash; it does not make the cache-side comparison trustworthy from that surface.) Treat a Cowork-bash `candidates`/`sweep_drift` result as **repo-side-only**: the ledger union and shared-dep direction checks stay valid, but do not treat "no candidates" as verified absence of cache drift. Before proceeding on a Cowork-bash "no candidates" result, either re-run Entry point A's candidate-source step from a Code-surface Windows shell, or verify cache state independently (the Read tool reaches the cache path via host access, unlike this sandbox's bash). Same category of gap and same fix pattern as step 7's Cowork/.claude surface boundary below — don't trust a Cowork-bash result for anything that needs real host filesystem access; hand off to Code instead.
- **Entry point B (pre-packaged install):** explicit path(s) to already-built `.skill` file(s) handed off by an earlier session or another surface, with instruction NOT to repackage. Runs the integrity pre-check below, then steps 5–8 only.

## Entry point B — pre-packaged install (steps 5–8 only)

When handed pre-built `.skill` files, do NOT re-run steps 1–4 and do NOT repackage — the handoff's premise is that packaging already happened. But never install on trust alone; a pre-built package can go stale between build and click (precedent: step 2's entire reason for existing), or can turn out never to have been built at all (2026-08-13, below). **The handoff's premise is a claim, not a fact — item 1 is what tests it, and it runs before anything else.**

**Bridge-first freshness screen (2026-08-15) — run this ONE cheap check before the per-package pre-check, whenever the Desktop Commander bridge is live.** Don't assume every named package still needs installing just because it was handed off that way. Cross-check two independent, fast signals: (a) a live `ListSkills` account call — does the target skill's description string already show the cited version, enabled; and (b) a Desktop-Commander SHA256 compare between the skill's AppData `skills-plugin` cache copy (locate via `Get-ChildItem … -Recurse -Directory -Filter '<skill>'` under `%APPDATA%\Claude\local-agent-mode-sessions\skills-plugin`) and its current repo copy. Both matching means the click already happened — in this session or an earlier unlogged one — so skip the rest of the per-package pre-check, `present_files`, and any Save-skill ask for that package entirely; go straight to Step 7's "already in sync" logging instead of presenting a redundant button. Only a package that DOESN'T clear this screen proceeds to the full per-package pre-check below. Proven live 2026-08-15: this exact check caught `package-and-stage-skill` v1.17 already installed moments before a second, redundant Save-skill ask would have gone out for it alongside a genuinely-pending `automation-health-monitor` v1.5 — cheaper and faster than either a hand-off-and-wait or the main.log Delta-gate dance in step 2 (which is repo-side and doesn't apply to Entry point B anyway). Not a substitute for the per-package integrity pre-check on anything that fails to match — that one still runs in full, since a fast screen finding "maybe already installed" is not the same guarantee as "verified exists/entries/freshness."

Replace steps 1–4 with this integrity pre-check, per package (for whichever packages the bridge-first screen above didn't already resolve):

1. **Exists — assert it, never assume it (hardened 2026-08-13).** The `.skill` file is at the stated path. This is a hard assertion on every named path, run FIRST and never waived on the strength of a circumstantial-sounding handoff (a real commit SHA, a named packaging tool, a plausible `_staging` path). If the stated path is empty or absent, sweep before concluding: the session's uploads dir, `ora-skills\_staging\` (including its dated subdirs), `Downloads`, `Desktop`, and a filename search across `C:\Users\Owner`.

   **If no package is found anywhere → MISSING, not stale. Different finding, different remedy.**
   - **Stale** = a package exists but no longer matches the repo → REJECT and route back to Entry point A to *re*build.
   - **Missing** = no package was ever built → the handoff premise is false, and a "do NOT repackage" instruction does **not** bind, because there is nothing to re-package. Proceed to Entry point A and build the FIRST package, stating plainly that the premise failed and why. Do not stop and ask; do not let the instruction's letter block its own purpose. Then run steps 0–8 in full — in particular step 0 (`plugin_of`) and step 1 (git-clean + `git log -1`), which the Entry point B path would otherwise have skipped entirely.
   - Either way, **surface the discrepancy explicitly** rather than quietly repairing it. A claimed packaging run that never happened is a write-side reporting failure; an existence check that silently self-heals destroys the only evidence of it.

   **Why this is asserted rather than assumed (2026-08-13).** A session was dispatched to install a pre-built `dirty-tree-triage.skill` "already built and packaged from `C:\Users\Owner\ora-skills\dirty-tree-triage` via `tools/package_skills.py`, commit 3eabd33, pushed to origin/main." Every verifiable part of that was true — `3eabd33` was real, was HEAD, and had added the skill's two source files — but no `.skill` artifact existed anywhere on the machine: not attached to the session, not in `_staging` (which held ~100 other packages), not in `Downloads`/`Desktop`, and absent from a filename sweep of `C:\Users\Owner`. Nothing downstream of packaging can catch this: items 2–4 (entries, freshness, stage) all presuppose a file to open, and step 2's v1.13 rewrite hardened only the READ side — don't trust a hash match as proof of install. This item is the write-side counterpart, and the only check in the skill that can detect a packaging step reported but never run.
2. **Entries.** List zip entries: forward-slash paths, expected file set (`SKILL.md` plus any `references/`/`templates/`/`scripts/` files and, for `SHARED_ROOT_DEPS` consumers, the injected shared dep).
3. **Freshness.** SHA256 the packaged copy of each shared root dep against the CURRENT repo-root copy (and, where the handoff claims SKILL.md currency, spot-check it against the repo skill dir). EOL rule applies: raw mismatch → CRLF→LF-normalized re-compare → only a normalized mismatch is real. A stale package is REJECTED — route back through Entry point A to rebuild; never install a package that no longer matches the repo. Stale is not the same finding as missing — see item 1 for the distinction and its different remedy.
4. **Stage.** Copy the verified `.skill` into the current session's outputs directory (present_files needs it there to render the Save-skill button).

Then proceed with steps 5–8 unchanged: surface via `present_files`, route multi-file skills to the Cowork Save-skill button, verify the runtime cache post-install, and log the confirmed click to `event_log.md`. First exercised 2026-07-16 (target-markets.json refresh: 4 pre-built consumer-skill packages installed this way).

## Procedure

0. **Plugin-membership routing — the WRONG-target gate (both entry points, run FIRST).** Before treating a skill as a standalone `.skill`, check whether it is a member of a version-controlled plugin bundle: `python -c "import sys;sys.path.insert(0,'tools');from package_skills import plugin_of;print(plugin_of('<skill>'))"` (or read `plugins/*/plugin-build.json`). If it returns a plugin name, the skill does NOT install via a standalone Save-skill click — that lands a shadow copy while the plugin's loaded copy stays stale (proven 2026-07-16: deal-retirement / submarket-spatial-analysis live only in the `ora-operations-extensions` bundle). **STOP the standalone path** and instead rebuild the plugin: `python tools/build_plugin.py <plugin> "<session outputs dir>" [--bump patch]`, `present_files` the resulting `.plugin`, and on confirmed install verify the plugin cache mirror (`…\rpm\plugin_<id>\skills\<skill>\`, not the standalone skills-plugin cache) before clearing the ledger. **The repo side of that byte-comparison is the skill's canonical top-level dir** — `C:\Users\Owner\ora-skills\<skill>\SKILL.md`, NOT `plugins\<plugin>\skills\<skill>\`: the bundle has no per-skill source tree; `build_plugin.py` assembles each member from its top-level dir at build time. Comparing against a `plugins/…/skills/…` path silently resolves to a non-existent file and reads as a FALSE mismatch (2026-07-17). The post-commit ledger already tags plugin members with `plugin: <name> | remedy: rebuild plugin …`; honor that tag. Only if `plugin_of` returns `None` do steps 1–8 (standalone) apply.
1. **Confirm source.** `C:\Users\Owner\ora-skills\<skill>\SKILL.md` exists. Run `git status --short -- <skill>/`; if dirty, STOP and commit first — repo-first rule: the repo leads the platform, never the reverse. Record the last commit (`git log -1`).
2. **Hash-compare the runtime cache for CONTENT, then gate the short-circuit on `main.log` — never on the hash alone (rewritten 2026-08-13).** Before packaging, hash-compare every file in the repo skill dir against its counterpart at `…\local-agent-mode-sessions\skills-plugin\<outer-UUID>\<inner-UUID>\skills\<skill>\` (SHA256 via PowerShell `Get-FileHash`; same file count, same names, same hashes). **Normalize line endings before declaring drift:** the platform import stores LF while git autocrlf gives Windows working copies CRLF, so a RAW hash mismatch on a `*.md`/text file may be content-identical. On any raw mismatch, re-compare with CRLF→LF-normalized, trailing-whitespace-trimmed content; only a normalized mismatch is real drift — a raw-only mismatch counts as content-IN-SYNC. **But a content match is no longer sufficient to STOP.**

   **Why the hash alone stopped being trustworthy.** `tools/sync_appdata_mirror.py` (pre-commit Check 4, live 2026-07-26) copies every staged skill's shipped files straight into every AppData mirror directory that ALREADY EXISTS for that skill, on every commit — before this step ever runs. Once a skill has been installed at least once (its mirror dir exists), the repo-vs-cache hash is therefore guaranteed to match the just-committed content by construction, regardless of whether the platform account has actually re-imported anything since. This step, followed literally through v1.12, would always certify a freshly committed skill as “already installed.” Evidence (2026-08-13, commit d03fe62 batch): before any Save-skill click, all five skills already read byte-identical to the repo, with `lease-abstraction-pipeline`'s cache mtime landing in the SAME SECOND as the commit — the old Step 2 would have stopped the batch dead and reported five non-installs as done. `_staging/PENDING_REIMPORT.md`'s own header has stated the correct doctrine since it was written and this step simply never conformed to it: *“Hash vs repo — confirms WHAT installed, never WHETHER.”* Only `AppData\Roaming\Claude\logs\main.log`'s non-zero `Delta: N to download` → `Sync complete: N downloaded, 0 failed` for this skill, at a timestamp no earlier than the skill's current repo commit, establishes that an install actually happened; cache mtime against a pre-click baseline is the second-line signal; hash-vs-repo is third and content-only, per the ledger's own priority order.

   **Revised gate:** STOP (skip packaging) only when BOTH hold: (i) `main.log` shows a non-zero `Delta:` → `Sync complete: N downloaded, 0 failed` cycle for this skill at or after its current repo commit's timestamp, AND (ii) the skill has no pending line in `_staging/PENDING_REIMPORT.md` (`pending_reimport.py list`/`candidates`). Only then log the one-line `event_log.md` “already in sync” note (“`<skill>` already in sync at v`<X.Y>`, no reimport needed”) and stop. In every other case — including a hash MATCH with no corroborating `main.log` cycle, which is evidence the mirror-sync hook ran, not evidence of installation — proceed to step 3. **Shared root deps are part of the content comparison.** For skills listed in `tools/package_skills.py` `SHARED_ROOT_DEPS` (as of 2026-08-15: acquisition-underwriting, daily-brief, deal-comparison, market-monitor — all sharing repo-root `target-markets.json`; `rent-comp` was a consumer here until its 2026-08-05 retirement removed it from the dict), the repo skill dir deliberately does NOT contain the dep; the packager injects it from the repo root at package time (see the skill dir's `PACKAGING-NOTE.md`). The pre-check must therefore hash-compare the REPO-ROOT copy of each shared dep against the cache's copy — a skill-dir-only comparison silently skips the data file entirely, and does NOT copy the dep into the skill dir to "fix" a perceived gap (2026-07-16: that produced a duplicate zip entry). Discovered 2026-07-16: the cache's target-markets.json was substantively stale (contradicted Notion ground truth on the Pipeline 'Market' rename) and only an unprompted diff caught it. This step exists because a 2026-07-15 session was dispatched to reimport two skills already packaged, staged, and installed by an earlier *unlogged* session — the handed-off premise ("hasn't reached the runtime yet") was stale, and only a hash check caught it before wasted packaging and a needless Save-skill ask.

**A shared-dep hash mismatch is not automatically "reimport needed" — check direction first.** A raw hash mismatch on a `SHARED_ROOT_DEPS` file means either the cache is a stale older version (fix = repackage + reimport) OR the cache holds runtime-only content that was never committed to the repo (fix = commit the cache content back to the repo FIRST — reimporting would DOWNGRADE the runtime, reproducing the 2026-07-16 target-markets.json episode). Never assume direction by eye. Before proceeding to step 3 on a shared-dep diff, run `python tools/pending_reimport.py shared-deps` (or read the direction-aware advisory block `candidates` already appends after its primary candidate list) and check the label for the affected dep/skill pair: `REPO-AHEAD` or `MISSING-IN-CACHE` → proceed to package + reimport as normal; `CACHE-AHEAD` or `DIVERGENT` → **STOP**, do not repackage that shared dep — surface the runtime-only content to Gabriel so it can be committed to the repo (CACHE-AHEAD) or manually reconciled (DIVERGENT) before any reimport touches it; `UNKNOWN` → git history was unavailable, verify the direction by hand before proceeding.
2a. **Pre-flight frontmatter gate — run BEFORE packaging, on every path (added v1.20).** Two frontmatter defects make the platform importer reject a `.skill` with **no error text at all** — the Save-skill click simply does nothing. No toast, no log line, no non-zero exit, nothing to diagnose from:

    - `description` longer than **1024 characters**
    - frontmatter `name` not byte-identical to the containing directory name

    On the Windows repo path `tools\package_skills.py` already catches both and prints `description N/1024 OK` — which is exactly why this has never bitten a host-packaged skill. **The gate exists for the paths where the packager cannot run:** a skill authored inside a cloud Cowork session with no Desktop Commander bridge, a hand-built `_staging` package, or any `.skill` assembled without the repo checked out. There, nothing validates the frontmatter and the first symptom is Gabriel reporting "can't save the skill." Confirmed 2026-08-17 (`listing-agreement-qc` v1.0, authored cloud-side: description 1220/1024, silent rejection, two build cycles lost before the cap was suspected).

    Assert it yourself — no repo, no host, no Desktop Commander:

    ```python
    # preflight.py <skill-dir>   ->   exit 0 clean, exit 1 with the reason
    import os, re, sys
    root = sys.argv[1].rstrip("/\\")
    want = os.path.basename(root)
    t = open(os.path.join(root, "SKILL.md"), encoding="utf8").read()
    fm = re.match(r"^---\n(.*?)\n---\n", t, re.S)
    errs, d = [], ""
    if not fm:
        errs.append("no YAML frontmatter block")
    else:
        b = fm.group(1)
        nm = re.search(r"^name:\s*(\S+)\s*$", b, re.M)
        dm = re.search(r'^description:\s*"?(.*?)"?\s*$', b, re.M | re.S)
        if not nm:                     errs.append("no name:")
        elif nm.group(1) != want:      errs.append(f"name {nm.group(1)!r} != dir {want!r}")
        if not dm:                     errs.append("no description:")
        else:
            d = dm.group(1)
            if len(d) > 1024:          errs.append(f"description {len(d)}/1024 - over by {len(d)-1024}")
            if "\n" in d:              errs.append("description spans multiple lines")
    print("\n".join("FAIL: " + e for e in errs) if errs
          else f"OK  name={want}  description={len(d)}/1024")
    sys.exit(1 if errs else 0)
    ```

    Assert the same discipline on the **archive** before surfacing it, because a hand-built zip also skips the entry rules step 3 otherwise delegates to the packager: every entry uses forward slashes (backslash entries → importer rejects, APPNOTE 4.4.17.1, ruling 2026-06-11), no directory records, and `<skill>/SKILL.md` present at the expected path. A hand-rolled `zipfile.ZipInfo` write with explicit forward-slash arcnames satisfies all three; `shutil.make_archive` and PowerShell `Compress-Archive` do not.

    **Report the numbers, not a verdict.** State `description N/1024` and the resolved `name`/dir pair in the packaging report the same way the sanctioned packager does, so a silent rejection downstream can be ruled out by reading the report instead of rebuilding.

3. **Package — sanctioned tool ONLY.** Via Desktop Commander on Windows: `python tools\package_skills.py "<session outputs dir>" <skill ...>`. NEVER PowerShell `Compress-Archive` (writes backslash zip entries → importer rejects per zip-spec APPNOTE 4.4.17.1; ruling 2026-06-11). The tool validates frontmatter (`name` == dir, `description` ≤ 1024 chars), scans named-count headers across every `*.md`, and asserts forward-slash entries. A non-zero exit is a real defect — surface it verbatim, do not work around it. **Host-shell discipline (2026-08-14, generalized 2026-08-15) — SKILL-WIDE, not just this step.** Every Desktop Commander PowerShell invocation ANYWHERE in this skill — packaging here in step 3, but just as much the verification/hash-compare, `main.log` reads, `append-event-log.py`, and `pending_reimport.py clear` calls in step 7 — that uses `$` variables or spans multiple statements goes in a `.ps1` file run via `powershell -NoProfile -ExecutionPolicy Bypass -File <path>`, never an inline `powershell -Command` one-shot. `$` tokens are stripped in transit and the command arrives mangled or throws a parser error. Originally scoped to this step alone (2026-08-14) after it recurred twice in one packaging session; re-scoped skill-wide 2026-08-15 after it recurred a further THREE times in one session's step-7 verification/logging work — none of them packaging — proving the failure mode isn't specific to `package_skills.py` invocations, it's specific to inline `-Command` itself. Default to the `.ps1`-file pattern for every DC PowerShell call in this skill; do not attempt inline first and fall back only on error.
4. **Stage.** Emit the `.skill` into the current Cowork session's outputs directory (the one that maps to `/mnt/user-data/outputs`). **Cloud Cowork sessions (2026-08-14):** the packager runs on the Windows host and cannot write a cloud session's outputs directly — emit to `ora-skills\_staging\<date>\`, then transfer into the session: connect `C:\Users\Owner\ora-skills` as a session folder and `device_stage_files` the artifact (folder grants are per-session — request once at session start), falling back to a base64 bridge with end-to-end SHA256 verification only when no folder can be connected. Either way the byte-identity of the staged copy is asserted by hash, never assumed.
5. **Surface.** `present_files` the `.skill` → renders the **Save skill** install button.
6. **Route multi-file skills to Cowork, not desktop Settings.** If the skill has ANY file beyond `SKILL.md` (a `references/`, `templates/`, or `scripts/` dir), tell Gabriel to install via the Cowork **Save skill** button, not Settings → Capabilities → Skills. **Confirmed bug (reproduced twice, 2026-07-11):** the desktop Settings single-`.skill` upload path silently drops subfolder files on import — `SKILL.md` lands, `references/*.md` etc. do not — while the Cowork install path installs the full package correctly. Single-file skills (no subfolders) are unaffected by either path.
7. **Verify post-install, then log the click — not just the commit.** After Gabriel confirms installation, check the AppData runtime cache mirror contains every file the packaged `.skill` did — not just `SKILL.md`. If any file is missing, the install silently failed (most likely the desktop-Settings bug above); tell Gabriel to re-install via Cowork instead of assuming the drift is closed. Once verified, log the confirmed install to `event_log.md` in the same pass: skill name(s), version, confirming timestamp, and that this was Gabriel's **Save-skill click**, not merely the upstream repo commit. A repo commit is evidence the fix was authored; it is not evidence anyone installed it — that gap (a click that happened but was never logged) is exactly what caused the 2026-07-15 redundant-dispatch near-miss step 2 now catches on the read side. This log entry is what lets a future step-2 pre-check, or a drift-check, trust "already installed" from the log instead of re-deriving it from a hash comparison every single time. **Then clear the skill from the post-commit ledger** so it stops reading pending: `python tools/pending_reimport.py clear <skill>`. The verified cache re-sync is the ONLY thing that clears an entry — a commit sets it, a confirmed install clears it.

   **Surface boundary (Cowork sessions cannot write `event_log.md` directly).** `event_log.md` and `append-event-log.py` live under `C:\Users\Owner\.claude\...`, a Code-only surface. Confirmed 2026-07-27: a Cowork session attempting `request_cowork_directory` on `.claude` itself, on `.claude\maintenance`, and on the `.claude\projects\...\memory` subpath was rejected on all three — every path under `.claude` is fail-closed to Cowork mounting, no partial carve-out exists. When this skill runs in a Cowork session, step 7 cannot execute the log write in-session: prepare the exact `event_log.md` entry line(s) (skill name, version, confirming timestamp, "Save-skill click" language) and hand them to Gabriel to run through `append-event-log.py --entry-file <path>` (never stdin — cp1252/encoding gotcha) from a Code session. Do not treat step 7 as complete, and do not clear the post-commit ledger, until that Code-side write is confirmed — a prepared-but-unexecuted log entry is exactly the "click happened but was never logged" gap this step exists to close. On the Code surface itself, no such boundary applies and step 7 runs as originally written, in-session.

   **Bridge carve-out (2026-08-14) — the boundary binds only when the session has no path to the Windows host.** A Cowork session with the Desktop Commander bridge (`mcp__remote-devices__Desktop_Commander__*` tools live) reaches `C:\Users\Owner\.claude\...` natively — the 2026-07-27 finding was about `request_cowork_directory` mounting, not about host access in general — so step 7 runs IN-SESSION over the bridge: `python C:\Users\Owner\.claude\maintenance\append-event-log.py --entry-file <path>` (never stdin — cp1252/encoding gotcha). Two hard rules learned live: (a) the entry file MUST start with a dated `## YYYY-MM-DD -- <title>` header or the appender exits 1; (b) confirm the append's exit 0 BEFORE running `pending_reimport.py clear` — never batch the append and the clears into one script (2026-08-14: a batched close-out cleared the ledger while the append had failed on the header rule, briefly inverting this step's ordering; caught and re-run same session). The prepare-and-hand-to-Gabriel path above remains the fallback ONLY for Cowork sessions with no Desktop Commander bridge.

   **Never trust a pre-staged `_staging` draft without a fresh verify — and archive it once its package is confirmed installed (2026-08-16).** `_staging/<date>/` is a shared scratch folder that many concurrent sessions write into on the same date, and a later session can find pre-written log-entry drafts, hash claims, or "already in sync" verdicts sitting there from an earlier, unidentified run. Do not reuse any of that content on trust, no matter how plausible the wording or how real the cited hashes look. **Proven the same day:** `_staging/2026-08-16/` held two mutually contradictory drafts for the same repo-architecture-review install — one roughly matched what actually happened, the other claimed the skill was "already installed by a concurrent session" before packaging had even run, which directly contradicted the installing session's own pre-packaging cache sweep (empty) — yet that false draft had already been appended into `event_log.md` itself as if it were fact. Re-derive `plugin_of`/git-log/hash/cache-state facts fresh for this session's own entry every time; a draft in `_staging` is unverified scratch, never evidence. Once a package's install is confirmed, logged, and its `PENDING_REIMPORT` entry cleared, move that package's now-spent `_staging/<date>/` artifacts (build scripts, superseded or false drafts, intermediate patch/diff files) to `_archive/<date>_<context>/` — never delete (Hard Invariant 6) — so the next session's `_staging` scan isn't left sorting live work from stale drafts by eye.
8. **Hand off.** Tell Gabriel: click **Save skill** (or, for single-file skills only, Settings → Capabilities) to register. After import the runtime cache re-syncs to the new version — that closes the drift; a re-run of `ora-skill-store-drift-check` should then read IN-SYNC.

## Done =

hash pre-check run first, every time, for CONTENT only — the short-circuit itself gated on a corroborating `main.log` non-zero Delta/Sync-complete cycle (plus no pending ledger line), never on the hash match alone · raw-hash mismatches re-checked EOL-normalized before being called drift · shared root-dep files (`SHARED_ROOT_DEPS`) hash-compared from the REPO ROOT, never copied into the skill dir · pre-flight frontmatter gate run and its `description N/1024` + `name`/dir pair REPORTED before packaging, on every path including cloud-authored and hand-built packages · packager exited 0 with `description N/1024 OK` + `N entries OK` + a forward-slash entry list · `.skill` present in session outputs · repo path git-clean (or dirty surfaced and committed) · `present_files` called · multi-file skills routed to Cowork install · post-install file-count verified against the packaged `.skill` · a `event_log.md` entry recorded once install is confirmed, naming the Save-skill click itself (not just the repo commit), the append's exit 0 confirmed BEFORE any ledger clear · host-shell PowerShell run via `.ps1` script files, never inline `-Command` · no write to the runtime cache · no email / external send · no pre-staged `_staging` draft (log entry, hash claim, verdict) reused without a fresh verify this session · a confirmed-installed package's spent `_staging` scratch archived to `_archive/<date>_<context>/`, never deleted. Entry point B: a bridge-first freshness screen (`ListSkills` + AppData cache-hash) run first when the Desktop Commander bridge is live, resolving any package already installed without a redundant pre-check/present_files/Save-skill ask · for whatever doesn't clear that screen, the four-item integrity pre-check (exists · entries · freshness vs current repo · staged to outputs) run per package before `present_files`, existence ASSERTED first and never inferred from the handoff, no repackaging, stale packages rejected back to Entry point A, missing packages routed to Entry point A as a FIRST build with the false premise stated plainly.

## Why a skill, not a scheduled task

Packaging + import is event-driven (it fires off a drift finding) and registration needs a human click — it cannot run unattended. Invoke on demand, or immediately after the drift check flags a repo-newer skill.
