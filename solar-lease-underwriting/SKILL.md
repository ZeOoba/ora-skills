# Solar / Rooftop Lease Underwriting (ORA) (v1.3)

## Scope and skill tie-break

- **This skill** owns: rent benchmarking against market, the developer's-side pro forma (their expected IRR), the pre-signature property checks (Step 1A), the red-flag checklist, and the negotiation punch list for rooftop solar / community-solar / behind-the-meter (BTM) leases.
- **legal-intelligence** owns clause-level contract analysis (indemnification, SNDA, insurance, default mechanics) — run it in parallel on the actual lease document; don't duplicate its job here.
- **acquisition-underwriting** owns whole-property acquisitions. A solar rooftop lease on a property ORA ALREADY OWNS is this skill's job, not acquisition-underwriting's, even though the buy-box/scorecard mental model (benchmark against comps, flag deviations, produce a recommendation) is deliberately similar.
- Deal pattern covered: a developer (King Energy, Wunderpower or similar) leases roof space from ORA ("Host") to build and operate a rooftop PV system — either enrolled in a state community solar (CS) program, or behind-the-meter with the building tenant buying power under a PPA — paying Host a rent schedule while the developer retains 100% of ITC, depreciation, RECs, and subscription/SREC/PPA revenue. If a proposal instead has ORA self-developing or co-investing, route to portfolio-growth / debt-management for the capital-stack side and use this skill only for the comparative "what would leasing to a developer get us instead" baseline.
- Negotiation framing and the clause-by-clause ask list live in the ORA Energy-Developer Negotiation Playbook template (Project "Alternative Income Portfolio"); this skill feeds it numbers.

## Step 1 — Extract deal terms into a term sheet

Pull from the Lease + Order Form (King Energy's format: Lease + Attachment B Order Form + Exhibits; Wunderpower's format: Project Order + Lease (Exhibit A) + General Terms (Exhibit C); other developers vary):

- System size (kW-DC), estimated annual production (kWh), roof SF occupied, structure (CS vs BTM; BTM = lease plus a tenant-signed PPA)
- Full rent schedule by year band, including whether extension years (typically Year 26+ after a 25-yr initial term to a 34-yr cap, or automatic 2×5-yr renewals) are priced — **flag immediately if extension-year rent is undefined; this is a recurring drafting gap** (found on the Red Branch deal, Order Form silent on Yr 26-34, while the Northwood deal for the same counterparty did define it at $75k/yr + CPI — inconsistent handling across deals from the same developer is a signal, not a coincidence).
- Any zero-rent introductory period and its length; any tolling of the term or rent start (e.g., term runs from COD, not signature)
- Revenue-share / production-linked / SREC-price-linked kicker or "upside guarantee", if any — extract the split (e.g., 90/10) and what revenue line it applies to
- Site Access Fee / roof capex reimbursement: amount, recoupment/clawback terms tied to early termination or rent abatement, and whether it is really a capex offset (funding work ORA would do anyway) vs. incremental value
- **Roof removal-and-reinstall (de/re):** who pays to remove and reinstall the system when the roof is replaced or repaired, any cap, notice period, lost-production compensation owed to the developer during the outage, and whether the developer's own model assumes a roof replacement (year, production loss %, de/re cost assumed). A developer model that assumes $0 de/re while the form puts de/re on Host is the single most common hidden cost (Wunderpower PO §5, 2026).
- Termination provisions: Host redevelopment right, Host buyout/purchase option (basis: FMV of system, plus any Recapture Amount and breakage premium), Default Event mechanics, developer "not viable" walk rights, and specifically the **Recapture Amount** clause — Host-caused early termination within the ITC recapture window (5 years, vesting 20%/yr) typically requires reimbursing the developer's lost ITC. Extract the exact year cutoff and flag it as a contingent liability that constrains disposition/redevelopment optionality through that date.
- ITC/NTP financing contingencies: "3 years to finance+NTP or either party may terminate," "5 years or automatic termination," and any accelerated deadline tied to federal tax-credit phase-out rules in effect at signing — log ALL of these as dated entries in the ORA Critical Deadlines Tracker (Notion collection `c89df6f2-1d18-4341-9e57-6a15a696b14a`) at signature, not after the fact.
- Tenant/host subscription rights to the community solar output (expect none — flag if absent; this is a live negotiating ask)
- Liability cap and claims window (King Energy standard: $1M aggregate, 1-yr claims period) — sanity-check against the asset's fire/structural exposure, not against the deal size
- Power rights: what the developer gets beyond roof area — electrical room space, conduit routes, transformer/pad and meter locations, utility easements, and any exclusivity over the roof, parking canopies, storage or EV charging

## Step 1A — Pre-signature property checks (run on every proposal; each is pass / fail / open)

These are facts about ORA's own property and entity, not the developer's paper. Read the source of record for each (Notion Property Register, executed tenant leases, SDAT/Secretary of State, roof reports); never infer.

1. **Roof age and replacement timing vs system life.** Pull Roof Install Year, Roof Type and Roof Warranty Expiry from the Property Register (and the latest roof inspection / PCA). Compute remaining roof life against the full system term including renewals. If a replacement falls inside the term: (a) prefer replace-before-install (developer often funds via Site Access Fee); otherwise (b) price the de/re event — obtain a de/re quote, or show a range labeled [SPECULATIVE] until quoted, and discount it to PV at the replacement year alongside the rent PV. Report the net PV of rent after de/re. If net PV is negative or immaterial, recommend no deal or a de/re-on-developer term.
2. **Tenant lease expiries vs solar start (COD) and term.** List every tenant in the building with lease expiry date, renewal options, and any roof, exterior, exclusive-use or utility rights in their lease. For **BTM**: the PPA buyer is a tenant whose lease is shorter than the PPA — confirm Host gives no PPA guarantee, no obligation to re-let to a PPA-assuming tenant, and no rent offset if the tenant leaves; quantify how much of the developer's revenue rests on tenants expiring before Year 10. For **CS**: confirm no tenant lease grants roof rights that conflict, and that construction access can be given under each lease's entry clause. Flag any tenant whose lease expires within 12 months of expected COD (construction disruption + re-leasing with a system on the roof).
3. **Host entity authority and duration.** Confirm the exact Host legal name, formation state and good standing, the signing authority (operating agreement / resolution), and the entity's **stated duration** against the full lease term. An LLC whose articles end before the lease does (e.g., Eric Goldberg Family, LLC articles end 12/31/2030) must be amended before execution. Confirm lender consent requirements in any mortgage on the property and whether an SNDA/recognition agreement is required.
4. **Utility and program eligibility.** Confirm the serving electric utility from a bill or utility document (Property Register Electric Utility field; never infer from territory). Maryland community solar is available only in BGE, Pepco, Delmarva Power and Potomac Edison territory — municipal utilities (e.g., Easton Utilities) and co-ops (e.g., Choptank, SMECO) are not, and developers decline them. For Ohio/Missouri, confirm the net-metering / program terms of the actual utility (AEP Ohio vs City of Columbus Division of Power; Evergy).
5. **Tax-credit timing evidence.** For solar beginning construction after 7/4/2026, OBBBA (P.L. 119-21) requires placed-in-service by 12/31/2027. Demand written evidence of beginning of construction for THIS project (physical work of a significant nature, or the 5% cost-incurred safe harbor where available — its availability for wind/solar has been litigation-dependent since Notice 2025-42 was vacated in 6/2026; re-verify current status at signing), and confirm the lease allocates the loss of the credit to the developer (no Host recapture or termination liability if the credit is lost). A developer email saying "we should be able to hold the ITC" is not evidence. Also check FEOC/prohibited-foreign-entity sourcing representations if the developer relies on the credit.
6. **Power rights.** Confirm the lease (a) grants roof area only for export/CS or the BTM system, with no claim on the building's service capacity, (b) lets Host keep or use any new transformer/service capacity built for the project for building load where the utility allows, or at least does not block a future service upgrade, (c) reserves to Host the rights to battery storage, EV charging, parking canopies and any roof area outside the array footprint, (d) requires developer cooperation (and pays its own costs) with any Host service upgrade, and (e) states that the system provides no backup power to tenants unless separately contracted.

## Step 2 — Benchmark the rent

Compute, on the actual (not headline) rent schedule:

- **$/kW-DC/yr** and **$/SF/yr**, both as a 25-year average (including any zero-rent years) and as the peak-tier rate
- **PV of rent at 8%** (ORA default discount rate for this asset class unless stated otherwise), before and after the Step 1A de/re cost
- Compare against recent ORA precedent for the same counterparty/program type before treating any single number as "market" — ORA's two King Energy MD community solar deals priced within $41-60/kW/yr average and $0.41-0.73/SF/yr average but arrived there via very different zero-rent windows (5 vs. 10 years); Wunderpower's 2026 MD offers (55 New Plant Ct 175 kW, 1900 N Broadway 204 kW) priced $40.5-55.0/kW/yr, with CS paying ~20% more rent than BTM for the same roof. A same-counterparty comp can still hide a materially different NPV.
- Never accept a comparison against a single anchor deal as sufficient — pull 2-3 external comps if available via acquisition-underwriting's COMP GRID DISCIPLINE (industrial comps only — see the gap noted in "Known gaps to close" below for why no solar-specific comp source exists yet) or market-monitor before calling a rate fair
- A **flat, non-escalating, non-revenue-linked** rent structure is the market default for this product — the negotiating lever is the floor rent and the length of any zero-rent period, not the escalated out-year rate, which developers will concede more easily since it's discounted furthest

## Step 3 — Model the developer's expected returns (SPECULATIVE unless developer discloses actuals)

Build an unlevered project pro forma from ORA's side of the table — this is inherently an outside view and must be labeled [SPECULATIVE]/[FORECAST]:

1. **Capex:** system kW-DC × current $/W-DC benchmark (source a current SEIA/NREL or Wood Mackenzie C&I benchmark, don't reuse a stale figure) + Site Access Fee (roof capex, paid by developer, NOT part of ITC-eligible basis)
2. **ITC:** current statutory rate × system capex only (not roof capex) — check current law/phase-down and beginning-of-construction status (Step 1A item 5), don't assume a rate from a prior year's memory
3. **Depreciation:** system capex less 50% of ITC value = depreciable basis; apply bonus depreciation rate in effect at signing (100% bonus depreciation restored under OBBBA for property acquired after 1/19/2025, subject to change — verify current status) × corporate rate (21% federal) for the tax shield; note this figure is realized by the developer's tax equity structure, not received in cash 1:1 — apply a monetization haircut (~85-95%) for transferability/tax-equity execution costs
4. **Revenue:** production (with ~0.5%/yr degradation, and the developer's own roof-replacement production loss if modeled) × (a) subscription/bill-credit or PPA rate — **this is the single largest and least-sourced input; sweep a range ($0.07-$0.17/kWh has been used as an illustrative band, not a citation) rather than presenting one number as fact** — plus (b) production/1000 × current state SREC or equivalent REC price (source from a live SREC exchange/SACP figure, not memory)
5. **Costs:** O&M (~$10-18/kW-DC/yr, escalated), subscriber administration (~5-8% of subscription revenue), inverter replacement reserve mid-life, the actual negotiated rent schedule
6. Compute unlevered IRR and NPV; **always present as a sensitivity table across the subscription-rate and installed-cost assumptions**, never a single point estimate, and say plainly that the developer's actual levered/tax-equity sponsor IRR runs materially higher than the unlevered figure — that gap is normal for this asset class, not evidence of a bad model
7. Quantify the rent's contribution: rerun the same model with the rent schedule zeroed out and report the IRR delta in points. This turns "is the rent fair" into a number instead of a vibe, and is the single most persuasive exhibit in a renegotiation conversation. Run it a second time with de/re moved onto the developer and report that IRR delta too — it sizes the de/re ask.

## Step 4 — Red-flag checklist (apply to every proposal before recommending signature)

- [ ] Zero-rent period longer than ~3-5 years with no floor rent
- [ ] No revenue share, SREC-price kicker, or any upside participation for Host
- [ ] Extension-year (post-Year-25) or automatic-renewal rent undefined or missing CPI escalation
- [ ] No ORA/tenant subscription-rights carve-out
- [ ] Recapture Amount / early-termination / purchase-option exposure not quantified in dollars before signing
- [ ] Liability cap materially below plausible fire/structural exposure given system size and roof placement
- [ ] Site Access Fee recoupment terms not modeled against ORA's own early-exit scenarios (redevelopment, sale)
- [ ] ITC/NTP financing deadlines not yet logged in the Critical Deadlines Tracker
- [ ] Deal terms not benchmarked against at least one other comp (internal precedent or external)
- [ ] **Host pays roof de/re, or de/re is uncapped, or the developer's model assumes $0 de/re (Step 1A-1)**
- [ ] **Roof replacement falls inside the system term with no replace-first plan or priced de/re (Step 1A-1)**
- [ ] **A tenant lease expires before COD + 12 months, or (BTM) the PPA outlasts the buying tenant's lease with any Host backstop (Step 1A-2)**
- [ ] **Host entity duration, authority, good standing or lender consent unconfirmed (Step 1A-3)**
- [ ] **Serving utility unconfirmed from a document, or the utility is ineligible for the program (Step 1A-4)**
- [ ] **No written beginning-of-construction evidence for this project, or Host bears any loss-of-credit risk (Step 1A-5)**
- [ ] **Lease silent on power rights: building service capacity, transformer use, storage/EV/canopy reservation, cooperation with Host upgrades (Step 1A-6)**

## Step 5 — Should ORA self-develop instead?

Default answer is **no** unless ALL of the following hold: (a) ORA's entity structure has confirmed tax appetite to absorb the Year-1 ITC + bonus depreciation directly (verify with tax counsel — a family-office pass-through often does not, without a tax-equity partner, which erodes the theoretical edge), (b) ORA is prepared to take on EPC contracting, state program application risk (e.g., MD CSEGS), and utility interconnection risk, and (c) ORA has or will build subscriber acquisition/servicing capability for the community-solar revenue line, which is the largest and most execution-dependent part of the returns. Absent all three, the better lever is renegotiating lease terms (Step 4 punch list), not taking on development risk. Revisit only if ORA scales into a market where it already holds tax capacity and in-house asset management that can absorb O&M near-zero marginal cost.

## Step 6 — Output

Produce: (1) a term sheet extraction, (2) the Step 1A pre-signature checks table (item, source document, result pass/fail/open, action), (3) the rent benchmark table including PV of rent before and after de/re, (4) the sensitized developer pro forma with IRR-impact-of-rent and IRR-impact-of-de/re, (5) the red-flag checklist with pass/fail, (6) a negotiation punch list for anything still executory (feed it into the Energy-Developer Negotiation Playbook template), (7) Critical Deadlines Tracker rows for every date-driven contingency, (8) Property Register updates for any utility, roof or service fact verified along the way, and (9) the pre-filled negotiation playbook and any tenant acknowledgments from Step 7. Run the 16-point QC Gate before presenting if this is going into an institutional deliverable (IC-style memo); a working analysis for Gabriel's own review does not require the full gate but should still cite sources and label every modeled (non-contractual) number.

## Step 7 — Pre-fill the negotiation playbook (automatic, every new proposal)

After Steps 1-4, produce a pre-filled copy of the ORA Energy-Developer Negotiation Playbook so negotiation starts from the numbers, not a blank form. Do this without being asked whenever this skill runs on a new or revised developer proposal.

1. **Template (read-only, never edit in place):** the highest-version `*_Energy-Developer-Negotiation_Playbook-Template_v*.docx` in `Business/Leases All properties/Claude Lease Project Outputs/` (v01 dated 2026-10-15). Stage it; copy it to the session working directory.
2. **Output name:** `YYYY-MM-DD_<Property>-<Developer>_NegotiationPlaybook_v01.docx` in the session `/outputs/` subfolder.
3. **Fill with python-docx** (tables are addressed by index in v01; if the header row of any table below does not match, STOP and report template drift instead of guessing):
   - Table 0 (cover, `Field | Detail`): replace the bracketed tokens for Developer, Property/Host entity, Structure, System, Proposal received, Prepared by/date.
   - Table 2 (`Term | Developer proposal | ORA target | Status`): column 1 = the Step 1 term-sheet value for each row (quote the section reference, e.g. "PO §5: Host pays de/re"); column 3 = `✓` if it meets the ORA target, `✗` if not, `?` if the paper is silent.
   - Table 3 (`# | Check | Source of record | Result | Action / owner`): column 3 = Step 1A result (PASS / FAIL / OPEN) with the document actually read; column 4 = the action and owner for every FAIL or OPEN.
   - Table 4 (`Metric | This proposal | ORA precedent band | Note`): column 1 = Step 2 and Step 3 figures (rent $/kW and $/SF averages, PV of rent at 8% before and after de/re, rent share of developer revenue, developer IRR range, IRR cost of rent, of a 2% escalator and of developer-paid de/re). Keep `[SPECULATIVE]` on every modeled figure.
   - Table 5 (standard asks): leave Open/Settle/Walk text as is; prefix the Issue cell with the developer's current position in one short phrase and mark asks that do not apply (e.g., PPA asks on a CS deal) `N/A —`.
   - Table 6 (clause grid): fill one row per red-flag clause from Step 4 (section, what it says, risk, ask); leave unused rows blank.
   - Leave Sections 6-8 and the appendix unchanged; add the deal to the appendix only after signing.
4. **QC:** open the result (render to PDF with LibreOffice), confirm no `[` tokens remain in tables 0 and 2-4 except fields genuinely unknown (mark those `OPEN`), and that every number ties to the Step 2/3 workings.
5. **Deliver** the pre-filled playbook with the Step 6 outputs. It is internal only: never send it to a developer.
6. **Tenant acknowledgment:** if Step 1A item 2 shows tenants whose leases predate master lease v2.8 / v3.1, also pre-fill `ORA_Template_TenantAcknowledgment_RoofEnergyUtility_v*.docx` (same folder) for each affected tenant: lease facts from the lease abstract, the project in Schedule 1. Draft only; sending it is an outbound counterparty communication that needs Gabriel's in-turn confirmation, and confidential-deal status must be checked before naming the developer.
