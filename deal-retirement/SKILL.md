# Deal Retirement (v1.9)

Lifecycle hygiene skill that retires deal-bound artifacts, scheduled tasks, Notion staging records, and DD packages once a deal closes or is killed.

## Scope

Triggered on deal lifecycle terminal states: CLOSED (acquisition completed) or KILLED (deal terminated before closing).

## Triggers

"Deal closed", "deal killed", "deal dead", "we passed", "retire [deal name]", "archive [deal name]", "post-closing cleanup".

## Inputs

- Deal name / Notion Acquisition Pipeline record
- Closing or kill date
- Deal-specific artifacts (e.g., efulton-dd-tracker)
- Deal-specific scheduled tasks (e.g., efulton-retire-partial-dashboard)
- DD package location (typically SharePoint /Acquisitions/[deal]/)

## Standard Workflows

### Closed Deal Retirement
1. Confirm closing in Notion Acquisition Pipeline; capture closing date and final terms. [v1.9] The Pipeline date is confirmatory only. The closing date of record for steps 2b, 7, 9 and 13 is the settlement date fixed in step 2b(b). If the two differ, use the settlement date and tell Gabriel.
2. Update Notion: deal moved from Acquisition Pipeline to Portfolio (with new property record).
2b. **[v1.7; owned-asset split v1.9] Deal Sourcing Log: stamp the closed deal `WON`.** In the Deal Sourcing Log (`collection://9a6ae219-85a3-4621-899c-c757fd062f8b`). Work in this order, and write nothing to any row until (e) clears:
   - **(a) Find every row for this deal** with the Killed workflow's 3a existence check: its `Pipeline Deal` relation, then normalized street address, then `Total SF`, then title (the log is known to carry duplicates). Never delete or archive a row. If no row exists, create none and say so.
   - **(b) [v1.9] Fix the acquisition date once, from the settlement statement.** Run `settlement-basis-extraction` on the settlement statement now (step 9 reuses its BASIS_REGISTER; do not run it twice). The settlement date printed on the statement is the acquisition date. On a backfill for an asset acquired earlier, the property's ACQUIRED row in `memory/disposition-ledger.md` (Source = settlement statement) serves instead. Never infer the date from a deed search, the Pipeline Tracker, a listing or memory prose. This one date is used for every comparison and for `Days LOI to Close` below. If neither source gives it, the acquisition date is unknown. Every row is then unresolved: write nothing to any row in 2b, and ask Gabriel for the settlement statement.
   - **(c) [v1.9] Classify each row.** A row's sighting date is the earlier of its `First Sighted` and `Date Seen`. Compare it to the acquisition date:
     - **Pipeline win:** the sighting date is strictly earlier than the acquisition date. The deal was sourced or bid, then acquired.
     - **Owned-asset sighting:** the acquisition date is strictly earlier than the sighting date. This is a re-listing or stale sighting of a property ORA already owned, not a pipeline win.
     - **Unresolved:** the acquisition date is unknown, the row has neither `First Sighted` nor `Date Seen`, or the sighting date and the acquisition date fall on the same day. Write nothing on an unresolved row. List it for Gabriel as a question (row link, the dates found and the source of each), and finish 2b on the other rows.
   - **(d) Pick the canonical row from the pipeline-win rows only:** the one with the richer screening history. An owned-asset sighting is never canonical while a pipeline-win row exists, however rich its history. Each other pipeline-win row is an extra duplicate. If there is no pipeline-win row, there is no canonical row and no duplicate marking; each owned-asset row is handled on its own. Tell Gabriel that this closing has no pipeline-win row in the log.
   - **(e) Run every stop check before the first write.** If any check fires, write nothing on any row of this deal and ask Gabriel:
     - the canonical row's `Status` is `Passed` or `Dead`, which contradicts a closing (ask which record is wrong). On an owned-asset row, `Passed` or `Dead` is expected, because ORA passed on its own asset, and does not stop;
     - any row's `LOI Outcome` (classified or unresolved) reads `LOST`, `SELLER-PULLED`, `WINNER-BUSTED` or `TERMINATED-DILIGENCE`;
     - an owned-asset row carries an `LOI Sent Date` (ORA does not bid on a property it already owns).
     - the canonical row already has `Exclude from Calibration` ticked or `Duplicate Of` set (an earlier 3a or v1.7 run marked the real win as a duplicate). Ask which row is canonical; never clear the flags without Gabriel's answer.
   - **(f) Writes on the canonical row.** Set `LOI Outcome` = `WON` when it reads `PENDING`, `EXPIRED-UNSENT` or empty, including a deal closed without an LOI (by proposal or direct negotiation). `WON` is the marker every arm of `ora-passed-deal-tracker` excludes. A row already at `WON` stays as it is. When `LOI Sent Date` is set, also write `Days LOI to Close` = the acquisition date from (b) minus `LOI Sent Date`, in days. The tracker's Step 4b writes the same column with a competitor's close on lost bids, so a read of ORA's own LOI-to-close velocity filters on `LOI Outcome` = `WON` and `Exclude from Calibration` unticked. Leave `Exclude from Calibration` unticked, so win-rate and `Days LOI to Close` calibration count this closing. `Status` stays as it is (the select has no closed value; the Pipeline Tracker carries Closed).
   - **(g) Writes on each extra pipeline-win row:** tick `Exclude from Calibration` AND set `Duplicate Of` to `app.notion.com/<canonical page id, 32 hex> (deduped YYYY-MM-DD)`, exactly as 3a does. **[v1.8] Both duplicate flags are required together;** one without the other is incomplete. The back-test (`maintenance/funnel-backtest.py` in `~/.claude`) recovers the scan's first-sighting prediction across a duplicate set by parsing that 32-hex id. `Verdict at First Sighting` and `Score at First Sighting` are never copied, moved or cleared on any row of the set (3e).
   - **(h) [v1.9] Writes on each owned-asset row.** Set `LOI Outcome` = `WON` on the same terms as (f), so the tracker stops trade-checking the row. Tick `Exclude from Calibration`. Append one line to `Notes / Flags` (append only, never overwrite): `⛔ OWN ASSET — LOI Outcome WON <stamped|confirmed> <YYYY-MM-DD> (deal-retirement v1.9 Step 2b) so the passed-deal tracker stops trade-checking it. ORA acquired <address> <acquisition date> (<source: settlement statement / disposition-ledger>), BEFORE this <sighting date> sighting — not a pipeline win; do not count in win-rate calibration.` Use "confirmed" when the row already read `WON`. If the row already carries a `⛔ OWN ASSET` line, do not append a second one. Leave `Status`, `Duplicate Of`, `Days LOI to Close`, `Verdict at First Sighting` and `Score at First Sighting` as they are (3e). An owned-asset row is excluded for its own reason, not as a duplicate, so v1.8's both-flags duplicate rule does not apply to it: `Exclude from Calibration` ticked with `Duplicate Of` blank is complete for this row, and the `⛔ OWN ASSET` line records why.
   - Write nothing else on these rows, and re-fetch them to confirm the values read back.

   **Why:** the tracker builds its watch list from every row with `Status` in {Passed, Dead, Screened}, a PASS or KILLED `Verdict`, or screen-time GATE-FLAGGED / FLOOR-FLAGGED notes, plus (Step 2a) every row whose `LOI Outcome` is `LOST`, `PENDING` or `WINNER-BUSTED`. A closed deal still carrying a screen-time flag, a stale `Status` or an unflagged duplicate stayed on that list. Once its deed recorded, ORA's own purchase could be read as the clearing or winning price and the acquisition logged as a passed or lost deal, in the one calibration channel the back-test relies on. No skill wrote `WON` before v1.7; the tracker spec excludes `WON` rows from every arm as of 2026-11-05. **Why v1.9:** `WON` alone fixed the tracker but created the opposite error. A property ORA already owned that resurfaced as a lead was stamped `WON` and would have counted as a pipeline win in the December back-test, inflating win-rate. `WON` keeps the row off the tracker. `Exclude from Calibration` keeps it out of calibration: the December back-test agenda (`tools/backtest_agenda.py`) already filters its lost-deal count on it. No win-rate or LOI-to-close reader exists in the repo yet, and any future one must filter on it. Canonical selection is restricted to pipeline-win rows so that a richer re-listing row cannot push the real win into the duplicate set, where it would be excluded.
3. Move DD package: SharePoint /Acquisitions/[deal]/ → SharePoint /Portfolio/[property]/Acquisition-DD/. If `deal-folder-intake` built a hash-verified deal folder (mirrored at `Claude_Workspace\01_Workspace\Deals\<Property_Name_City_ST>`), that folder is the package to move.
4. Retire deal-specific artifacts: list_artifacts → identify any with deal slug → archive (delete or move to ora-archive folder).
5. Disable deal-specific scheduled tasks via update_scheduled_task with enabled=false.
6. Add property to active operating workflows: lease-renewal pipeline, monthly close checklist, insurance renewal calendar, tax appeal calendar.
7. Schedule one-time post-mortem task at +90 days post-closing.
8. Append a row to `memory/deal-decision-ledger.md` — Verdict = CLOSED, one-line reason (e.g. "closed at $X, financed via Y"), and buy-box rule validated/refined if the deal confirmed or stress-tested a governor or screening heuristic.
9. **[v1.3] Append the ACQUIRED baseline row to `memory/disposition-ledger.md`** — Date = the settlement date fixed in step 2b(b) (from the settlement statement, never the Pipeline closing date), Property = property address, Event = "ACQUIRED", Terms/Amount = purchase price + financing structure (1031 QI / seller-financed / assumed loan / unencumbered, as applicable), Rationale = "Baseline acquisition", Source = settlement statement. [v1.9] If step 2b(b) found no settlement date, do not append; ask for the statement. If the ledger already holds an ACQUIRED row for this property (a backfill), do not append a second one. Use the `settlement-basis-extraction` run from step 2b (run it now only if 2b did not); its BASIS_REGISTER supplies the price and basis figures for this row, so nothing is retyped. This is a DIFFERENT file from step 8's `deal-decision-ledger.md`, which stops at the CLOSED verdict — `disposition-ledger.md` is where the asset's life continues from here (future HOLD/REFI/1031/SALE rulings from disposition-analysis land in the same row-per-event). Do not skip this step believing step 8 already covers it; the two files have no overlap by design (see disposition-ledger.md's own "Scope boundary" note).
10. ### Killed Deal Retirement

**Retiring a deal means writing BOTH Notion databases, always.** The Acquisition Pipeline Tracker records the decision; the Deal Sourcing Log is what `ora-passed-deal-tracker` actually sweeps every month for a later trade. Writing only the first is the failure mode this workflow now exists to prevent — see step 3.

1. Capture kill reason in Notion (price, DD finding, market change, financing).
2. **Acquisition Pipeline Tracker row** (`collection://bcfe4a03-7e61-4ac1-a0bb-c44174fa138b`) — set `Stage` to the terminal value matching the decision (`Passed` for a pass, `Killed` for a kill; the Stage select's exact options govern) **and** write `Kill Reason` as a full dated rationale: decision + date + decider, the floors/tests that drove it with their numbers, and a pointer to the decision brief. Stamp `Last Activity` and `Last Substantive Update` with the decision date. Append a dated `## YYYY-MM-DD — DECISION: <verdict>` section to the page body — never overwrite the existing body. Leave `Next Action Date` EMPTY (step 3d). Leave `LOI Status` at its truthful value; it is a known-unreliable field and nothing may branch on it.
3. **[v1.4] Deal Sourcing Log row — MANDATORY, and this row is the canonical passed-deal record.** Data source `collection://9a6ae219-85a3-4621-899c-c757fd062f8b`. There is no Notion Knowledge Base "Deals Passed" log — one was specified here through v1.3 but was never built, and a repo-wide plus Notion-wide search (2026-09-19) found no such database and **no task or skill that reads one**. So this row, not a lessons-learned page, carries the passed-deal record: one fact, one home. A lessons-learned narrative, where the deal warrants one, goes in `Notes / Flags` on this row and in the step-4 memory ledger.

   **3a — existence check first.** Does a Sourcing Log row already exist for this deal? **[v1.8] Run this check (or re-run it) immediately before any create:** query the data source by normalized street address and `Listing URL` across rows of every `Status`, `Dead` and `Passed` included, because a sourcing scan may have created the row since the step began. Query the data source, not search alone (search lags). If a create returns no page ID or a quota notice, follow the scans' STEP 5 CREATE-VERIFY rule: look the row up by the same key and never blind-retry. Query by normalized street address, then by `Total SF`, then by title — the log is known to carry duplicate rows for the same property (`511 Industrial Mile Road`). **If a row exists, UPDATE it. Do not create a second one.** If two rows already exist for the deal, update the one with the richer screening history and surface the duplicate to Gabriel rather than merging or deleting. **Then tick `Exclude from Calibration` on every extra row and set its `Duplicate Of` to `app.notion.com/<canonical page id, 32 hex> (deduped YYYY-MM-DD)`**, both on every extra row; one without the other is incomplete (see 3e) (checkbox property added 2026-09-19, Gabriel-directed) — a `🔁 DUPLICATE` marker in `Notes / Flags` is prose and does not filter, so a duplicate retired to `Status = Dead` still lands inside `ora-passed-deal-tracker` Step 2's watch set and double-counts one pass as calibration evidence. Flag the extra rows only; never the canonical row, and never delete or archive either.

   **3b — field mapping (write every field the deal actually has).**

   | Field | Value |
   |---|---|
   | `Status` | `Passed` |
   | `Verdict` | `PASS` |
   | `Go / No-Go` | `🔴 Pass` |
   | `Walk Price` | the ratified walk price, as computed at screen/IC time |
   | `Ask at First Sighting` | the ask when ORA first saw the deal |
   | `Total SF` · `Year Built` | as verified |
   | `Asset Type` · `Construction Type` | as verified |
   | `Metro / Submarket` | as verified |
   | `Buy Box Score (100)` · `Quality Score` · `Expected Score` · `P(exec) %` | **only where the IC memo/scorecard gives a single number** — see 3c |
   | `First Sighted` · `Date Seen` | first-sighting date |
   | `IC Memo Done` · `IRR Model Built` · `Scorecard Done` | tick each that is true |
   | `Broker / Contact` | the live thread(s), listing side and buy side, stated as such |
   | `DD-Critical Status` | which items cleared, which are still open, and as of when |
   | `Next Action` | `[YYYY-MM-DD] None — deal passed.` plus, if applicable, what a reopen would require |
   | `Notes / Flags` | the dated PASS rationale in full: floors and their numbers, the stale premises corrected, any unresolved conflict in the source data, every deliberately-blank field and why, and pointers to the decision brief and the pipeline row |
   | `Pipeline Deal` (relation) | → the Acquisition Pipeline Tracker page for this deal (Notion back-fills `Sourcing Entry` on that row) |

   **3c — leave these blank, and say in `Notes / Flags` why. Never back-compute a value the deal never had.**

   | Field | Leave blank when |
   |---|---|
   | `Loss Class` | **No LOI was ever drafted or sent.** The classifier is `ora-passed-deal-tracker` §4b's, and it applies ONLY to the LOST-AT-LOI arm (`LOI Outcome` ∈ {LOST, PENDING, WINNER-BUSTED}) — deals ORA actually bid on. With no LOI there is no `ORA Offer Price` and no `ORA Max Defensible Price` (which §4b and `loi-generation` §6c both require to be fixed at LOI time and **never** back-computed). Do not write `UNCLASSIFIED` either: that value signals a *failed classification of a real loss*, and asserting it would misrepresent a screen-stage pass as a lost bid. |
   | `Floor Result` | No single option (PASS / FAIL-BASIS / FAIL-YIELD / FAIL-BOTH / N/A) is truthfully the whole story — e.g. the IRR floor failed while yield-on-cost cleared, or basis fails only at one end of the replacement-cost range. Put the split result in `Notes / Flags` instead of forcing an option. |
   | `Economics Score` (and any number field) | The memo gives a **range**, not a value. A number property cannot hold a range; write the range in `Notes / Flags`. |
   | `Asking Price` | Live sources disagree and the conflict is unresolved. Record both figures with their fetch dates in `Notes / Flags`; do not pick one. |
   | `Source` | No existing select option accurately describes how the deal arrived. Describe the channel in `Notes / Flags`; do not force the nearest option. |
