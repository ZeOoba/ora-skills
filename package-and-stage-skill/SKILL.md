# package-and-stage-skill

Companion to `ora-skill-store-drift-check`. Turns a "repo newer → re-upload to Cowork/claude.ai needed" finding (or any repo skill edit that must reach the platform) into one staged, one-click installer.

**Source of truth = the git repo** `C:\Users\Owner\ora-skills\<skill>\SKILL.md`. The AppData runtime cache is a read-only mirror that rebuilds from the platform after import — never write it directly (2026-06-11 Roaming-alias clobber incident).

**Registration is human-gated.** This skill packages and stages; it does NOT install. A session cannot write the skill registry — Gabriel clicks **Save skill** (or Settings → Capabilities) on the staged `.skill`.

**A publish/unpublished claim in a Rev-log or advisory must be freshly sourced, never carried forward (added 2026-08-15).** Motivated by a Rev 5 log that recorded capex-budgeting as Gabriel-confirmed unpublished as of 2026-08-09, while the Code catalog separately carried a 2026-08-12 update — nothing had re-checked live state between the two records, so a Rev 10 pass had no way to tell which was current without a manual walk. Before ANY session writes a sentence asserting a skill IS or IS NOT currently published/enabled, run `python tools\skill_drift_report.py --publish-status <skill ...>` and cite its verdict + `checked_at` timestamp inline. Do not cite a prior Rev-log's claim, memory, or the frontmatter version token alone as evidence of current publish state — only a fresh run of this flag (or, from a Cowork session, a live `ListSkills` account call) counts as verification. This is a doc-only convention, not a code gate: nothing blocks an un-cited claim from being written, so the discipline is on whoever authors the log entry.

## Input

- **Entry point A (package + stage, default):** one or more skill names. Default: the skill(s) the latest drift-check comment flagged **repo-newer**, or the skill(s) returned by `python tools/pending_reimport.py candidates` — the UNION of the post-commit PENDING-REIMPORT ledger (written by `tools/hooks/post-commit` on every commit that changes a skill's packaged content or the shared `target-markets.json`) and a fresh full repo-vs-cache SHA256 sweep across every packageable skill. **Do not call `pending_reimport.py list` alone as the candidate source** — the ledger only records skills touched by a commit *after* the hook existed (added 2026-07-16); drift that predates the hook, or a hook run that failed/was bypassed, never reaches it, and a session that trusts `list` as exhaustive silently skips those skills' STEP 1b precheck entirely (root-caused 2026-07-16: Changelog v1.7). `candidates` is read-only and never mutates the ledger; a skill it surfaces that only came from the sweep (no ledger line) is exactly the retroactive-blindness case this exists to close. Run `python tools/pending_reimport.py backfill` to persist sweep-only findings into the ledger itself when a durable record is wanted, not just a one-off union.

  **Surface boundary — a Cowork-bash `candidates` run can't see the runtime cache (found 2026-08-03).** `CACHE_ROOT` is a native-Windows AppData path with no mount inside Cowork's `mcp__workspace__bash` sandbox. When `pending_reimport.py candidates`/`sweep_drift` runs from there, `skill_drifted()` cannot tell "the cache directory doesn't exist" apart from "the sandbox can't see it" and short-circuits to "not drifted" either way — so a Cowork-bash run reports **zero cache-side drift regardless of ground truth**. (This is separate from, and not fixed by, the same-day `_win_long()` fix that stopped a POSIX-context path crash in this same tool — that fix makes the repo-vs-repo/shared-dep checks run cleanly from Cowork bash; it does not make the cache-side comparison trustworthy from that surface.) Treat a Cowork-bash `candidates`/`sweep_drift` result as **repo-side-only**: the ledger union and shared-dep direction checks stay valid, but do not treat "no candidates" as verified absence of cache drift. Before proceeding on a Cowork-bash "no candidates" result, either re-run Entry point A's candidate-source step from a Code-surface Windows shell, or verify cache state independently (the Read tool reaches the cache path via host access, unlike this sandbox's bash). Same category of gap and same fix pattern as step 7's Cowork/.claude surface boundary below — don't trust a Cowork-bash result for anything that needs real host filesystem access; hand off to Code instead.
- **Entry point B (pre-packaged install):** explicit path(s) to already-built `.skill` file(s) handed off by an earlier session or another surface, with instruction NOT to repackage. Runs the integrity pre-check below, then steps 5–8 only.

## Entry point B — pre-packaged install (steps 5–8 only)

When handed pre-built `.skill` files, do NOT re-run steps 1–4 and do NOT repackage — the handoff's premise is that packaging already happened. But never install on trust alone; a pre-built package can go stale between build and click (precedent: step 2's entire reason for existing), or can turn out never to have been built at all (2026-08-13, below). **The handoff's premise is a claim, not a fact — item 1 is what tests it, and it runs before anything else.**

**Bridge-first freshness screen (2026-08-15) — run this ONE cheap check before the per-package pre-check, whenever the Desktop Commander bridge is live.** Don't assume every named package still needs installing just because it was handed off that way. Cross-check two independent, fast signals: (a) a live `ListSkills` account call — does the target skill's description string already show the cited version, enabled; and (b) a Desktop-Commander SHA256 compare between the skill's AppData `skills-plugin` cache copy (locate via `Get-ChildItem … -Recurse -Directory -Filter '<skill>'` under `%APPDATA%\Claude\local-agent-mode-sessions\skills-plugin`) and its current repo copy. Both matching means the click already happened — in this session or an earlier unlogged one — so skip the rest of the per-package pre-check, `present_files`, and any Save-skill ask for that package entirely; go straight to Step 7's "already in sync" logging instead of presenting a redundant button. Only a package that DOESN'T clear this screen proceeds to the full per-package pre-check below. Full incident (2026-08-15: this exact check caught `package-and-stage-skill` v1.17 already installed moments before a redundant Save-skill ask): Changelog v1.18(a). Not a substitute for the per-package integrity pre-check on anything that fails to match — that one still runs in full, since a fast screen finding "maybe already installed" is not the same guarantee as "verified exists/entries/freshness."

Replace steps 1–4 with this integrity pre-check, per package (for whichever packages the bridge-first screen above didn't already resolve):

1. **Exists — assert it, never assume it (hardened 2026-08-13).** The `.skill` file is at the stated path. This is a hard assertion on every named path, run FIRST and never waived on the strength of a circumstantial-sounding handoff (a real commit SHA, a named packaging tool, a plausible `_staging` path). If the stated path is empty or absent, sweep before concluding: the session's uploads dir, `ora-skills\_staging\` (including its dated subdirs), `Downloads`, `Desktop`, and a filename search across `C:\Users\Owner`.

   **If no package is found anywhere → MISSING, not stale. Different finding, different remedy.**
   - **Stale** = a package exists but no longer matches the repo → REJECT and route back to Entry point A to *re*build.
   - **Missing** = no package was ever built → the handoff premise is false, and a "do NOT repackage" instruction does **not** bind, because there is nothing to re-package. Proceed to Entry point A and build the FIRST package, stating plainly that the premise failed and why. Do not stop and ask; do not let the instruction's letter block its own purpose. Then run steps 0–8 in full — in particular step 0 (`plugin_of`) and step 1 (git-clean + `git log -1`), which the Entry point B path would otherwise have skipped entirely.
   - Either way, **surface the discrepancy explicitly** rather than quietly repairing it. A claimed packaging run that never happened is a write-side reporting failure; an existence check that silently self-heals destroys the only evidence of it.

   **Why this is asserted rather than assumed.** A plausible-sounding handoff (real commit SHA, named packaging tool, HEAD) can still describe a packaging run that never happened — nothing downstream of packaging can catch it, since items 2–4 (entries, freshness, stage) all presuppose a file to open, and step 2's hash-vs-repo check only hardened the READ side (a hash match is not proof of install). This item is the write-side counterpart. Full incident (2026-08-13, `dirty-tree-triage.skill` claimed built from a real commit, no artifact anywhere on the machine): Changelog v1.14.
2. **Entries.** List zip entries: forward-slash paths, expected file set (`SKILL.md` plus any `references/`/`templates/`/`scripts/` files and, for `SHARED_ROOT_DEPS` consumers, the injected shared dep).
3. **Freshness.** SHA256 the packaged copy of each shared root dep against the CURRENT repo-root copy (and, where the handoff claims SKILL.md currency, spot-check it against the repo skill dir). EOL rule applies: raw mismatch → CRLF→LF-normalized re-compare → only a normalized mismatch is real. A stale package is REJECTED — route back through Entry point A to rebuild; never install a package that no longer matches the repo. Stale is not the same finding as missing — see item 1 for the distinction and its different remedy.
4. **Stage.** Copy the verified `.skill` into the current session's outputs directory (present_files needs it there to render the Save-skill button). **Also baseline the target cache directory's own CreationTime here, unconditionally (2026-08-21 fix)** — Entry point B skips step 2 entirely, so without this the pre-click CreationTime step 7's fallback discriminator needs is never captured on this path, leaving that fallback unusable exactly when `main.log` corroboration is unavailable.

Then proceed with steps 5–8 unchanged: surface via `present_files`, route multi-file skills to the Cowork Save-skill button, verify the runtime cache post-install, and log the confirmed click to `event_log.md`. First exercised 2026-07-16 (target-markets.json refresh: 4 pre-built consumer-skill packages installed this way).

## Procedure

0. **Plugin-membership routing — the WRONG-target gate (both entry points, run FIRST).** Before treating a skill as a standalone `.skill`, check whether it is a member of a version-controlled plugin bundle: `python -c "import sys;sys.path.insert(0,'tools');from package_skills import plugin_of;print(plugin_of('<skill>'))"` (or read `plugins/*/plugin-build.json`). If it returns a plugin name, the skill does NOT install via a standalone Save-skill click — that lands a shadow copy while the plugin's loaded copy stays stale (proven 2026-07-16: deal-retirement / submarket-spatial-analysis live only in the `ora-operations-extensions` bundle). **STOP the standalone path** and instead rebuild the plugin: `python tools/build_plugin.py <plugin> "<session outputs dir>" [--bump patch]`, `present_files` the resulting `.plugin`, and on confirmed install verify the plugin cache mirror (`…\rpm\plugin_<id>\skills\<skill>\`, not the standalone skills-plugin cache) before clearing the ledger. **The repo side of that byte-comparison is the skill's canonical top-level dir** — `C:\Users\Owner\ora-skills\<skill>\SKILL.md`, NOT `plugins\<plugin>\skills\<skill>\`: the bundle has no per-skill source tree; `build_plugin.py` assembles each member from its top-level dir at build time. Comparing against a `plugins/…/skills/…` path silently resolves to a non-existent file and reads as a FALSE mismatch (2026-07-17). The post-commit ledger already tags plugin members with `plugin: <name> | remedy: rebuild plugin …`; honor that tag. Only if `plugin_of` returns `None` do steps 1–8 (standalone) apply.
1. **Confirm source.** `C:\Users\Owner\ora-skills\<skill>\SKILL.md` exists. Run `git status --short -- <skill>/`; if dirty, STOP and commit first — repo-first rule: the repo leads the platform, never the reverse. Record the last commit (`git log -1`).

   **Commit by pathspec, never bare — the shared-index race (added v1.25, 2026-08-22).** `ora-skills` is a shared checkout that several Claude sessions write to concurrently, and **the git index is shared state between all of them.** A bare `git commit -m "…"` commits whatever is in the index at that instant, not what this session staged — so another session's `git add`, landing in the seconds between your `git status` check and your `git commit`, silently rides into your commit under your message. Always name the paths:

   ```
   git commit -m "<msg>" -- <skill>/SKILL.md <skill>/references/…
   ```

   A pathspec-limited commit ignores the rest of the index entirely and is the only form safe in this repo. Two corollaries: (a) `git status` is a **snapshot, not a lock** — re-check `git diff --cached --name-only` immediately before committing and confirm it contains only your paths; (b) if it does not, do NOT `git reset` the extra paths away as a reflex — that is another session's live WIP, and unstaging it races them back. Commit by pathspec and leave their staged work untouched.

   **Verify after committing, always:** `git show --stat --oneline HEAD` must list only your files. If it lists more, the sweep already happened — `git reset --soft HEAD~1`, `git restore --staged` the foreign paths, and recommit by pathspec, which returns those files to exactly the state you found them in. Full incident (2026-08-22, `acquisition-underwriting` v4.13 refi-rate change): a bare commit swept two `acquisition-underwriting-eval-harness` files another session was actively editing; caught by the post-commit `--stat` read, split back out, and the other session committed its own work four minutes later unharmed. **Note the near-miss in the diagnosis, not just the fix:** the first hypothesis was that the pre-commit hook auto-staged by top-level directory prefix (`acquisition-underwriting` matching `acquisition-underwriting-eval-harness`). It does not — `tools/hooks/pre-commit` contains no `git add` on any path. Do not "fix" the hook; the hook is not the mechanism, and a prefix-match patch there would have shipped a wrong repair for a real bug. Concurrency is the mechanism.

   **Claim before you edit, when the session will make more than one commit (v1.26).** The pathspec rule above makes each individual commit safe; it does nothing about two sessions editing the same `SKILL.md` minutes apart. `~/.claude/hooks/lib/claim_work.py` exists for that and nothing routes to it by default — `dirty-tree-triage` v1.1 pairs its ora-skills check with a claim, but a session that goes straight to packaging never passes through that skill. So: on the Code surface, take a claim on each target skill dir before the first edit of a multi-commit session, and release it at hand-off. From Cowork with no bridge the claim is unreachable — in that case say so in the hand-off rather than implying the edit was serialized. A claim is not a lock either; it is a declaration another session can see, which is strictly more than the index offers.

   **When the contested file is the one you are editing.** If `git status` shows the target skill's own `SKILL.md` staged or modified by another session, STOP and report rather than editing — you are looking at an in-flight doctrine batch, and an edit now races a version bump you cannot see. `dirty-tree-triage` (attribution + two-pass mtime settle) and `isolated-commit` (claim, stage, push) are the skills for that case; this step's job is only to detect it. Contested WIP is reported, never force-resolved.
2. **Hash-compare the runtime cache for CONTENT, then gate the short-circuit on `main.log` — never on the hash alone (rewritten 2026-08-13).** Before packaging, hash-compare every file in the repo skill dir against its counterpart at `…\local-agent-mode-sessions\skills-plugin\<outer-UUID>\<inner-UUID>\skills\<skill>\` (SHA256 via PowerShell `Get-FileHash`; same file count, same names, same hashes). **Normalize line endings before declaring drift:** the platform import stores LF while git autocrlf gives Windows working copies CRLF, so a RAW hash mismatch on a `*.md`/text file may be content-identical. On any raw mismatch, re-compare with CRLF→LF-normalized, trailing-whitespace-trimmed content; only a normalized mismatch is real drift — a raw-only mismatch counts as content-IN-SYNC. **But a content match is no longer sufficient to STOP.**

   **Why the hash alone stopped being trustworthy.** `tools/sync_appdata_mirror.py` (pre-commit Check 4) copies every staged skill's shipped files into every AppData mirror directory that already exists for that skill, on every commit — before this step ever runs. So once a skill has been installed at least once, the repo-vs-cache hash is guaranteed to match the just-committed content by construction, regardless of whether the platform account has actually re-imported anything since; hash alone would certify a freshly committed skill as "already installed" even with zero real installs. Full incident (2026-08-13, commit d03fe62 five-skill batch): Changelog v1.13. `_staging/PENDING_REIMPORT.md`'s own header states the doctrine: *"Hash vs repo — confirms WHAT installed, never WHETHER."* Only `AppData\Roaming\Claude\logs\main.log`'s non-zero `Delta: N to download` → `Sync complete: N downloaded, 0 failed` for this skill, at a timestamp no earlier than the skill's current repo commit, establishes that an install actually happened; cache mtime against a pre-click baseline is the second-line signal; hash-vs-repo is third and content-only, per the ledger's own priority order.

   **Revised gate:** STOP (skip packaging) only when BOTH hold: (i) `main.log` shows a non-zero `Delta:` → `Sync complete: N downloaded, 0 failed` cycle for this skill at or after its current repo commit's timestamp, AND (ii) the skill has no pending line in `_staging/PENDING_REIMPORT.md` (`pending_reimport.py list`/`candidates`). Only then log the one-line `event_log.md` “already in sync” note (“`<skill>` already in sync at v`<X.Y>`, no reimport needed”) and stop. In every other case — including a hash MATCH with no corroborating `main.log` cycle, which is evidence the mirror-sync hook ran, not evidence of installation — proceed to step 3. **Shared root deps are part of the content comparison.** For skills listed in `tools/package_skills.py` `SHARED_ROOT_DEPS` (as of 2026-08-15: acquisition-underwriting, daily-brief, deal-comparison, market-monitor — all sharing repo-root `target-markets.json`; `rent-comp` was a consumer here until its 2026-08-05 retirement removed it from the dict), the repo skill dir deliberately does NOT contain the dep; the packager injects it from the repo root at package time (see the skill dir's `PACKAGING-NOTE.md`). The pre-check must therefore hash-compare the REPO-ROOT copy of each shared dep against the cache's copy — a skill-dir-only comparison silently skips the data file entirely, and does NOT copy the dep into the skill dir to "fix" a perceived gap (2026-07-16: that produced a duplicate zip entry). Discovered 2026-07-16: the cache's target-markets.json was substantively stale (contradicted Notion ground truth on the Pipeline 'Market' rename) and only an unprompted diff caught it. This step exists because a 2026-07-15 session was dispatched to reimport two skills already packaged, staged, and installed by an earlier *unlogged* session — the handed-off premise ("hasn't reached the runtime yet") was stale, and only a hash check caught it before wasted packaging and a needless Save-skill ask.

**`main.log` liveness — check it before trusting either side of the gate (added 2026-08-21).** Both halves of the revised gate assume `main.log` is actively being written. It isn't always: the desktop build can go quiet for a day or more between app restarts (observed 2026-08-21 — last line "going down for update" at 2026-08-20 20:51:03, zero `SkillsPlugin` activity of any kind the following day). When `main.log`'s own mtime is stale relative to now, condition (i) can never be satisfied for ANY skill regardless of what actually happened on the platform side — treat that as "main.log unavailable," not as "no install occurred," and fall back to the cache-directory CreationTime discriminator (step 7) instead of concluding non-installation from silence. **Baseline the cache directory's own CreationTime during this pre-check UNCONDITIONALLY, every run — not only when `main.log` already looks stale (2026-08-21 fix).** Whether step 7's fallback ends up needed depends on `main.log`'s state at verification time, which can change between the pre-check and the post-install check; capturing the baseline is a cheap directory-stat and the alternative (an Entry-point-A session reaching step 7 with no baseline because step 2 skipped capturing it) leaves the fallback itself unusable exactly when it's needed. Entry point B's own integrity pre-check below captures this same baseline for sessions that skip step 2 entirely.

**There are TWO `main.log` files — check the Local one, not just Roaming (added 2026-08-22).** Everything above (and every prior incident that motivated it) was checking `%APPDATA%\Claude\logs\main.log` — the ROAMING copy — and finding it stale. A SEPARATE file at `%LOCALAPPDATA%\Claude\Logs\main.log` (note the different casing and directory: `Logs` not `logs`) is actually the one the desktop app writes `[SkillsPlugin]` sync activity to continuously; it was found live and current (last write matching the current session's clock) on the same machine, at the same moment the Roaming copy had gone dark for over a day. Check the Local path FIRST — only fall back to the CreationTime-only discriminator when BOTH paths are stale. **But the Local log is skill-blind — it never names which skill was synced.** Its `[SkillsPlugin] Delta: N to download` / `Sync complete: N downloaded` lines carry only a count, not a skill name, and the desktop app frequently re-triggers the same pending sync 2-4 times a few seconds apart (confirmed live: a single register-scheduled-task click produced two separate `Delta: 1`/`Sync complete: 1` pairs two seconds apart), so a raw count cannot be attributed to one specific skill when multiple installs are in flight around the same time — treat a bare "a sync happened around then" as circumstantial, not proof. The correlation that DOES work: **match the log timestamp against that skill's own cache-directory CreationTime move to the second.** When a skill's CreationTime moves to, say, `18:15:57`, and the Local log shows a `Delta: 1 to download` / `Sync complete: 1 downloaded` pair at exactly `18:15:57`, that pairing is first-hand, skill-specific evidence — stronger than CreationTime alone, since it additionally rules out the mirror-sync-hook explanation (that hook never touches `main.log`). A log entry with no CreationTime match, or a CreationTime move with no log entry at the same second, is each individually still meaningful (per the existing CreationTime doctrine below) but should not be over-stated as "log-confirmed."

**A shared-dep hash mismatch is not automatically "reimport needed" — check direction first.** A raw hash mismatch on a `SHARED_ROOT_DEPS` file means either the cache is a stale older version (fix = repackage + reimport) OR the cache holds runtime-only content that was never committed to the repo (fix = commit the cache content back to the repo FIRST — reimporting would DOWNGRADE the runtime, reproducing the 2026-07-16 target-markets.json episode). Never assume direction by eye. Before proceeding to step 3 on a shared-dep diff, run `python tools/pending_reimport.py shared-deps` (or read the direction-aware advisory block `candidates` already appends after its primary candidate list) and check the label for the affected dep/skill pair: `REPO-AHEAD` or `MISSING-IN-CACHE` → proceed to package + reimport as normal; `CACHE-AHEAD` or `DIVERGENT` → **STOP**, do not repackage that shared dep — surface the runtime-only content to Gabriel so it can be committed to the repo (CACHE-AHEAD) or manually reconciled (DIVERGENT) before any reimport touches it; `UNKNOWN` → git history was unavailable, verify the direction by hand before proceeding.
2a. **Pre-flight frontmatter gate (added v1.21).** Two defects make the platform importer reject a `.skill` with **no error text anywhere** — the Save-skill click is simply a no-op: a `description` over **1024 characters**, or a frontmatter `name` not byte-identical to its directory. `tools/package_skills.py` catches both, so this only bites on the paths where that tool cannot run — a cloud Cowork session with no Desktop Commander bridge, a hand-built `_staging` package, any `.skill` assembled without the repo. Assert it yourself there:

    ```python
    import os, re, sys
    root = sys.argv[1].rstrip("/\\"); want = os.path.basename(root)
    b = re.match(r"^---\n(.*?)\n---\n",
                 open(os.path.join(root, "SKILL.md"), encoding="utf8").read(), re.S).group(1)
    nm = re.search(r"^name:\s*(\S+)\s*$", b, re.M).group(1).strip("'\"")   # quotes are legal
    d  = re.search(r'^description:\s*"?(.*?)"?\s*$', b, re.M | re.S).group(1)
    bad = ([f"name {nm!r} != dir {want!r}"] if nm != want else []) + \
          ([f"description {len(d)}/1024"] if len(d) > 1024 else [])
    print(("FAIL: " + "; ".join(bad)) if bad else f"OK name={want} description={len(d)}/1024")
    sys.exit(1 if bad else 0)
    ```

    **Check the budget BEFORE editing a description, not after (v1.27).** Run
    `python tools/description_budget.py <skill>` — it reports `N/1024` and remaining headroom,
    and `--budget <chars>` exits non-zero unless the skill can absorb an edit of that size.
    Run with no arguments it ranks every skill tightest-first. The 1024 ceiling is not
    theoretical: `settlement-basis-extraction` sits at 1019 (**5 characters of headroom**),
    `package-and-stage-skill` at 1015, and six more are under 30. Learning this at package
    time costs an edit-trim-recheck cycle every time (twice in one session, 2026-08-22).

    **`.strip("'\"")` in the snippet above is load-bearing.** `name: "debt-management"` is a
    legal quoted YAML scalar and installs fine; `package_skills.py` strips quotes before
    comparing (its line 179). Through v1.26 this snippet did NOT, so it reported a false
    `NAME MISMATCH` on the two skills that quote their name — `debt-management` and
    `masterlease-revision-cycle` — both of which are installed and working. A fallback
    checker that disagrees with the real packager is worse than no fallback checker.

    A hand-built archive also skips the entry rules step 3 delegates to the packager — assert those too: forward-slash entries only (backslash → importer rejects, APPNOTE 4.4.17.1), no directory records, `<skill>/SKILL.md` at the expected path. `zipfile.ZipInfo` with explicit arcnames satisfies all three; `shutil.make_archive` and `Compress-Archive` do not. **Report `description N/1024` and the `name`/dir pair rather than a verdict**, so a silent rejection downstream is ruled out by reading the report instead of rebuilding.

    Authoring a skill cloud-side does not exempt step 1: the repo is still the basis. Read `C:\Users\Owner\ora-skills\<skill>\SKILL.md` over the bridge before editing — never the `~/.claude/skills/synced/` mirror, which serves the last *imported* version and silently lags any repo commit not yet re-installed.

3. **Package — sanctioned tool ONLY.** Via Desktop Commander on Windows: `python tools\package_skills.py "<session outputs dir>" <skill ...>`. NEVER PowerShell `Compress-Archive` (writes backslash zip entries → importer rejects per zip-spec APPNOTE 4.4.17.1; ruling 2026-06-11). The tool validates frontmatter (`name` == dir, `description` ≤ 1024 chars), scans named-count headers across every `*.md`, and asserts forward-slash entries. A non-zero exit is a real defect — surface it verbatim, do not work around it. **Host-shell discipline — SKILL-WIDE, not just this step.** Every Desktop Commander PowerShell invocation ANYWHERE in this skill — packaging here in step 3, but just as much the verification/hash-compare, `main.log` reads, `append-event-log.py`, and `pending_reimport.py clear` calls in step 7 — that uses `$` variables or spans multiple statements goes in a `.ps1` file run via `powershell -NoProfile -ExecutionPolicy Bypass -File <path>`, never an inline `powershell -Command` one-shot. `$` tokens are stripped in transit and the command arrives mangled or throws a parser error. Default to the `.ps1`-file pattern for every DC PowerShell call in this skill; do not attempt inline first and fall back only on error. Full incident (recurred 5 times across two sessions before being scoped skill-wide): Changelog v1.18(b).

   **Canonical invocation (copy this, don't re-derive it — added 2026-08-21).** Write the script with Desktop Commander `write_file` to an absolute path under the repo or `_staging` (never a temp path the host can't resolve), then run it:
   ```
   powershell -NoProfile -ExecutionPolicy Bypass -File "<absolute-path-to-script>.ps1"
   ```
   Inside the `.ps1`, use one `Set-Location` line (or fully-qualified paths) instead of chaining commands — Windows PowerShell 5.1, the default host shell here, has no `&&` statement separator and throws `InvalidEndOfLine` on `cmd1 && cmd2` (confirmed live 2026-08-21). `$` variables and multi-statement logic are unrestricted inside the file.

   **`Start-Process -ArgumentList` splits on spaces — and EVERY ORA root has spaces (v1.27).** The array form silently mangles paths:
   ```powershell
   # WRONG -- "C:\Users\Owner\OneDrive - Oxford Capital Partners\Business" arrives as
   # three arguments, and the script runs against "C:\Users\Owner\OneDrive"
   Start-Process python -ArgumentList @($script, $root, "--quiet")

   # RIGHT -- one string, every path quoted inside it
   $a = '"{0}" "{1}" --quiet' -f $script, $root
   Start-Process python -ArgumentList $a -RedirectStandardOutput $out -NoNewWindow
   ```
   This is the same failure class as the inline-`-Command` `$`-stripping rule above: the command is not rejected, it is quietly rewritten. **It does not error — it succeeds against the wrong target and prints a confident result.** A sweep that reported `1 workbook(s) | 0 dead-or-partial` had walked `C:\Users\Owner\OneDrive`, not the Business tree; it took two occurrences in one session (2026-08-22) to spot, because both looked like clean runs. Sanity-check the item count any detached job reports before believing its verdict.

   **Resource-lint any skill that ships a `scripts/` directory, before packaging (v1.27).** Run `python tools/script_resource_lint.py <skill>`. It flags a small set of high-confidence memory hazards — `openpyxl.load_workbook()` without `read_only=True`, unbounded `pandas.read_*`, whole-file `.read()`, materialised recursive walks — plus the `Start-Process -ArgumentList` array form above. Advisory, not blocking: silence a deliberate one with `# resource-ok: <reason>` on the flagged line, which forces the justification to be written down. **This exists because every gate ORA had passed a script that then used 9.1 GB and exhausted the machine's paging file** (model-bulk-edit v1.0, 2026-08-22): frontmatter validation, packager entry checks, a syntax check and a live self-test all went green, because none of them look at resource behaviour. "It only reads files" is not a resource argument.
4. **Stage.** Emit the `.skill` into the current Cowork session's outputs directory (the one that maps to `/mnt/user-data/outputs`). **Cloud Cowork sessions (2026-08-14):** the packager runs on the Windows host and cannot write a cloud session's outputs directly — emit to `ora-skills\_staging\<date>\`, then transfer into the session: connect `C:\Users\Owner\ora-skills` as a session folder and `device_stage_files` the artifact (folder grants are per-session — request once at session start), falling back to a base64 bridge with end-to-end SHA256 verification only when no folder can be connected. Either way the byte-identity of the staged copy is asserted by hash, never assumed.
5. **Surface.** `present_files` the `.skill` → renders the **Save skill** install button.
6. **Route multi-file skills to Cowork, not desktop Settings.** If the skill has ANY file beyond `SKILL.md` (a `references/`, `templates/`, or `scripts/` dir), tell Gabriel to install via the Cowork **Save skill** button, not Settings → Capabilities → Skills. **Confirmed bug (reproduced twice, 2026-07-11):** the desktop Settings single-`.skill` upload path silently drops subfolder files on import — `SKILL.md` lands, `references/*.md` etc. do not — while the Cowork install path installs the full package correctly. Single-file skills (no subfolders) are unaffected by either path.
7. **Verify post-install, then log the click — not just the commit.** After Gabriel confirms installation, check the AppData runtime cache mirror contains every file the packaged `.skill` did — not just `SKILL.md`. If any file is missing, the install silently failed (most likely the desktop-Settings bug above); tell Gabriel to re-install via Cowork instead of assuming the drift is closed.

   **Cache-directory CreationTime is the discriminator between a real re-import and a mirror-sync overwrite (added 2026-08-21, main.log-unavailable case).** `sync_appdata_mirror.py`'s in-place content overwrite (v1.13) rewrites file bytes but leaves the containing skill directory's own CreationTime untouched; a genuine platform Save-skill install tears down and recreates that directory, so its CreationTime moves to (approximately) the click time and every file inside shares that same creation timestamp. When `main.log` corroboration is unavailable (step 2), compare the cache directory's CreationTime against the pre-click baseline captured during the pre-check — a moved CreationTime is first-hand evidence of a real re-import; an unchanged one, with only file mtimes/hashes matching, is exactly the hash-match-by-construction case v1.13 already distrusts. Confirmed live 2026-08-21 (`acquisition-proposal-generation` v3.1): the cache directory's CreationTime moved from 16:21:45 (pre-click, itself of uncertain provenance) to 16:46:25, with all 5 files created at that same instant.

   Once verified, log the confirmed install to `event_log.md` in the same pass: skill name(s), version, confirming timestamp, and that this was Gabriel's **Save-skill click**, not merely the upstream repo commit. A repo commit is evidence the fix was authored; it is not evidence anyone installed it — that gap (a click that happened but was never logged) is exactly what caused the 2026-07-15 redundant-dispatch near-miss step 2 now catches on the read side. This log entry is what lets a future step-2 pre-check, or a drift-check, trust "already installed" from the log instead of re-deriving it from a hash comparison every single time. **Then clear the skill from the post-commit ledger** so it stops reading pending: `python tools/pending_reimport.py clear <skill>`. The verified cache re-sync is the ONLY thing that clears an entry — a commit sets it, a confirmed install clears it.

   **Surface boundary (Cowork sessions cannot write `event_log.md` directly).** `event_log.md` and `append-event-log.py` live under `C:\Users\Owner\.claude\...`, a Code-only surface. Confirmed 2026-07-27: a Cowork session attempting `request_cowork_directory` on `.claude` itself, on `.claude\maintenance`, and on the `.claude\projects\...\memory` subpath was rejected on all three — every path under `.claude` is fail-closed to Cowork mounting, no partial carve-out exists. When this skill runs in a Cowork session, step 7 cannot execute the log write in-session: prepare the exact `event_log.md` entry line(s) (skill name, version, confirming timestamp, "Save-skill click" language) and hand them to Gabriel to run through `append-event-log.py --entry-file <path>` (never stdin — cp1252/encoding gotcha) from a Code session. Do not treat step 7 as complete, and do not clear the post-commit ledger, until that Code-side write is confirmed — a prepared-but-unexecuted log entry is exactly the "click happened but was never logged" gap this step exists to close. On the Code surface itself, no such boundary applies and step 7 runs as originally written, in-session.

   **Bridge carve-out (2026-08-14) — the boundary binds only when the session has no path to the Windows host.** A Cowork session with the Desktop Commander bridge (`mcp__remote-devices__Desktop_Commander__*` tools live) reaches `C:\Users\Owner\.claude\...` natively — the 2026-07-27 finding was about `request_cowork_directory` mounting, not about host access in general — so step 7 runs IN-SESSION over the bridge: `python C:\Users\Owner\.claude\maintenance\append-event-log.py --entry-file <path>` (never stdin — cp1252/encoding gotcha). The prepare-and-hand-to-Gabriel path above remains the fallback ONLY for Cowork sessions with no Desktop Commander bridge.

   **Never trust a pre-staged `_staging` draft without a fresh verify — and archive it once its package is confirmed installed.** `_staging/<date>/` is a shared scratch folder many concurrent sessions write into on the same date; a later session can find pre-written log-entry drafts, hash claims, or "already in sync" verdicts sitting there from an earlier, unidentified run. Do not reuse any of it on trust, no matter how plausible the wording or how real the cited hashes look — re-derive `plugin_of`/git-log/hash/cache-state facts fresh for this session's own entry every time. Full incident (two contradictory same-day drafts, one already appended into `event_log.md` as fact): Changelog v1.19. Once a package's install is confirmed, logged, and its `PENDING_REIMPORT` entry cleared, move that package's now-spent `_staging/<date>/` artifacts to `_archive/<date>_<context>/` — never delete (Hard Invariant 6).
   **CLOSING SWEEP — run `repo_first_check.py` at the END of the session too, not only before packaging (added 2026-08-24).** The pre-packaging run answers "is this skill safe to package." It says nothing about what the session's own commits did to the rest of the store, and cache-ahead content can appear at any point in a session — including from a concurrent session, or from a Save-skill click on a skill built elsewhere. Before signing off, run **all three**:
   - `python tools/repo_first_check.py` — must end `no cache-ahead skills`. A **CACHE-AHEAD** result is urgent, not informational: `sync_appdata_mirror.py` runs as pre-commit Check 4 and copies staged skills' files repo → mirror, so the next commit touching that skill silently overwrites the newer cache copy with the older repo one. The tool auto-rescues to `_staging/repo-first-rescue/<skill>/`, which is the only reason the content is recoverable at all — reconcile it into the repo before anything else touches that skill.
   - `python tools/frontmatter_sweep.py` — must end `0 finding(s)`. The per-skill gates only see what you packaged or staged; this sees all of them.
   - `python tools/verify_installed_cache.py [<skill> …]` — reads what the PLATFORM holds, for anything installed this session.

   Live catch, 2026-08-24: a closing run flagged `owner-outreach` CACHE-AHEAD — another session's v1.3 SKILL.md plus `ORA_OwnerOutreach-T1Letter_FormatSpec_v1.1.md` and `t1_letter_format.py`, none of which existed on any branch. That session had made three commits already; a fourth touching that skill would have destroyed ~16 KB of content. Reconciled at `4c9206d` after confirming the cache copy was a clean superset (145 of 146 repo lines preserved). It surfaced only because the check was run at the end.

   **The platform's skill listing is NOT a per-skill diagnostic.** It truncates: a long alphabetical tail renders name-only, and which skills land there changes between renders (`loi-generation` and `listing-agreement-qc` showed full descriptions early on 2026-08-24 and name-only later, unchanged). Never read name-only as a defect, and never confirm an install from the listing alone — use the three commands above.
8. **Hand off.** Tell Gabriel: click **Save skill** (or, for single-file skills only, Settings → Capabilities) to register. After import the runtime cache re-syncs to the new version — that closes the drift; a re-run of `ora-skill-store-drift-check` should then read IN-SYNC.

## Why a skill, not a scheduled task
