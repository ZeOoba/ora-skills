- v1.24 (2026-08-22: check the LOCAL main.log, not just Roaming — and how to attribute its skill-blind counts). An independent review pass verifying a register-scheduled-task event_log entry found `%LOCALAPPDATA%\Claude\Logs\main.log` — a second, separate file from the `%APPDATA%\Claude\logs\main.log` this skill has always checked — actively live with direct `Sync complete` corroboration at a moment the Roaming copy had been stale for over a day. Every prior main.log-liveness incident (v1.16, v1.22) was checking only the Roaming path. Retroactively re-applied to this reimport cycle's two "click provenance inconclusive" flags: `debt-management` and `package-and-stage-skill` itself both turned out to have genuinely re-imported LATER than originally checked — their cache CreationTimes had since moved (18:15:57 and 17:53:56 respectively) to timestamps that match exact Local-log `Delta: N`/`Sync complete: N` events to the second, resolving both as confirmed installs (see event_log.md 2026-08-22). `repo-architecture-review`'s flag stays open — its CreationTime never moved at all, and no Local-log event correlates to it. Also documented a real limitation found while doing that correlation: the Local log's sync lines carry only a count, never a skill name, and the app frequently re-triggers the same pending sync 2-4 times a few seconds apart — so a bare "a sync happened around then" is not skill-specific proof; only an exact-second match against that skill's own CreationTime move counts as first-hand evidence. Doc-only; no packaging, hash, or ledger logic changed.

- v1.25 (2026-08-22: commit by pathspec — the shared-index race). Step 1 gains the rule that a bare `git commit -m` in `ora-skills` commits the whole index, not this session's staged paths, and the index is shared with every other concurrent Claude session. Found live during the `acquisition-underwriting` v4.13 refi-rate change: a bare commit swept two `acquisition-underwriting-eval-harness` files another session was mid-edit on into `febb870` under the refi-rate message; caught by a post-commit `git show --stat` read, split out via soft-reset + `git restore --staged` + recommit, and the other session committed its own work cleanly four minutes later (`7d10e3f`). **The wrong-fix near-miss is recorded deliberately:** the first diagnosis was that `tools/hooks/pre-commit` auto-staged by top-level-directory prefix, and the proposed remedy was a prefix-exact match in the hook. The hook contains no `git add` at all — the remedy would have patched a mechanism that does not exist while leaving the real race open. Also added: `git status` is a snapshot, not a lock (re-check `git diff --cached --name-only` immediately pre-commit); never reflexively `git reset` foreign staged paths, which races the owning session back; and a STOP-and-report branch for when the target skill's own `SKILL.md` is itself staged by another session, routing to `dirty-tree-triage`/`isolated-commit` rather than editing into an in-flight doctrine batch. Doc-only; no packaging, hash, or ledger logic changed.

- v1.26 (2026-08-22: route to claim_work.py by default). v1.25 made each individual commit safe by pathspec but left the wider race open: two sessions editing the same `SKILL.md` minutes apart is not something a pathspec fixes. `~/.claude/hooks/lib/claim_work.py` already exists and nothing routed to it — `dirty-tree-triage` v1.1 pairs its ora-skills check with a claim, but a session that goes straight from edit to packaging never passes through that skill, which is exactly the path this skill describes. Step 1 now says to claim each target skill dir before the first edit of any multi-commit session and release at hand-off, with the honest caveats that a Cowork session without the DC bridge cannot reach the claim (say so rather than implying serialization) and that a claim is a visible declaration, not a lock. Doc-only.

- v1.27 (2026-08-22: two new repo tools + two doc fixes, all from failures this skill's own gates missed). **(a) `tools/description_budget.py`** — reports frontmatter `description` headroom BEFORE an edit, with `--budget <chars>` to assert a planned edit will fit; no-args ranks every skill tightest-first. Two overflows in one session (1052/1024 then 1064/1024) were each caught only at package time, after the edit was written. The ranking immediately surfaced how little slack exists: `settlement-basis-extraction` 1019/1024 (**5 chars**), this skill 1015, six more under 30. **(b) `tools/script_resource_lint.py`** — advisory scan of packaged `scripts/` for memory hazards (`load_workbook` without `read_only=True`, unbounded `pandas.read_*`, whole-file `.read()`, materialised recursive walks) and the `Start-Process -ArgumentList` array form; `# resource-ok: <reason>` silences a deliberate case. Written because `model-bulk-edit` v1.0 cleared frontmatter validation, packager entry checks, a syntax check AND a live self-test, then consumed 9.1 GB and exhausted the machine's paging file on its first real run — no existing gate looks at resource behaviour. It found one genuine pre-existing hit on first run: `rent-roll-reconciliation/scripts/parse_rent_roll.py:24`. **(c) Step 2a's snippet was WRONG and is fixed** — it compared the raw `name:` capture against the directory without stripping quotes, so it reported a false `NAME MISMATCH` on `debt-management` and `masterlease-revision-cycle`, both of which quote their name legally and are installed and working. `package_skills.py` has always stripped quotes (line 179); the documented fallback disagreed with the real packager on 2 of 64 skills. **(d) `Start-Process -ArgumentList` array-form trap** added to step 3's host-shell discipline: it splits on spaces, every ORA root contains spaces, and the result is not an error but a confident run against the wrong directory — a sweep reporting `1 workbook(s)` had walked `C:\Users\Owner\OneDrive`. Doc + tooling only; no packaging, hash, or ledger logic changed.

- v1.28 (2026-08-24: closing sweep + two new tools). **Step 7 now requires a CLOSING SWEEP before sign-off, not just a pre-packaging check.** `repo_first_check.py` was only ever run before packaging, which answers "is this skill safe to package" and nothing about what the session's own commits did to the rest of the store. Cache-ahead content can appear at any point in a session — from a concurrent session, or from a Save-skill click on a skill built elsewhere. Live catch the day this was written: a closing run flagged `owner-outreach` CACHE-AHEAD, holding another session's v1.3 SKILL.md plus two files (`ORA_OwnerOutreach-T1Letter_FormatSpec_v1.1.md`, `t1_letter_format.py`) that existed on no branch; the session had already made three commits and a fourth touching that skill would have had `sync_appdata_mirror.py` overwrite ~16 KB of it. Reconciled at `4c9206d`. **Two new tools back the sweep. (a) `tools/frontmatter_sweep.py`** — runs `validate_skill_frontmatter()` across every skill dir, exit 1 on findings. Written because five skills (`ora-flood-zoning-dd`, `document-assembly`, `exception-detection`, `monthly-close`, `portfolio-reporting`) had shipped their body changelog heading as their description for nearly a month: the 2026-07-29 Phase-4 lint left an unterminated quoted scalar whose closing quote sat in the body, so none of their trigger vocabulary was routing. The per-skill gates never saw it because they only fire on what you package. **(b) `tools/verify_installed_cache.py`** — reads the installed `SKILL.md` in the runtime cache and reports whether the description scalar is balanced. `repo_first_check.py` answers "does the cache match the repo"; this answers "what does the installed file actually say," which is the question when the repo copy itself was in doubt. **Also recorded: the platform's skill listing is NOT a per-skill diagnostic** — it truncates, a long alphabetical tail renders name-only, and membership in that tail shifts between renders (`loi-generation`, `listing-agreement-qc` on 2026-08-24). Never confirm an install from it. Doc + tooling; no packaging, hash, or ledger logic changed. Description trimmed to restore headroom (was 1015/1024).
