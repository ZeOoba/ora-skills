# package-and-stage-skill — Changelog (v1.0–v1.19)

Archived from `SKILL.md` 2026-08-22 (ORA Automation Audit Revision 18 remediation — repo-only, excluded from packaging per `tools/package_skills.py`'s top-level `versions/` exclusion). Current version's changelog entry lives in `SKILL.md` itself; only superseded entries move here going forward.

- v1.19 (2026-08-16: never trust pre-staged `_staging` drafts + archive-on-clear). Found live during a same-day repo-architecture-review first install: `_staging/2026-08-16/` held two mutually contradictory pre-written `event_log_entry_*.md` drafts for the same install — one roughly matched what actually happened, the other claimed the skill was "already installed by a concurrent session" before packaging had even run, directly contradicted by the installing session's own pre-packaging cache sweep (empty) — yet the false draft had already been appended into `event_log.md` itself as if it were fact. Step 7 now states explicitly: never reuse a pre-staged draft's wording, hashes, or verdict on trust; re-derive this session's own `plugin_of`/git-log/hash/cache-state facts fresh every time. Also added: once a package's install is confirmed+logged+ledger-cleared, move its spent `_staging/<date>/` scratch (build scripts, superseded/false drafts, intermediate patch files) to `_archive/<date>_<context>/`, never delete (Hard Invariant 6) — closes the "staging folder becomes a source of contradictory drafts" gap the same session flagged. Doc-only; no packaging/hash/ledger logic changed.
- v1.18 (2026-08-15: bridge-first freshness screen for Entry point B + host-shell discipline generalized skill-wide + `_STAGED.ok` manifest accumulates). Three fixes from the same Cowork/DC-bridge Entry point B session that installed automation-health-monitor v1.5 and found package-and-stage-skill itself already at v1.17: (a) **Entry point B gains a bridge-first freshness screen** run before the per-package pre-check, whenever the DC bridge is live — a `ListSkills` account check cross-checked against a Desktop-Commander AppData-cache-vs-repo SHA256 compare. A match on both skips the rest of the pre-check, `present_files`, and any Save-skill ask for that package, going straight to Step 7's "already in sync" logging. Proven live: caught package-and-stage-skill v1.17 already installed (from an earlier, unlogged session) moments before this session would otherwise have asked for a second, redundant click, alongside genuinely-pending automation-health-monitor. (b) **Host-shell discipline (originally step-3-only, 2026-08-14) re-scoped skill-wide.** The same session hit the inline `powershell -Command` `$`-stripping failure THREE more times doing step-7 verification/`main.log` reads/`append-event-log.py`/`pending_reimport.py clear` work — none of it packaging — proving the failure is inline `-Command` itself, not anything specific to `package_skills.py` calls. Step 3's rule now states explicitly it binds every DC PowerShell invocation anywhere in this skill; default to a `.ps1` file, don't try inline first. (c) **Companion `tools/package_skills.py` fix (same day, same investigation):** `write_staging_manifest()` was overwriting `_STAGED.ok` on every batch instead of accumulating — a second same-day batch into a shared `_staging/<date>/` outdir silently erased the first batch's entries, which is exactly what made automation-health-monitor's own packaging invisible to this session's freshness triage and forced a manual per-file git-log/hash fallback to confirm it wasn't stale. Now merges by skill name across every batch written into an outdir, adds a `last_batch` field so a caller can still tell "this invocation packaged zero things" apart from "the outdir has zero packages ever," and tolerates a corrupt prior sentinel without blocking the write. 5 new tests in `tools/test_package_skills.py` (`StagingManifest`: second-batch-preserves-first, repackage-refreshes-not-duplicates, last-batch-reflects-current-invocation, corrupt-sentinel-does-not-block); full 45-test suite green.

- v1.16 (2026-08-15: publish-state claims must be freshly sourced): added a doc-only rule that any Rev-log/advisory sentence asserting a skill's current publish/enabled state must cite a fresh `tools/skill_drift_report.py --publish-status <skill>` run (or a live Cowork `ListSkills` call), never a prior Rev-log's claim carried forward. Root-caused from a Rev 10 remediation pass finding a Rev 5 log's "Gabriel-confirmed unpublished 2026-08-09" claim for capex-budgeting silently stale against a 2026-08-12 Code-catalog update, with nothing having re-verified live state in between. Companion change, same day: `tools/skill_drift_report.py` gained a `--publish-status` mode (INSTALLED / NOT INSTALLED / BROKEN INSTALL per named skill, sourced from the runtime cache at read time) so the citation is a one-line, timestamped command rather than a manual cache walk; 4 new tests in `tools/test_skill_drift_report.py` (`PublishStatusRendering`). - v1.14 (2026-08-13: Entry point B item 1 hardened — existence asserted, missing distinguished from stale): item 1 was a bare one-liner ("The `.skill` file is at the stated path") with no instruction to actually verify it and no branch for the file not being there. A same-day dispatch to install a pre-built `dirty-tree-triage.skill` from commit 3eabd33 was entirely plausible on its face — the SHA was real, was HEAD, and had added the skill's two source files — but no `.skill` artifact existed anywhere on the machine (not attached, not in `_staging`'s ~100 packages, not in Downloads/Desktop, absent from a filename sweep of `C:\Users\Owner`); the packaging run had been reported but never happened. Items 2–4 cannot catch this — they all presuppose a file to open — and v1.13 hardened only the READ side (a hash match is not proof of install). Item 1 is now the write-side counterpart: a hard assertion run first, an explicit sweep before concluding absence, and a MISSING branch separate from STALE. Missing means the handoff premise is false, so a "do NOT repackage" instruction does not bind (there is nothing to re-package) — route to Entry point A, build the FIRST package, run steps 0–8 in full including the step 0 `plugin_of` and step 1 git-clean checks Entry point B would have skipped, and state the discrepancy rather than silently self-healing it.
- v1.13 (2026-08-13: Step 2 short-circuit rewritten — hash-vs-repo demoted to content-only signal): `tools/sync_appdata_mirror.py` (pre-commit Check 4, live 2026-07-26) copies every staged skill's shipped files into every already-existing AppData mirror on every commit, which means Step 2's repo-vs-cache hash comparison is guaranteed to match immediately after any commit to a previously-installed skill — regardless of whether the platform account has re-imported anything. The two tools were never reconciled: Step 2 dates from v1.2 (2026-07-15), eleven days before the mirror-sync hook existed. Proven by the 2026-08-13 commit d03fe62 five-skill batch: all five read byte-identical to the repo before any Save-skill click (`lease-abstraction-pipeline`'s cache mtime matched the commit second-for-second); following the old Step 2 literally would have stopped the batch and certified five non-installs as done. Step 2 now STOPS only when `main.log` shows a non-zero `Delta:` → `Sync complete: N downloaded, 0 failed` cycle for the skill at or after its current repo commit AND the skill has no pending `_staging/PENDING_REIMPORT.md` line — matching the doctrine the ledger's own header has stated since it was written ("Hash vs repo — confirms WHAT installed, never WHETHER"). A bare hash match no longer short-circuits anything on its own.

Found alongside (but distinct from) the same-day `_win_long()` fix in `pending_reimport.py`, which stops a POSIX-context path crash but does not make cache-side comparisons trustworthy from Cowork bash. - v1.7 (2026-07-16: retroactive-blindness fix): Entry point A's default candidate source changed from `pending_reimport.py list` (ledger only) to `pending_reimport.py candidates` (ledger UNION a fresh full repo-vs-cache SHA256 sweep, EOL-normalized, across every packageable skill). The ledger only ever records skills a commit touched after tools/hooks/post-commit existed (e5903c2, 2026-07-16) — drift predating the hook, or a hook run that failed/was bypassed, was silently invisible to any session that treated `list` as exhaustive, meaning those skills never even reached STEP 1b's precheck. Root-caused from acquisition-underwriting (v4.1, commit b76bf94) and this skill's own v1.5 (commit 4218063) both predating the hook and sitting stale in the runtime cache with no ledger entry. `candidates` is read-only (never writes); `pending_reimport.py backfill` persists sweep-only findings into the ledger for anyone who wants a durable record instead of a one-off union. A skill with no cache directory at all (never installed) is correctly excluded from both — that's ora-skill-store-drift-check's separate REPO-ONLY category, not a reimport candidate.
- v1.6 (2026-07-16): wired to the new post-commit PENDING-REIMPORT ledger. `tools/hooks/post-commit` now calls `tools/pending_reimport.py record HEAD` on every commit that touches a skill's packaged content or the shared `target-markets.json`, writing the affected skill(s) to the untracked `_staging/PENDING_REIMPORT.md` — a commit-time signal that closes the repo-ahead-of-cache gap at its source instead of waiting for the next drift audit (root-caused from acquisition-underwriting sitting at v4.0 after v4.1 b76bf94 was committed+pushed unreimported). Entry point A now defaults to the ledger as its work queue; step 7 clears the entry (`pending_reimport.py clear <skill>`) only after a CONFIRMED install re-syncs the cache. The hook cannot reimport (the Save-skill click stays manual) — it detects and signals.

- v1.4 (2026-07-16): step-2 pre-check (and post-install verify) must EOL-normalize before declaring drift. The platform import stores LF; git autocrlf checks out CRLF; raw SHA256 therefore diverges on content-identical files, reading perpetually repo-newer. Found the same day v1.3 shipped: the v1.3 post-install verify itself raw-mismatched (repo CRLF vs cache LF) and passed only on normalized comparison. Rule: raw mismatch → normalized re-compare → only a normalized mismatch is drift.
- v1.3 (2026-07-16): step-2 pre-check extended to SHARED_ROOT_DEPS — for the five consumer skills whose `target-markets.json` is injected from the repo root at package time, the hash comparison must include the repo-root copy vs the cache copy, and must never "recover" the dep into the skill dir.
