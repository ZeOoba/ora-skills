# ORA Setup Audit (v1.15)

Formal, evidence-grounded audit of the Claude Code/Cowork environment itself — not a codebase, the harness. Produces the same keep/fix/combine/delete verdict format the "ORA Automation Audit" artifact has used since its first revision, continued in place rather than replaced.

## Guardrails (apply to every thread below)

- **Never flag (skip outright):** anything named in `CLAUDE.md` (skill tie-breaks, Hard Invariants, routing canon) — referenced there means load-bearing regardless of frequency; anything gating a Hard Invariant, a financial governor (DSCR/LTV constants), or a compliance/legal function; anything with a documented multi-year recurrence (e.g. a credential-rotation skill) — rarity by design, not by neglect.
- **Rarity is neutral, not evidence of bloat — use `skillUsage` telemetry, state its surface, never prune on a count alone.** `~/.claude.json#skillUsage` holds `usageCount` + `lastUsedAt` per skill: CC/MCP surface only (a Cowork-only skill reads zero), no time window, and split bare/plugin-qualified names — merge on the segment after the last colon before ranking, and rank by `words × merged count`. A prune verdict needs corroborating evidence (CLAUDE.md references, event_log/memory mentions, task-folder presence on either fleet, explicit supersession language) and you must state what was checked and came back empty. Some skills (`annual-cycle`, `deal-retirement`) are read BY REPO FILE PATH from live tasks, so deleting their directories breaks those tasks silently. Full rationale and the Revision 9/23 measurements: `references/guardrails-telemetry.md`.

## Scope

Six independent read-only threads, each cheap to verify and each prone to going stale between audits because nothing else in the environment checks them together:
1. **Plugins & connectors** — `settings.json` (`enabledPlugins`, `skillOverrides`), `plugins/installed_plugins.json`, `plugins/cache/`, `plugins/marketplaces/` (a SEPARATE tree from cache — see `reference_plugin_cleanup_scope_cache_vs_marketplaces.md`, a prior cleanup missed it), `plugins/blocklist.json`, `confidential-repos.json` (repo root, NOT `hooks/` — corrected 2026-08-22, Automation Audit R18 Thread 1 found the un-pathed reference here led to a wrong `hooks/` guess), and any MCP connector config. Cross-check against known-dead connectors in memory (Rube, Composio, QuickBooks Online MCP) to confirm none have crept back.
   **Usage method (no telemetry exists for this category — see Guardrails):** for each installed plugin, roll up its bundled skills' findings from thread 3 — a plugin whose every skill is `keep` is `keep`; a plugin whose every skill is a delete-candidate is itself a delete-candidate. For each MCP connector, cross-check against CLAUDE.md's "Tools & data" hierarchy (Notion/HubSpot/M365/Netlify are named there — `keep` by construction); for anything installed but not named there, check `mcp-needs-auth-cache.json` (repo root) timestamps and any event_log/memory mentions of real use — zero on both is a `delete`-candidate, not a confirmed-unused.
2. **Scheduled-task fleet** — read both registries live (CC/MCP + LAMS/Cowork) via `fleet-status.py`. Look for same-time collisions, duplicate-purpose pairs, missed-cycle tasks (throttled-and-retrying vs gone silent are different bug classes), and throttle-skip trend; diff live membership against `_state/registry-membership.json`; check the FRESHNESS of `_state/` and `maintenance/` outputs themselves (a stale probe output is a finding). **Never run `registry-membership-probe.py` during the investigation** — it overwrites the baseline evidence. Full text: `references/thread-detail.md` § Thread 2.
3. **Skill catalog redundancy** — every SKILL.md in `~/ora-skills` (git status/log first; read-only) plus `~/.claude/skills` and `~/.claude/scheduled-tasks/*/SKILL.md`. Pairwise-check overlapping triggers against CLAUDE.md's Skill tie-breaks before flagging; only an unresolved collision is a finding. **Size check = `wc -w` × merged `skillUsage` count, never size alone**, and report the daily aggregate of scheduled-task spec loads, not just per-file sizes. Check whether a big skill carries a changelog RETENTION RULE and a body-size cap. Full method, prior measurements and the R22 correction: `references/thread-detail.md` § Thread 3.
4. **Token-bloat sources** — CLAUDE.md (`~/.claude/CLAUDE.md`) word count vs. its WARN 1700 / FAIL 1850 gate, counted ONLY by `~/.claude/maintenance/doctrine-integrity-probe.py` (NOT `~/.claude/hooks/`, and never bare `wc -w` — it undercounts by ~135 words, R17-3); MEMORY.md size vs. its 21,500B WARN / 24,400B HARD gate (counted by `~/.claude/maintenance/memory-integrity-probe.py`); `~/.claude/session-context.md` (the SessionStart-injected block — at the repo root, NOT under `maintenance/`, which holds only `session-context-xref-probe.py`) against its 40-line / 80-word-per-bullet caps, and — the check most likely to find something real — whether any self-monitoring artifact this environment produces (the System Schematic, or any future dashboard-style scheduled-task output) has an unbounded growth pattern: an ever-appending log with no cap, duplicated content, or no rollover step. A monitoring tool that becomes the token-spend problem it was built to catch is the single highest-value class of finding here (see the 2026-08-13 schematic rev-log fix, `~/.claude/scheduled-tasks/ora-cc-schematic-refresh/SKILL.md`, for the pattern to check other scheduled-task-authored artifacts against).

5. **Skill hygiene lint** (added v1.13, 2026-09-22) — deterministic, run both, cite output verbatim: `python ~/ora-skills/tools/frontmatter_sweep.py --quiet` (name/description gate, incl. the description-history rule: no version, date or changelog text in `description`) and `python ~/ora-skills/tools/sync_local_skills_mirror.py --all --check` (every `~/.claude/skills` mirror vs. the repo, CRLF-insensitive; exit 1 = drift). Also list skills that exist in only one of `~/.claude/skills` / `~/ora-skills` (a local-only ORA skill has no git backup). Drift is a finding even though post-merge/post-rewrite hooks now repair it — persistent drift means the hooks are not firing (hooksPath unset on a clone, or edits landing outside main).

6. **Subagent cost** (added v1.14, 2026-09-30) — run `python ~/.claude/maintenance/subagent-cost-report.py --top 15` and cite it verbatim with its window. It is a weighted approximation (cache reads at 1/10, usage deduped by `message.id`) for ranking agent types, never billed spend. Check: (a) each type's share of weighted input — at first measurement `general-purpose` was 90%, so the lever was dispatch habits, not agent files; (b) the Fable share of runs (25% at first measurement), and for any type above ~10% sample its first-prompt text for confidential/financial/governor/security work before calling it avoidable (92% of sampled Fable `general-purpose` runs were legitimately hard-tier); (c) `model:` frontmatter across `~/.claude/agents/*.md` against the spec §7.1 tiers — a dispatch's explicit `model` overrides the frontmatter, so judge from the models the report observed, not from the pin; (d) agent-body word counts, since the body loads on every dispatch. **Exempt from downshift verdicts:** agents doing confidential, financial, governor, security or legal-precision work (`security-auditor`, `underwriting-checker`, `psa-redline-checker`, `site-qc-reviewer`, anything the spec names hard-tier) — invariants keep confidential/financial/governor code at Fable or above and reviewer ≥ implementer. Findings are `fix` verdicts on frontmatter or dispatch guidance; any edit follows Step 5 (report, never execute in the audit pass).

## Triggers

"Audit my setup", "optimize my Claude Code environment", "what's safe to remove", "reduce token spend", "refine my skills/plugins/scheduled tasks", or a reference to reviewing "the artifact" (System Schematic and/or Automation Audit) for setup health.

## Inputs

- `Artifact action:list` — find the current "ORA Automation Audit" artifact URL before doing anything else. This skill CONTINUES that artifact as a new numbered revision; it does not create a parallel one. If genuinely none exists (first-ever run), create it using the same masthead/kpi-grid/chip-table conventions this file's reference implementation established.
- The "Claude Code — System Schematic" artifact, if it exists, as a secondary live-status cross-check — but verify its claims against a direct file read before repeating them; its own prose has been wrong before (a transient plugin-flip incident got narrated as current state in one past revision).
- Direct reads of `settings.json`, both scheduled-task registries, `~/ora-skills`, and `~/.claude/maintenance/_state/` — ground truth beats any artifact's prose, always.

## Standard Workflow

0. **Self-check: is this loaded copy current?** (added 2026-08-15, closing the gap Revision 10 found the hard way.) Read `~/ora-skills/ora-setup-audit/SKILL.md`'s H1 version marker (`# ORA Setup Audit (vX.Y)`) and compare it against THIS file's own H1 marker, above. (Descriptions carry no version since v1.13 — the pre-commit gate rejects one.) If they differ, you are very likely running a stale local mirror (`~/.claude/skills/ora-setup-audit/SKILL.md`) rather than the canonical repo copy — exactly what happened to the first unattended run of this skill, which silently executed v1.2 (missing Step 4a's rev-band cap) while the repo had already moved to v1.3. State the mismatch explicitly in the rev-band you publish rather than silently proceeding as if you were current, and flag it as a fresh finding if you cannot see one already recorded. This check only compares version STRINGS, not full content — for the byte-level detector that runs independently of this skill having to invoke itself first, see `setup-self-audit.py`'s `check_skill_mirror_drift()` (added 2026-08-15, Automation Audit R10-1).

   **0b. ACCOUNT SKILL STORE check.** Call `ListSkills` (keywords: this skill's name, `acquisition-underwriting`, `register-scheduled-task`) and compare each description's trailing `vX.Y` with the repo copy. Report any lag, and the same skill enabled twice at different versions as the highest-severity finding (governor-facing). On Cowork the `ListSkills` widget is NAME-keyed and cannot see duplicates — report the sub-check UNPERFORMED there, never clean. The store LIST view truncates descriptions (~550 chars), so version tokens are absent: use the detail page or `tools/verify_installed_cache.py`. Retiring a store copy is Gabriel-only. Full text: `references/step0b-store-check.md`.


   **The store LIST view no longer shows version tokens (added v1.11, 2026-09-07).** The store page truncates each skill's `description` at roughly **550 characters** in the list view, and ORA descriptions carry their `vX.Y` token at the very END — so for most skills the token is simply absent from the list. Never read a missing token as "no version", and do not scrape the list for versions: open the skill's **detail page**, or read the **runtime cache** copy (`tools/verify_installed_cache.py`), which is the only local file reflecting what the store actually served.

1. **Locate continuity.** `Artifact action:list`, find the Automation Audit (or equivalent) URL. Read its most recent revision to know what's already been ruled on — don't re-litigate a closed finding without new evidence.
2. **Run the six threads.** Independent and parallelizable (spawn one Agent per thread if the session supports it) — they don't depend on each other. Each thread reports specific, named, file-and-line-cited findings, not impressions.
   **Every dispatched brief MUST bound its own commands (R22-14, 2026-09-06).** Thread 4's first dispatch on 2026-09-05 died on the 600s stream watchdog with zero output, almost certainly on an unbounded recursive `find` over `~/.claude`; a re-dispatch whose brief said *"never run a command without bounding it — every `find`/`du` depth-bounded with `2>/dev/null`, an explicit timeout on anything slow, many small fast commands rather than one big sweep"* completed normally and produced that revision's two largest findings. Carry that instruction verbatim in every thread brief. The failure is in how the thread is ASKED, not in the environment — and note the second-order cost: a stalled thread tempts the next pass to reprint the prior revision's numbers as if freshly measured, which is the exact evidence-honesty failure the Guardrails forbid. Say a thread stalled; never carry its baselines forward silently.
3. **Cross-verify claims that conflict.** When a source artifact's narrative disagrees with a live read (settings.json says X, the Schematic's prose says Y), the live read wins — say so explicitly rather than silently picking one.
4. **Synthesize into the artifact's existing format:** a new `rev-band` at the top (bump the revision number), updated/added KPI tiles for anything freshly measured, new sections per finding with a `keep`/`fix`/`combine`/`delete`/`ask`/`dead` chip verdict and cited evidence, and a footer note summarizing what changed. Findings that need Gabriel's call (ambiguous scope, a config file with contradictory state, anything touching a single-writer registry) get `ask`, not a unilateral edit.
4a. **MANDATORY rev-band cap (added 2026-08-14, closing a Revision 8 finding — this artifact carried the identical unbounded-growth defect Revision 7 found in the System Schematic: a full rev-band appended every revision, no cap, ever built).** The masthead's stacked `rev-band` divs MUST NOT exceed **4 inline revisions** after any revision's edit. Before publishing:
   - Count the current inline rev-bands, including the one you're adding this pass. If it exceeds 4, move the OLDEST rev-band(s) — full prose and all — to a companion file `~/.claude/artifacts/ora-automation-audit-history.md` (create it if it doesn't exist; APPEND, never overwrite — permanent archive, per standing invariant 6).
   - Replace each moved rev-band with a single collapsed line beneath the kept ones (e.g. "Revisions 1–4 archived to `ora-automation-audit-history.md` — see that file for full prose"), not a bare pointer with no context.
   - **Working copy and caps — `references/artifact-caps.md`:** durable working copy at `~/.claude/artifacts/ora-automation-audit.html` holding only the authored fragment (never a saved read with the frame wrapper; assert no `<script`); each inline rev-band under ~12,000 chars; at most 2 revisions' finding sections inline, older ones APPENDED to `ora-automation-audit-history.md`; no new `<section>` when the findings fit the rev-band.
   - **Snapshot archive (added v1.13, R26-8).** Each revision, move every artifact `.html.bak-*` snapshot to `~/.claude/artifacts/archive/` — archive, never delete (Invariant 6). Five existing snapshots were moved there on 2026-09-22.
   - **Do not add a new `<section>` for a revision whose findings already fit in its rev-band.** Revision 21 deliberately added none for exactly this reason; a revision that appends both a band and a section pays the cost twice.
5. **Do not execute fixes in the same pass unless explicitly asked to.** This skill's job is the investigation and the verdict table; executing `delete`/`fix`/`combine` calls against shared-checkout files (settings.json, scheduled-task registries, `~/ora-skills`) needs the single-writer claim protocol and, for anything hitting the blast-radius list (hooks/, registries, CLAUDE.md, governor code), Gabriel's explicit sign-off — keep investigation and remediation as separately confirmable steps, matching how the 2026-08-05 cleanup was ratified separately from the audit that found it.
6. **Publish via `Artifact`, passing `url:`** to update the existing artifact in place — never omit it, that orphans the link Gabriel already has.
7. **Memory:** one project-memory entry per audit revision (findings + what's pending Gabriel's call), pointed from `MEMORY.md`. Don't duplicate the artifact's content into memory — the memory entry is a pointer plus the two-or-three things a future session needs to know before trusting the artifact's claims at face value.

## Outputs

- Updated Automation Audit artifact (same URL, new revision).
- One project-memory pointer entry.
- Optionally, a short remediation plan (separate deliverable) for any `fix`/`delete`/`combine`-tagged finding Gabriel wants actioned — this skill produces the verdict, not necessarily the execution.

## Non-goals

Does not execute registry writes, plugin uninstalls, or skill deletions itself (see step 5). Does not replace `fleet-advisory-remediation` (which triages a pasted advisory into mechanical fixes) or `orphaned-task-forensics` (which root-causes a specific stale-producer symptom) — this skill is the periodic, broad, evidence-gathering pass those two operate on top of. Does not re-derive `~/.claude/maintenance/setup-self-audit.py`'s dark-task/frontmatter-regression/secret-scan/connector-reauth/skill-mirror-drift checks (already live, wired into `ora-health-guard`) — cite its last output for those specific findings rather than re-running the same logic.

## Changelog

**Retention rule (added 2026-09-07, ORA Automation Audit R23-5 — ported from `register-scheduled-task` v2.18 and `package-and-stage-skill` v1.30, which already carry it):** keep at most the **6 most recent versions** as full inline entries. The moment an edit would add a 7th, that same edit must also compress the oldest full inline entry to a one-line `**vX.Y (date):** Full text: versions/CHANGELOG-vA.B-vX.Y.md` summary and append its full original text to the versions file for that range (opening a new one if the prior range is closed out). Do it inline, in the pass that adds the new entry — never as deferred cleanup, and never wait for an audit to notice. **This file is the sharpest case for the rule:** v1.3 added Step 4a to cap the *artifact's* rev-bands and v1.10 added a per-band length cap to it, while this skill's own Changelog grew uncapped the entire time — the file telling the artifact to bound itself was the one file that never did. v1.10 measured it at 9,696B/29% and deferred the fix; the single v1.11 entry added in between took it to 12,180B/**32.3%**, so the share rose even as the file grew. A one-off extraction does not hold; a threshold does.

**Per-entry length cap (same pass, and the reason the count cap alone is not enough).** The 6-entry rule bounds how MANY entries are inline, never how LARGE each is — the exact defect v1.10 fixed in the artifact's rev-bands and `ora-cc-schematic-refresh` fixed at its v1.4. Cap each full inline entry at **~2,000 characters**, calibrated rather than copied: measured 2026-09-07, this skill's six surviving entries run 1,043–1,754B (mean 1,353B) and `register-scheduled-task`'s three full entries 763–1,296B, so the cap fits every compliant entry today with headroom, while `package-and-stage-skill`'s 2,208B v1.28 — the outlier in the skill that grew 30% — sits above it. An entry that would exceed the cap states its finding and verdict inline and cites its `project_automation_audit_revNN_*.md` memory file for the detail, the same escape hatch Step 4a gives a multi-finding rev-band. Check both caps in the pass that adds an entry.
