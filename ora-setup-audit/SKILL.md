# ORA Setup Audit

Formal, evidence-grounded audit of the Claude Code/Cowork environment itself — not a codebase, the harness. Produces the same keep/fix/combine/delete verdict format the "ORA Automation Audit" artifact has used since its first revision, continued in place rather than replaced.

## Guardrails (apply to every thread below)

- **Never flag (skip outright):** anything named in `CLAUDE.md` (skill tie-breaks, Hard Invariants, routing canon) — referenced there means load-bearing regardless of frequency; anything gating a Hard Invariant, a financial governor (DSCR/LTV constants), or a compliance/legal function; anything with a documented multi-year recurrence (e.g. a credential-rotation skill) — rarity by design, not by neglect.
- **Rarity is neutral, not evidence of bloat.** **Per-skill invocation telemetry DOES exist and you should use it — corrected 2026-09-06 (R23-10), after this clause said the opposite for 13 revisions while contradicting itself in its own next sentence.** `~/.claude.json#skillUsage` holds real `usageCount` + `lastUsedAt` per skill (115 name-variants / 1,011 logged invocations as of Revision 23; Revision 9 used it on 2026-08-14 to produce findings, one day after this clause claimed it did not exist). **Its three real limits, none of which is "it doesn't exist":** (1) CC/MCP surface ONLY — a skill that runs solely via Cowork/LAMS reads zero, so a zero means "not invoked from Code," never "unused"; (2) **no time window** — counts are cumulative from an unrecorded start, so a total cannot be turned into a rate; (3) **split namespaces** — the same skill is counted separately under bare and plugin-qualified names, **20 such pairs at Revision 23** (up from 6 at Revision 9; `docx` spans four), so **always merge on the segment after the last colon before ranking** or you undercount by up to ~65%. Rank by `words × merged count` when you want realized cost, not by size alone. `claude-markdown-health-check`'s Phase 7 JSONL signal (`~/.claude/projects/**/*.jsonl`) is structurally CC/MCP-surface-only in exactly the same way (sampled 25 CC + 25 LAMS sessions: 14/25 CC sessions had a matching transcript file, 0/25 LAMS sessions did — LAMS/Cowork tasks execute in a separate VM/cloud sandbox whose transcripts never sync locally). Treat the two as the SAME blind spot restated, never as independent or corroborating signals. So: **use the counts, and state their surface** — but never let a count alone carry a prune verdict. A prune verdict still needs corroborating evidence (CLAUDE.md references, event_log/memory mentions, task-folder presence on either fleet registry, explicit supersession language in another skill's own description), and you must state what was checked and came back empty so the absence is verifiable rather than asserted. **Revision 23 ran exactly that method over 50 zero- and low-usage skills and returned ZERO delete-candidates** — six of the zeros were zero because Gabriel had already unpublished them, and two (`annual-cycle`, `deal-retirement`) are read BY REPO FILE PATH from live scheduled tasks *precisely because* they are no longer name-invocable, so deleting their directories would break two running tasks silently. Expect that shape again. The question is never "how often does this run" — it's "is there still a reason this needs to exist."

## Scope

Four independent read-only threads, each cheap to verify and each prone to going stale between audits because nothing else in the environment checks them together:
1. **Plugins & connectors** — `settings.json` (`enabledPlugins`, `skillOverrides`), `plugins/installed_plugins.json`, `plugins/cache/`, `plugins/marketplaces/` (a SEPARATE tree from cache — see `reference_plugin_cleanup_scope_cache_vs_marketplaces.md`, a prior cleanup missed it), `plugins/blocklist.json`, `confidential-repos.json` (repo root, NOT `hooks/` — corrected 2026-08-22, Automation Audit R18 Thread 1 found the un-pathed reference here led to a wrong `hooks/` guess), and any MCP connector config. Cross-check against known-dead connectors in memory (Rube, Composio, QuickBooks Online MCP) to confirm none have crept back.
   **Usage method (no telemetry exists for this category — see Guardrails):** for each installed plugin, roll up its bundled skills' findings from thread 3 — a plugin whose every skill is `keep` is `keep`; a plugin whose every skill is a delete-candidate is itself a delete-candidate. For each MCP connector, cross-check against CLAUDE.md's "Tools & data" hierarchy (Notion/HubSpot/M365/Netlify are named there — `keep` by construction); for anything installed but not named there, check `mcp-needs-auth-cache.json` (repo root) timestamps and any event_log/memory mentions of real use — zero on both is a `delete`-candidate, not a confirmed-unused.
2. **Scheduled-task fleet** — both registries live (CC/MCP + LAMS/Cowork), via `fleet-status.py` or direct registry reads. Look for: same-time collisions, duplicate-purpose task pairs, missed-cycle tasks (and whether they're throttled-and-retrying vs. gone silent — two different bug classes, don't conflate them), and throttle-skip trend direction (climbing vs. stabilizing). **Also diff live registry membership against `~/.claude/maintenance/_state/registry-membership.json` (R22-1/R22-2, 2026-09-06)** — a task can vanish from a registry entirely while its spec folder stays on disk, which is the inverse of the dark-task pattern and is invisible to every file-level guard. **And check the FRESHNESS of the `_state/` and `maintenance/` outputs themselves, not only their content:** Revision 22 found three writers (`registry-membership.log`, `override-token-sweep.log`, `session-env-retention.log`) frozen within ~30h of each other, and because every check in this environment asserts on what a file SAYS rather than on when it last changed, a detector that stops producing is invisible — which is exactly why the two dropped money-moving tasks went unnoticed. A stale probe output is a finding in its own right. **Never run `registry-membership-probe.py` as part of the investigation** — it refreshes its own baseline snapshot, destroying the pre-drop evidence any membership finding rests on; cite the frozen snapshot instead and leave running it to remediation.
3. **Skill catalog redundancy** — every `SKILL.md` in `~/ora-skills` (git status/log first — single-writer repo, read-only here so no claim needed) plus any local `~/.claude/skills`. Pairwise-check for overlapping trigger descriptions, and verify every apparent overlap against CLAUDE.md's own "Skill tie-breaks" section before flagging it — most are already resolved there or self-resolve via one skill's description explicitly chaining/deferring to another. Only a genuine, unresolved collision (a frontmatter trigger that contradicts a ratified tie-break) is a real finding. Also flag outsized skills (word count) that are both large AND high-frequency, since that combination is the actual token cost, not size alone. **Scope note (R22-6, 2026-09-06): this size check MUST also cover `~/.claude/scheduled-tasks/*/SKILL.md`, not just the two skill trees.** **⛔ Revision 22's claim that this intersection is "genuinely EMPTY in `ora-skills`" was WRONG and is corrected here (R23-3) — do not repeat it.** It ranked the four LARGEST files, found them all manually invoked, and concluded emptiness without ever weighting by frequency. Weighted properly, the intersection is occupied: `register-scheduled-task` is 5,244w **and** the third-most-invoked skill in the environment (73 merged invocations), having grown 2,028w → 5,244w (+159%) in 21 days. **Method: rank by `wc -w` × merged `skillUsage` count, never by size alone.** At Revision 23 that ranking put 85% of all realized ORA skill-load cost in five skills — `register-scheduled-task` (393,908 word-loads), `package-and-stage-skill` (213,425), `daily-brief` (146,052), `ora-setup-audit` (58,805), `acquisition-underwriting` (53,264) — the top two being internal plumbing rather than deal work. Separately and additively, nine daily-firing CC tasks were loading 53,973 words (~73K tokens) of spec text every day, 61% of it in two files (`ora-health-guard` 16,482w, `ora-pm-ledger` 16,398w — the latter cut to 12,180w on 2026-09-06 by extracting 13 dated build-history NOTE sections to `references/`, ~171K tokens/month). Re-measure the fleet aggregate each pass rather than carrying these forward; report the daily aggregate, not just per-file sizes. **Also check whether a big skill carries a changelog RETENTION RULE** — the threshold, not the one-off extraction, is what holds size down: `register-scheduled-task` adopted one at v2.18 and stayed flat, while `package-and-stage-skill` had an extraction but no rule and grew 30% after being tagged `fix` at Revision 15 (rule added 2026-09-06).
4. **Token-bloat sources** — CLAUDE.md (`~/.claude/CLAUDE.md`) word count vs. its WARN 1700 / FAIL 1850 gate, counted ONLY by `~/.claude/maintenance/doctrine-integrity-probe.py` (NOT `~/.claude/hooks/`, and never bare `wc -w` — it undercounts by ~135 words, R17-3); MEMORY.md size vs. its 21,500B WARN / 24,400B HARD gate (counted by `~/.claude/maintenance/memory-integrity-probe.py`); `~/.claude/session-context.md` (the SessionStart-injected block — at the repo root, NOT under `maintenance/`, which holds only `session-context-xref-probe.py`) against its 40-line / 80-word-per-bullet caps, and — the check most likely to find something real — whether any self-monitoring artifact this environment produces (the System Schematic, or any future dashboard-style scheduled-task output) has an unbounded growth pattern: an ever-appending log with no cap, duplicated content, or no rollover step. A monitoring tool that becomes the token-spend problem it was built to catch is the single highest-value class of finding here (see the 2026-08-13 schematic rev-log fix, `~/.claude/scheduled-tasks/ora-cc-schematic-refresh/SKILL.md`, for the pattern to check other scheduled-task-authored artifacts against).
