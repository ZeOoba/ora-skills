# Step 4a — artifact working copy and caps, full text

Moved verbatim from `SKILL.md` (v1.15 core/reference split, no rule changed). `SKILL.md` keeps the operative checks as stubs; this file holds the full wording, history and measurements.

## Caps

   - Keep a durable working copy of the artifact's HTML at `~/.claude/artifacts/ora-automation-audit.html`, mirroring the System Schematic's DURABLE SOURCE pattern (`ora-cc-schematic-refresh/SKILL.md`) — Read + targeted-Edit that file each revision instead of WebFetching the full published artifact every time. If the working copy and the published artifact disagree (a prior session updated one without the other), the published artifact is authoritative — pull it into the working copy first, then apply this revision on top. **When you do, store ONLY the authored fragment — never a saved read verbatim (added v1.8, R21-14).** An `Artifact action:read` saves the platform's frame-runtime wrapper along with the content: `<!doctype html><html><head>` plus ~34KB of minified runtime JS, ending in a trailing `</body></html>`. That wrapper is re-added on every refresh and nests: at Revision 21 the working copy carried **two** of them (34,026B, 18% of the file) and the published copy three. Before saving, slice from the first `<title>` to the last `</div>` preceding the trailing `</body></html>`, and assert `content.count('<script') == 0` — the authored artifact contains no scripts, so any script tag means wrapper bytes survived. The publisher supplies its own skeleton, so the fragment is what it wants anyway.
   - **Per-band length cap (added v1.10, 2026-09-07 — porting the fix the System Schematic got at Revision 8 and this artifact never received).** The 4-entry count cap bounds how MANY bands are inline, not how LARGE each one is, so a band can grow without limit and never trip it. Measured 2026-09-07: the four "within cap" bands totalled **101,587B** — Revision 23 33,782B, Revision 22 36,361B (which grew again in a republish that added no new revision), Revision 21 24,420B, against Revision 20's 4,473B for a clean verification pass. The newest two are ~8x the reference. `ora-cc-schematic-refresh/SKILL.md` has carried a ~5,000-char per-entry cap since its v1.4 for exactly this failure ("the count cap alone let the file regrow 123.5KB→147KB because one entry ballooned to ~2x the others"); the same reasoning was never applied here. **Keep each inline rev-band — the one you write this pass, and each kept from prior passes — under ~12,000 characters.** The threshold is calibrated, not copied: a clean verification pass fits with room to spare, while a full multi-finding pass must push detail down a layer. Overflow has a designated home already — every revision writes a `project_automation_audit_revNN_*.md` memory file under this skill's own Outputs section, and `event_log.md` carries the dated history; the rev-band is the summary, not the record. Trim to the material facts and the verdict chips, and cite the memory file for the rest.
   - **Section cap (added v1.8, closing R21-11).** The same bound applies to the per-finding `<section>` blocks below the masthead, which Step 4a's original wording did not cover — at Revision 21 they were 88,769B across 16 sections reaching back to Revision 7, 52% of the file and larger than the capped masthead. Keep at most **2 revisions' worth of finding sections inline**; move older ones, full markup and all, to `ora-automation-audit-history.md` under a `## Sections — Revision N` heading (APPEND, never overwrite — same standing invariant 6 as the rev-band rollover), and leave a single collapsed line in their place naming what moved and where. Sections that are not per-revision verdict tables — the standing reference sections (`Where the description payload sits`, `Not the problem`) — are exempt: they are current-state, not revision history.
