## Thread 2

2. **Scheduled-task fleet** — both registries live (CC/MCP + LAMS/Cowork), via `fleet-status.py` or direct registry reads. Look for: same-time collisions, duplicate-purpose task pairs, missed-cycle tasks (and whether they're throttled-and-retrying vs. gone silent — two different bug classes, don't conflate them), and throttle-skip trend direction (climbing vs. stabilizing). **Also diff live registry membership against `~/.claude/maintenance/_state/registry-membership.json` (R22-1/R22-2, 2026-09-06)** — a task can vanish from a registry entirely while its spec folder stays on disk, which is the inverse of the dark-task pattern and is invisible to every file-level guard. **And check the FRESHNESS of the `_state/` and `maintenance/` outputs themselves, not only their content:** Revision 22 found three writers (`registry-membership.log`, `override-token-sweep.log`, `session-env-retention.log`) frozen within ~30h of each other, and because every check in this environment asserts on what a file SAYS rather than on when it last changed, a detector that stops producing is invisible — which is exactly why the two dropped money-moving tasks went unnoticed. A stale probe output is a finding in its own right. **Never run `registry-membership-probe.py` as part of the investigation** — it refreshes its own baseline snapshot, destroying the pre-drop evidence any membership finding rests on; cite the frozen snapshot instead and leave running it to remediation.

## Thread 3

3. **Skill catalog redundancy** — every `SKILL.md` in `~/ora-skills` (git status/log first — single-writer repo, read-only here so no claim needed) plus any local `~/.claude/skills`. Pairwise-check for overlapping trigger descriptions, and verify every apparent overlap against CLAUDE.md's own "Skill tie-breaks" section before flagging it — most are already resolved there or self-resolve via one skill's description explicitly chaining/deferring to another. Only a genuine, unresolved collision (a frontmatter trigger that contradicts a ratified tie-break) is a real finding. Also flag outsized skills (word count) that are both large AND high-frequency, since that combination is the actual token cost, not size alone. **Scope note (R22-6, 2026-09-06): this size check MUST also cover `~/.claude/scheduled-tasks/*/SKILL.md`, not just the two skill trees.** **⛔ Revision 22's claim that this intersection is "genuinely EMPTY in `ora-skills`" was WRONG and is corrected here (R23-3) — do not repeat it.** It ranked the four LARGEST files, found them all manually invoked, and concluded emptiness without ever weighting by frequency. Weighted properly, the intersection is occupied: `register-scheduled-task` is 5,244w **and** the third-most-invoked skill in the environment (73 merged invocations), having grown 2,028w → 5,244w (+159%) in 21 days. **Method: rank by `wc -w` × merged `skillUsage` count, never by size alone.** At Revision 23 that ranking put 85% of all realized ORA skill-load cost in five skills — `register-scheduled-task` (393,908 word-loads), `package-and-stage-skill` (213,425), `daily-brief` (146,052), `ora-setup-audit` (58,805), `acquisition-underwriting` (53,264) — the top two being internal plumbing rather than deal work. Separately and additively, nine daily-firing CC tasks were loading 53,973 words (~73K tokens) of spec text every day, 61% of it in two files (`ora-health-guard` 16,482w, `ora-pm-ledger` 16,398w — the latter cut to 12,180w on 2026-09-06 by extracting 13 dated build-history NOTE sections to `references/`, ~171K tokens/month). Re-measure the fleet aggregate each pass rather than carrying these forward; report the daily aggregate, not just per-file sizes. **Also check whether a big skill carries a changelog RETENTION RULE** — the threshold, not the one-off extraction, is what holds size down: `register-scheduled-task` adopted one at v2.18 and stayed flat, while `package-and-stage-skill` had an extraction but no rule and grew 30% after being tagged `fix` at Revision 15 (rule added 2026-09-06).
